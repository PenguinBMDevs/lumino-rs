## REF-LGS-015：limiter 的 LOOKAHEAD=256 与设置页允许的 64/128 块长冲突——切片下溢 panic

> **类型**：Bug ｜ **优先级**：High ｜ **工作量**：Low

## 现象
`crates/audio/gpu-synth/src/synth/engine/limiter.rs:18` 定义 `LOOKAHEAD = 256`（帧，"~4 ms @ 64 kHz"），而设置页的 LGS 缓冲区选项提供 **64 / 128** 帧（`crates/editor/ui-settings/src/pages/audio/lgs.rs:56` 的 `clamp(6, 13)` = 64..8192）。
当 `block_size < 256` 时，`block_size*2 < 512`，limiter 的延迟线索引会变成负数 → 切片下溢 panic（屎山报告 H2 记录，`docs/2026-10-06-全仓屎山扫描-总报告.md:1229-1236`）。该报告当时以「LGS 后端当前未接线」为由把等级降级——**现在 LGS 已接线，这是活的崩溃路径**。
另注：`readback.rs:118-121` 的文档仍写「64 帧 / 1 ms」，与 `limiter.rs:18` 的 256 帧 / 4 ms 不一致（文档漂移见 REF-LGS-017）。

## 实现步骤
1. 复现：把 LGS 缓冲区设为 64 或 128 帧，播放任意素材，确认 panic（附 backtrace）
2. 二选一（实现前先在 issue 里定口径）：
   - **A. 钳制配置**：`SynthConfig::validate()` 增加「`block_size ≥ LOOKAHEAD×2`」或「`block_size ≥ 256`」的硬校验，设置页同步收紧可选值；错误信息指明最小值
   - **B. 修复内核**：让 limiter 的延迟线支持 `block < LOOKAHEAD`（`limiter.rs:54-61` 已有通用延迟线推进的历史修复，确认是否覆盖全部路径）
3. 若选 A，必须同时改设置页可选值 + 校验 + 配置迁移（已存 64/128 的用户配置要有明确处理，不得静默改值）
4. 补单测：`block_size` 取 {64,128,256,257,512} 各跑一次渲染不 panic

## 设计说明

| 项目 | 说明 |
|---|---|
| 修复取向 | 优先让配置层拒绝非法组合（明确报错优于内核兜底），内核侧保留防御 |
| 兼容性 | 已保存的 64/128 配置：加载时钳到合法值并给出可见提示（不静默） |
| 排除项 | 不改 limiter 的 0.5 ms attack / 80 ms release / 0.98 阈值语义 |

## 关联问题
- 关联 **#143（AUD-002，open：导出格式能力矩阵）** 与 **#144（AUD-003，open：采样率解耦）**：同属「配置合法值」体系，口径需一致
- 关联 **REF-LGS-009**：若离线默认块长上调，块长取值范围会再次变动——本卡应先把下界钉死

## 验收标准

- [ ] 设置页不再提供会导致崩溃的取值；非法配置加载时有可见提示且不静默改写

## REF-LGS-016：`flush_epoch` 无递增点——过载重同步清队列机制的裁决

> **类型**：Bug ｜ **优先级**：Low ｜ **工作量**：Low

## 现状
`docs/2026-10-11-REND-017-GPU缓冲状态指示器-实施记录.md:105-107` 记录：`src/audio/playback/start.rs` 的「过载重同步清队列」机制在 `7bb878b9`（REND-016 改为「宁糊不切」的降级保护）之后，**`flush_epoch` 没有任何递增点**——该路径永不触发。代码里仍留着「发现 epoch 变化就丢弃已渲染旧音频」的回调分支（`start.rs:413-419`、`:56-58`），而 `docs/2026-10-09-REND-016-...:78-80` 的现场证据曾把它当作防断声手段之一。
后果：一段**永不执行的代码**留在音频关键路径上，且文档把它当作有效机制描述——后续排障会误判。

## 实现步骤
1. 全仓确认 `flush_epoch` 的读写点（`AtomicU64`/等价物）：grep 定义、递增点、消费点，给出结论
2. 裁决并落地其中一条：
   - **A. 删除**：移除未触发的分支与字段，并在 REND-016/017 文档中改写为「已废弃」
   - **B. 恢复触发**：明确触发条件（何种过载/证据阈值）后重新接上递增点，并补验收场景
3. 无论选哪条，都要在 `docs/2026-10-09-REND-016-LGS实时防爆-实施记录.md` / `2026-10-11-REND-017-...md` 上标注裁决结果（保持历史记录可追溯）

## 设计说明

| 项目 | 说明 |
|---|---|
| 修复取向 | 未定，需与 REND-016 owner 裁决（卡内先给结论表，不擅自选） |
| 兼容性 | 选 A 时不得改变任何可观察行为（该分支本就不触发） |
| 排除项 | 不动 Governnor 四级阈值与丢弃策略 |

- 若选 B，需重新走一遍 REND-016 的三场景验收（穿爆点 / 直接播 / 播放中跳转）

## REF-LGS-018：`lumino-gpu-synth` 继承工作区 lint（unwrap/expect 白名单化）

> **类型**：Task ｜ **优先级**：Low ｜ **工作量**：Low

## 现状
`crates/audio/gpu-synth/Cargo.toml` **刻意不继承**工作区 lint（无 `[lints] workspace = true`），注释说明是「作为 vendored 子 crate 原样搬入」；仓库的 `AGENTS.md` 对 `unwrap_used` 有强约束，该 crate 因此长期处于规则之外。实测残留：`admission.rs:103,137`、`offline.rs` 等多处 `unwrap_or_else(|e| e.into_inner())` / `expect`。
风险：随着 LGS 成为现役后端（REND-016/AUD-004/AUD-008 系列已接线），该 crate 的代码质量与其承载职责不再匹配。

## 实现步骤
1. 在 `Cargo.toml` 加 `[lints] workspace = true`，先跑一遍 `cargo clippy -p lumino-gpu-synth --all-targets` 收集全部新增告警
2. 分类处理：**必须修**（真实可 panic 的生产路径）与**合理保留**（锁中毒恢复 `into_inner`、初始化期 `expect`、测试代码）
3. 保留项用文件级/行级 `#[allow(...)]` + 一行理由注明；不得用 crate 级 blanket allow
4. 在 `AGENTS.md` 或该 crate README 记录「本 crate 的白名单项与理由」

## 设计说明

| 项目 | 说明 |
|---|---|
| 修复取向 | 先对齐规则，再逐个定性；不追求一次性清零 |
| 兼容性 | 纯 lint/注释层，无行为变化（除必要错误处理改写外） |
| 排除项 | 不在本卡顺手做 REF-LGS-001..022 的重构 |

## 关联问题
- 关联 **AUD-008（#163，open）**：LGS 重建 worker 的 panic 路径蒸发 MidiApi——属同一类「错误处理不严谨」问题
- 关联 **DOCS-001（#22）** 的 crate 清单口径

## 验收标准
