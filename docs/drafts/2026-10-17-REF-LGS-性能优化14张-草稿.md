## REF-LGS-001：mix.wgsl 并行度重构——gather 分块归约

> **类型**：Task ｜ **优先级**：High ｜ **工作量**：High

## 现状
`mix.wgsl` 是 **gather** 结构：1 个线程负责 1 个输出帧，循环**全部**声部。grid 只有 `(⌈block/128⌉, 1, 1)` 个 workgroup——block 512 时**只有 4 个 workgroup / 512 线程**，在 RTX 2060（30 SM）上占用率约 1%；实测该 pass 是 `collect` 阶段的主成本，`sustained65536` 场景每块 GPU 时间 24.0 ms（预算 10.67 ms）。

> 度量口径（本卡统一）：`LUMINO_PROFILE=1 cargo run --release -p lumino-gpu-synth --example profile_gpu -- <midi> <sf2> <frames> <block>`；夹具 `sustained65536.mid` + `rich.sf2`（kestrel `gen-assets` 生成，可重建）；48 kHz。
> RTX 2060 基线：`sustained65536` 峰值 ~29.4k 声部、block 512 = 18.49 s（**0.541× 实时**）；block 4096 = 7.18 s（1.39×）。

## 诊断步骤
1. 复现基线：`profile_gpu sustained65536.mid rich.sf2 480000 512`，记录 `倍实时` 与 `collect/total` 分相
2. 固定声部数复测（先跑 `sustained2048.mid`）区分「固定开销」与「声部数相关」成本
3. 用 `block 512/1024/2048/4096` 四点确认 mix 并行度对块长的依赖（基线：0.541/0.89/1.24/1.39×）
4. 在 PR 描述中给出改动前后同一命令的墙钟与分相对照

## 实现步骤
1. 把「1 线程 = 1 帧 × 全部声部」改为「1 线程 = 1 帧 × 1/CHUNKS 声部」：`mix.wgsl` 增加 `CHUNKS` 维（`@builtin(global_invocation_id).y`），线程只累加 `v ∈ [chunk*ceil(voices/CHUNKS), (chunk+1)*…)`
2. `dispatch.rs` 的 mix dispatch grid 改为 `(⌈block/128⌉, CHUNKS, 1)`（`src/synth/engine/dispatch.rs:207-215`）
3. 新增 `mix_partial` 缓冲：`[chunk][frame][channel]`（`f32`，尺寸 `CHUNKS × block × channels`），mix pass 写部分和；新增一个极小的 `mix_reduce` pass（grid `(⌈block/128⌉,1,1)`）按固定顺序（chunk 0→CHUNKS-1）相加写回 `output`
4. `CHUNKS` 走常量注入（与 `RENDER_SEGMENTS` 同一套字符串替换机制，见 `src/gpu/pipelines.rs:25-33`），初值 8–16，实测后定档
5. 逐通道 CC 状态机（`cur/frames`）与 pan 三角函数求值目前每线程重算一次——本期保持**语义不变**（每个 chunk 线程仍从块首重放事件），只改声部维拆分；`cur` 的重算成本在 REF-LGS-004 单独处理
6. **范围决策**：本期**保留** `voice_out`（渲染写、mix 读）；删掉它是 REF-LGS-002 的范围，本卡不得顺手改

## 优化方向

| 场景 | 诊断重点 | 可能原因 |
|---|---|---|
| mix 占比高且随 block 变小而恶化 | 并行 workgroup 数 = block/128 | gather 结构把并行度锁在「输出帧数」上 |
| 声部数上升时 mix 线性变慢 | 每线程循环全部声部 | 缺声部维拆分与部分和归约 |
| 块长 4096 时反而变快 | 固定开销被摊薄 | 提交/回读/事件重放的每块成本 |

## 设计说明

| 项目 | 说明 |
|---|---|
| 复用策略 | 归约形状照 kestrel 的 `partials[frame][wg]` 思路；不引入原子（保持既有「与同步版逐位一致」的口径），部分和按固定顺序相加 |
| 兼容性 | `CHUNKS=1` 时必须退化为当前行为；`block`、`channels`、事件语义一概不变 |
| 隔离性 | 只动 mix 链路（`mix.wgsl` + `dispatch.rs` + `pipelines.rs` + 缓冲），不碰 render/抢占/Governor |
| 实现复杂度 | 中：新增一个 pass 与一个缓冲，shader 改动集中在一处循环边界 |

## 性能目标
- `sustained65536` / block 512 / 峰值 ~29.4k 声部：**0.541× → ≥1.2× 实时**
- mix pass 占 `collect` 的比例降到 <20%（分相可测）
- `sustained2048` 场景不退化（当前 10.03×，允许 ±3%）

## 关联问题
- 本卡是 **REF-LGS-002（消除 voice_out）** 的前置：REF-LGS-002 在 render pass 内归约，届时本卡的 `mix_partial` 形状可直接复用
- 与 **#116（REND-008B，open）** 不重叠：#116 削减的是每块上传/回读固定成本，本卡改的是 mix 计算并行度
- 与 **REF-LGS-013（基准护栏）**：建议 REF-LGS-013 先落地，本卡验收直接用其指标
- 精度红线：`STATES_SYNC_EVERY=1`、`render.wgsl` 的 `prog clamp`、`GrowableBuffer` 清零等既有防御不得改动（历史爆音/NaN 教训见 `fix-realtime-clipping-high-polyphony.md`）

## 验收标准
- [ ] `profile_gpu sustained65536.mid rich.sf2 480000 512` 倍实时 ≥1.2×（改动前 0.541×），PR 附前后对照
- [ ] 音频与改动前**逐位一致**（同块长、同配置、同素材）；不一致时给出差异幅度与结论
- [ ] `CHUNKS=1` 时行为与改动前一致（可回归开关）
- [ ] `cargo test -p lumino-gpu-synth` 全绿；实时场景（≥2k 声部）无新增 underrun
- [ ] 显存增量等于 `CHUNKS × block × channels × 4 B`（在 PR 中报数）
- [ ] cargo fmt / clippy 通过

## REF-LGS-002：消除 voice_out——渲染 pass 内按通道 workgroup 归约

> **类型**：Task ｜ **优先级**：Medium ｜ **工作量**：High

## 现状
render pass 把每个声部整块的立体声采样写进 `voice_out`（`src/gpu/shaders/render.wgsl:396-398`，每声部每帧 8 B = block 512 时 **4 KB/声部**），mix pass 再整块读一遍（`mix.wgsl:112-122`）——同一条音频数据**写一遍读一遍**，且 `voice_out` 是全池尺寸的显存占用（`init.rs:84-91`，`dispatch.rs:74-78` 按历史峰值只增不减）。kestrel 用「渲染 pass 内 workgroup 归约 + partials」完全避免这层落地。

> 度量口径：同上（`profile_gpu` + `LUMINO_PROFILE`）。
> 基线：`sustained65536` / block 512 = 0.541×；block 4096 = 1.39×（此时 mix 变便宜，`voice_out` 的读写流量仍在）。

## 诊断步骤
1. 先落地 REF-LGS-001 并记录其基线（本卡的对照起点）
2. 量化 `voice_out` 流量：`16 B × voices × block` 每块写入+读出，以及 `voice_out_buf` 的显存峰值（`dispatch.rs:74-78` 的 `ensure` 逻辑）
3. 复测 `sustained2048`（~930 声部）与 `sustained65536`（~29.4k 声部）两档，确认收益随声部数放大

## 实现步骤
1. render pass 每个 workgroup 处理 128 个声部 × `SEGS` 段：段内先把「本 WG 覆盖的帧区间 × 通道」的部分和写入 workgroup shared（`var<workgroup>`，形状 `[frames_in_seg][channels]`），每段末按通道累加进 `voice_partials[wg][frame][channel]`
2. `voice_chans`（通道/released 位）改为在 render pass 内按声部读入寄存器（现在 mix 读它，`mix.wgsl:113`）
3. mix pass 退化为「每帧累加 `voice_partials[*][frame][ch]`」——只剩 `⌈block/128⌉ × channels` 级联，事件状态机与 pan/amp 保留（`mix.wgsl:134-182`）
4. 删除 `voice_out_buf`（`init.rs:84-91`、`dispatch.rs:74-78`、`dispatch.rs:194-215` 的绑定与 ensure）；`gpu.rs:47-55` 的 binding 索引表随之调整
5. 若 shared 容量不足（`max_workgroup_storage`，本机 Vulkan 49152 B / DX12 32768 B，见 `gpu/context.rs`），按 `channels` 切分多次 barrier 或把段长降到 `SEG_LEN/2`
6. **明确不做**：不引入原子、不改 `SEGS`（`gpu.rs:37` 的 `RENDER_SEGMENTS`）语义；filtered 声部的单段退化行为保持不变

## 优化方向

| 场景 | 诊断重点 | 可能原因 |
|---|---|---|
| 高复音时 GPU 时间随声部线性上升 | `voice_out` 读写带宽 | 中间音频落地两次 |
| 高复音时显存吃紧 | `voice_out_buf` 只增不减 | 按历史峰值 ensure（`dispatch.rs:74-78`） |
| block 越大越省 | mix 每线程循环声部数不变 | 见 REF-LGS-001，本卡进一步移除该循环 |

## 设计说明

| 项目 | 说明 |
|---|---|
| 复用策略 | 归约形状对齐 kestrel `reduce_into_partials`（workgroup storage 两级归约），但**不引入**其五种 pass 的其余部分 |
| 兼容性 | 音频逐位一致优先；`voice_chans` 的 `channel | released<<8` 位打包必须原样保留（`pool.rs:126-132`、`mix.wgsl:113-115`） |
| 隔离性 | 只动 render→mix 的数据通路；抢占/Governor/Governor 统计不受影响 |
| 实现复杂度 | 高：shader 与绑定组同时改，需要分步验证（建议先只做「部分和缓冲」再删 `voice_out`） |

## 性能目标
- `sustained65536` / block 4096：**1.39× → ≥1.8×**
- `voice_out` 相关显存归零（`block × voices × 8 B` 全部省下，29.4k 声部 @512 = 120 MB → 0）
- mix pass 不再含 per-voice 循环（grep 可证：`mix.wgsl` 内无 `mix_params.voice_count` 循环）

## 关联问题
- **依赖 REF-LGS-001**：先落地分块归约，再谈删除中间缓冲
- 与 **#87（REND-002-GPU 多端口）**：`voice_chans` 的通道语义（`port*16+ch ≤ 255`）必须保持，本卡不得改变通道空间
- 显存记账：`docs/2026-10-17-数据源冗余审计.md` 指出 `GpuBufferStats` 无显存字段，本卡的显存收益需要手工报数（或随 REF-LGS-013 补埋点）

## 验收标准
- [ ] `sustained65536` / block 4096 倍实时 ≥1.8×（对照 REF-LGS-001 落地后的实测值）
- [ ] 音频逐位一致；`voice_out` 相关缓冲从 `gpu.rs` binding 表与 `init.rs` 中彻底移除（grep 无残留）
- [ ] 显存峰值下降 = `block × 峰值声部 × 8 B`（报数）
- [ ] 多端口素材（`port*16+ch`）与单端口素材音频均无回归
- [ ] `cargo test -p lumino-gpu-synth` 全绿；实时播放 2k/8k 声部无新增 underrun
- [ ] cargo fmt / clippy 通过

## REF-LGS-003：mix.wgsl 私有内存与冗余累加器收窄（低风险快赢）

> **类型**：Task ｜ **优先级**：Medium ｜ **工作量**：Low

## 现状
`mix.wgsl` 每线程静态分配约 **17.4 KiB** 私有内存：`acc_l/acc_r/acc_rel_l/acc_rel_r`（4×256×4 B = 4 KiB）+ `cur: array<MixStart,256>`（12 KiB）+ `frames: array<u32,256>`（1 KiB）（`mix.wgsl:100-103,127-128`）。其中两处是**可直接消除的浪费**：
1. `acc_rel_l/acc_rel_r` 与 `acc_l/acc_r` 在 `mix.wgsl:180-181` 被**相加后乘同一个 amp** —— released 分组在最终结果里没有语义差异，却多付 2 个数组 + 每声部 2 次加；
2. `MAX_CHANNELS = 256`（`mix.wgsl:56`）是全局通道空间上限，而 `channel_count` 默认只有 16（单端口）——数组按 256 无条件分配。
GPU 私有内存溢出到 local memory 会走 L1/L2，是 mix 的隐性成本之一。

> 度量口径：同上。基线：`sustained65536` block 512 = 0.541×；`sustained2048`（~930 声部）= 10.03×。

## 诊断步骤
1. 用 `sustained65536` / block 512 记录基线（`total`、`collect`、倍实时）
2. 在改动前后各跑一次 `sustained2048`，确认低复音场景不被拖慢

## 实现步骤
1. 删除 `acc_rel_l/acc_rel_r`：released 与未 released 的贡献合并进 `acc_l/acc_r`（`mix.wgsl:111-123`），末段 `out_l/out_r` 的表达式同步简化（`:180-181`）——**语义等价性需在 PR 中用对拍证明**
2. 把 `cur`/`frames` 从「按 `MAX_CHANNELS` 静态数组」改为按 `channel_count` 上界使用：若 WGSL 不允许动态数组，则改用两个小缓冲（`mix_states` / `mix_frames`）承载逐通道状态机，线程只读写 `channel_count` 项
3. 顺带移除 `mix.wgsl:165-168` 的 `if (ch >= MAX_CHANNELS) { break; }` 死守卫（循环上界已是 `channel_count`）
4. **明确不做**：不改事件重放语义（REF-LGS-004 的范围）、不改 pan 三角函数与 lerp 行为

## 优化方向

| 场景 | 诊断重点 | 可能原因 |
|---|---|---|
| 任意复音下 mix 都有固定成本 | 每线程私有内存 | 4 个 256 项数组静态分配 |
| 通道数少的工程收益更明显 | `channel_count` 与数组上界脱钩 | `MAX_CHANNELS` 无条件分配 |
| released 分组 | 结果表达式 | 两组累加后同乘一个 amp（无语义差异） |

## 设计说明

| 项目 | 说明 |
|---|---|
| 复用策略 | 无需新抽象；只做数组收缩与冗余项删除 |
| 兼容性 | **必须逐位一致**；released 分支合并的理论等价性要在 PR 里给出推导 |
| 隔离性 | 单文件 shader 改动（可能 +1 个小绑定） |

## REF-LGS-004：mix 事件重放复杂度削减（O(block × events) → 增量）

> **类型**：Task ｜ **优先级**：Low ｜ **工作量**：Medium

## 现状
mix 的每个输出帧线程都要**从 `i = 0` 重扫本块事件表**，直到 `mix_events[i].frame > f`（`mix.wgsl:134-158`）：最坏复杂度 `O(block × event_count)`，且 `c >= channel_count` 的事件用 `continue` 跳过但仍计入扫描（`:138-141`）。黑乐谱单块事件可达 4,096 条（`drain.rs:22` 的 `MAX_EVENTS_PER_BLOCK`），block 512 时即 512 × 4,096 ≈ **209 万次事件比较/块**。

> 度量口径：同上。基线：`sustained65536` block 512 = 0.541×（该素材事件少，本卡收益需用**高事件密度**素材另测：真实黑乐谱密集段 30 s）。

## 诊断步骤
1. 构造/选取高 NPS 素材（真实黑乐谱密集段 30 s），记录 `total` 与 event_count
2. 对比 `sustained65536`（低事件）与密集段（高事件）两档，确认 mix 时间与 `event_count` 的相关性
3. 在 PR 中给出「每块事件数 × 块长」与 mix 耗时的对照表

## 实现步骤
1. 方向 A（推荐，改动最小）：把「每帧重扫」改为**逐帧增量**——`mix.wgsl` 的帧循环改为串行推进一个事件游标（chunk 拆分由 REF-LGS-001 负责，本卡保证每 chunk 从块首游标推进）
2. 方向 B（更彻底）：把逐通道 lerp 状态机**预先展开**成「每帧的 channel 增益表」（`block × channels` 的 `f32`），由一个独立小 pass 生成；mix 帧线程只做查表与乘加
3. 顺带把 `c >= channel_count` 的事件在**生成端**过滤（`bind.rs`/`channel.rs` 侧），不再进 `mix_events` 缓冲
4. 保持「事件按帧精确生效、从块首状态重放」的既有语义（`mix.wgsl:1-18` 的口径），不得改成近似平滑

## 优化方向

| 场景 | 诊断重点 | 可能原因 |

| 密集段 mix 时间异常 | 事件条数 × 帧数 | 每帧从 i=0 重扫 |

## 性能目标

- `sustained65536`（低事件）不退化

## REF-LGS-005：渲染段状态重放消除——段起点闭式计算

> **类型**：Task ｜ **优先级**：High ｜ **工作量**：Medium

## 现状
render 用 2D 派发换并行度：`grid = (⌈voices/128⌉, RENDER_SEGMENTS=4, 1)`，每个 segment 先**逐帧重放** `advance_frame` 把自己快进到段起点（`src/gpu/shaders/render.wgsl:325-336`）。block 512 / `SEG_LEN = 128` 时，每声部每块实际推进次数 = 512（实渲）+ `128×(0+1+2+3)` = **768 次重放**，即 **+150% 的状态推进**（`:322-324` 注释自述"no sample reads"）。每次重放还含一次 `env_stages[p.env_base + stage_idx]` 的 12 B storage 读（`:219`）与一次 `f32(s.env_t)/f32(denom)` 除法（`:227`）。

> 度量口径：同上。基线：`sustained65536` block 512 = 0.541×（GPU `collect` 24.0 ms/块）；block 4096 = 1.39×。

## 诊断步骤
1. 记录 `sustained65536` / block 512 与 4096 的 `collect` 分相作为对照
2. 估算重放占比：把 `SEGS` 由 4 改 1（仅本地实验，不入库）对比 `collect`，得到段机制的净成本上界
3. PR 中给出 `SEGS=1/2/4` 三点对照

## 实现步骤
1. 位置推进是**仿射**的（`speed` 每块恒定，`render.wgsl:254-262`）：段起点位置可直接闭式求出 `pos(seg_start) = pos(0) + seg_start × speed`（定点 32.32 加法，注意 `frac` 进位只依赖总量）
2. 包络是**分段闭式**的（`env_stages` 的 `kind/duration/target`，`:212-236`）：段起点状态按 stage 逐个跨越（通常 4–7 段），无需逐帧
3. `release_at` / `start_at` / `ended` 三个门限同样可以 O(1) 判定段起点是否已进入 release/结束（`:200-210, :240-251`）
4. 实现为 `fn advance_to(p, st, frame_offset) -> VoiceState`，替换 `render.wgsl:325-336` 的逐帧循环；保留原 `advance_frame` 供逐帧渲染使用，两者必须由**同一套 stage 语义常量**驱动
5. 补 kernel 级测试：对随机包络/循环/release 组合，断言 `advance_to(k)` 与连续调用 `advance_frame` k 次的状态**逐位相同**
6. **明确不做**：不改变 `SEGS`/`SEG_LEN` 的划分与 filtered 声部的单段退化（`render.wgsl:291-306`）

## 优化方向

| 场景 | 诊断重点 | 可能原因 |
|---|---|---|
| render 时间随 SEGS 上升 | 段起点快进成本 | 逐帧重放（+150%） |
| 每帧一次 storage 读 | `env_stages` 访问 | 阶段表在 storage buffer |
| 高复音时 render 主导 | workgroup 内状态推进 | 段数 × 帧数的冗余 |

## 设计说明

| 项目 | 说明 |
|---|---|
| 复用策略 | 不改数据结构，只把「重放」换成「闭式跳跃」；`VoiceState` 布局（`layout.rs:51-71`）不变 |
| 兼容性 | 逐位一致是硬要求——闭式与重放必须给出等价性测试（步骤 5） |
| 隔离性 | 只动 `render.wgsl` 的段快进与新增 helper |
| 实现复杂度 | 中：数学不复杂，但等价性测试是主要工作量 |

## 性能目标
- 每声部每块的 `advance_frame` 调用数从 **1280 → ~512**（或段边界 3 次闭式跳跃）
- `sustained65536` block 512：**0.541× → ≥0.75×**；block 4096 ≥1.6×

## 关联问题
- `env_stages` 每帧读（`:219`）与除法（`:227`）属 **REF-LGS-006** 范围；本卡只处理"重放次数"
- filtered 声部不能快进（信号相关 biquad）：`render.wgsl:288` 在 seg>0 仍先读 68 B `states[voice]` 再 return——顺手修掉这处白读（同卡内，属同一段代码）

## REF-LGS-006：render 每帧热路径去 storage 读与除法

> **类型**：Task ｜ **优先级**：Medium ｜ **工作量**：Low

## 现状
最内层帧循环里有两项可预算化的成本：
1. `env_stages[p.env_base + stage_idx]` —— **每帧**一次 12 B storage 读（`src/gpu/shaders/render.wgsl:219`），而阶段切换只在少数帧发生；

1. 记录 `sustained65536` block 512 基线
2. 用「把 `env_stages` 读提到段首」的实验分支对比 `collect`，量化每帧 storage 读的成本

## 实现步骤
1. 在 `advance_frame` 之外维护「当前阶段缓存」：`cur_kind` / `cur_target` / `cur_inv_duration`，仅在 `env_stage` 递增时刷新（`:230-234`）
2. 帧循环内用 `ev = env_eval_cached(...)` 取代每帧的表读与除法
3. 段快进的循环（若 REF-LGS-005 已落地则改为闭式）同样使用该缓存
4. 保留 `max(es.duration, 1)` 的零除守卫语义（换算成 `inv_duration` 时对 0 取 1）

## 优化方向

| 场景 | 诊断重点 | 可能原因 |
|---|---|---|
| 每帧一次 storage 读 | `env_stages` 访问模式 | 阶段表未缓存 |
| 每帧一次 f32 除法 | `prog` 计算 | 除数可预算倒数 |

| 隔离性 | 单文件 shader |
| 实现复杂度 | 低 |

## 性能目标

## REF-LGS-013：LGS 性能护栏与基准（倍实时 / 分相 / 声部帧率进 CI）

> **类型**：Task ｜ **优先级**：High ｜ **工作量**：Medium

## 现状
LGS **没有任何自动化性能基准**：唯一的证据散落在 `.ai-context/sessions/` 与 `docs/` 的历史记录里，且已出现**文档与代码不一致**（admission NPS 阈值文档写 32k/8k 与 128k/64k 两说，代码是 64k/32k；声部上限文档 65536/32768、代码 16384/8192）。同时 `GpuBufferStats` 只有队列/负载/声部/欠载，**没有采样显存与 CPU 采样缓存字节**（`docs/2026-10-17-数据源冗余审计.md:255-257`）。后果：性能回归无法在 CI 发现，本次对比也依赖外部工程（kestrel）的基准工具才拿到数字。

> 度量口径：本卡就是**定义**口径的卡。基线（RTX 2060，48 kHz）：`sustained65536` block 512 = 0.541×、block 4096 = 1.39×；`sustained2048` = 10.03×；真实黑乐谱 100 s = 3.67×；纯 GPU 0.83 ns/声部/帧。

## 诊断步骤
1. 盘点现有可用测量入口：`examples/profile_gpu.rs`（离线）、`LUMINO_PROFILE=1`（分相）、`PlaybackStatsReader`/`GpuBufferStats`（实时）
2. 确认夹具来源与许可证（kestrel `gen-assets` 产物 + 自有素材）
3. 在 PR 中列出当前基线与测量方法，作为后续所有优化卡的对照基准

## 实现步骤
1. 落地 `cargo bench`（或 `--example bench_lgs`）三档夹具：`sustained2048`、`sustained65536`、真实黑乐谱 30 s 切片；输出四项指标：**倍实时 / 每块分相 / 峰值声部 / 声部帧率（voice-frames/s）**
2. 夹具入库：`sustained2048.mid`（16 KB）、`sustained65536.mid`（524 KB）、`rich.sf2`（30 KB）；真实素材与大音源只记录路径与哈希，不入库
3. 把「改动前后对比表」写成 PR 模板要求（无对照表的性能 PR 不合并）
4. `GpuBufferStats` 增补：采样显存（GPU chunk 字节）与 CPU 采样缓存字节；UI 指示器（REND-017 #140 已落地）随之显示
5. CI：先做「手动触发 + 结果归档」（GPU 机器不稳定），稳定后再考虑阈值门禁（回归 >10% 报警）

## 优化方向

| 场景 | 诊断重点 | 可能原因 |
|---|---|---|
| 回归无法发现 | 无自动化基准 | 缺夹具与指标口径 |
| 优化无法验收 | 分相不可见 | 只有 `LUMINO_PROFILE` 的粗粒度 |
| 显存回归不可见 | `GpuBufferStats` 字段缺失 | 未统计采样显存 |

## REF-LGS-014：SF2 采样数据双份驻留——统一为单一权威源

> **类型**：Task ｜ **优先级**：Low ｜ **工作量**：Medium

## 现状
`docs/2026-10-17-数据源冗余审计.md:255-257,341`：LGS 后端持有一份 `SoundFont` 的同时执行音频导出时，**进程内出现两份同 SF2 的完整采样数据**（再叠加 GPU chunk）；`gpu-synth/src/soundfont/load.rs:26-27` 无任何缓存，`load_soundfont` 每次重解析。对 30–300 MB 级音源意味着数百 MB 的冗余内存/显存压力，且端口布局重建（`set_midi_port_layout`）会再次全量重建 `GpuSynth`（文档记「重建期间 ~100–200 ms 断音」，`docs/2026-10-04-REND-002-实时多端口-行动方案.md:91,102`）。

> 度量口径：进程内采样字节（`GpuBufferStats` 补字段后可直接读，见 REF-LGS-013）；端口重建耗时用现有日志/打点。

## 诊断步骤
1. 复现双份：LGS 播放 + 同时导出，测量进程 RSS 与 GPU 采样 chunk 字节
2. 确认端口布局重建时的重复解析路径（`api/lgs.rs:277-304` 的 Rebuild 分支）
3. 在 PR 中给出「一份 vs 两份」的实测字节数

## 实现步骤
1. `load_soundfont` 路径引入**按 (路径, mtime, size) 键的缓存**（`OnceLock`/`Mutex<HashMap>` 或 `Arc<SoundFont>` 共享），避免重复解析与多份驻留
2. 导出与实时共享同一份采样数据（若跨进程/跨 device 受限，至少做到**同进程内单份**并在文档写明边界）
3. 端口布局重建：评估复用已解析样本 + 只重建声部/通道映射，或把重建移到后台线程并给出进度（**范围决策**：本期至少不重复解析样本；完整热重建可另开卡）
4. **明确不做**：不改 `SoundFont` 的数据结构与磁盘格式

## 优化方向

| 场景 | 诊断重点 | 可能原因 |
|---|---|---|
| 内存峰值高 | 采样数据份数 | 无缓存，重复解析 |
| 端口重建卡顿 | 全量重建 GpuSynth | 重建含样本重解析 |
| 导出与播放并存 | 进程内冗余 | 两条路径各自加载 |

## 设计说明

| 项目 | 说明 |
|---|---|
| 复用策略 | 缓存 + `Arc` 共享；不引入新的音源格式或抽象 |
| 兼容性 | 音频逐位一致；缓存键必须含 mtime/size，源文件变更后不得命中旧缓存 |
| 隔离性 | 只动音源加载与重建路径 |
| 实现复杂度 | 中 |

## 性能目标
- 同进程内同 SF2 采样数据 **只有一份**（实测字节数减半）
- 端口布局重建不再重复解析样本：重建耗时下降 ≥50%（从 ~100–200 ms 量级降下来）

## 关联问题
- 与 **REF-LGS-013** 的显存统计字段配套（否则收益不可观测）
- 关联 **#87（REND-002-GPU，已关闭）** 的端口空间语义：重建路径不得改变 `port*16+ch` 映射
- 关联 **AUD-008（#163，open：LGS 重建 worker 的 panic 路径）**：重建路径的正确性与本卡同域，注意不要互相覆盖改动
