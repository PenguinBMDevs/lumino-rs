## 2. 现状调用链（证据链）

```
GridWidget::update  (grid/program_impl.rs:58-110, 156-172)
   └─ EditorAction::Pressed/Moved/Released
        └─ Editor::handle_action (interaction.rs:27-105)
             ├─ handle_pressed  (interaction/pressed.rs:15-25 → 68)          Tool::Brush
             │    └─ handle_brush_pressed (brush.rs:18-31)
             │         ├─ 命中音符 → start_note_edit（铅笔同源）
             │         └─ start_brush_stroke (brush.rs:34-44)
             │              ├─ push_history()            ← document 历史：首格
             │              └─ insert_brush_block        ← 立即写 document（首格）
             ├─ handle_moved    (interaction/moved.rs:14-18)  ← brush_last_cell.is_some() 提前分流
             │    └─ handle_brush_moved (brush.rs:47-60) → insert_brush_block（仅当前格）
             └─ handle_released (interaction/released.rs:71-75)
                  └─ finish_brush_stroke (brush.rs:118-123)
```

写入函数 `insert_brush_block`（`brush.rs:63-85`）：

- 长度 = `view.snap_precision`（一个网格单元），力度/通道 = `DEFAULT_NOTE_VELOCITY` / `DEFAULT_MIDI_CHANNEL`；
- `level` 从 0 起向上：`key + level`（>255 截断），音轨 = `BrushConfig.tracks[level]`，未配置则从当前轨起沿普通轨（排除 0）序行走（`brush.rs:92-115`）；
- 每格收尾：`mark_notes_changed()` + `mark_track_notes_changed_for(Some(affected))`。

## 3. 断墨根因（RCA）

| 层 | 事实 |
|---|---|
| 现象 | 快速拖动（一帧跨多格）时，预览/生成的音符出现空洞 |
| 直接原因 | `handle_brush_moved` 以「格」为单位落笔，且只落**当前采样格**（`brush.rs:52-59`），两采样点之间没有任何几何处理 |
| 机制原因 | 采样是**事件驱动**（`CursorMoved`），而落笔是**点驱动**（单格盖戳）；点集 ⊊ 线段覆盖集，采样频率一降就丢格 |
| 设计原因 | 落笔函数签名 `insert_brush_block(tick, key)` 只接受单点，没有"线段→格集合"的抽象，插值无处安放 |
| 根因 | **覆盖语义缺失**：正确语义是"笔画的几何覆盖集"（中心线线段 ⊕ 粗细度），实现却写成"采样点集合" |
| 修复 | 预览与生成共用同一个覆盖函数：相邻采样点做**格空间连贯线段栅格化**（DDA），输出格集合后再按层展开（§6.2） |

> 该根因同时解释卡面"预览笔画与最终生成的音符都连续无洞"的要求——两者必须走**同一个覆盖函数**，否则拖快时预览连续、生成有洞（或反之），会出现"看起来对、生成错"的隐性 bug。

## 4. 目标架构：两阶段交互

### 4.1 状态机

```
Idle ──press(空白, 非 Conductor)──▶ Drawing   （只记录折线点，不写 document）
Idle ──press(笔画实心区)──────────▶ Dragging  （整条笔画平移预览）
Drawing ──move──▶ 追加采样点（预览实时重算）
Drawing ──release──▶ Pending（笔画进入待确认集合，√/× 出现）
Dragging ──release──▶ Pending
Pending ──√──▶ 批量生成音符（一次历史记录）─▶ Idle
Pending ──× / 切工具──▶ 丢弃 ─▶ Idle
```

与曲线工具一致的约束（`crates/editor/editor-state/src/editor_state/line_tool.rs:190-339`）：

- 多条笔画共存（`strokes: Vec<BrushStroke>`），空白处按下开始新笔画、**不清空**已有；
- 独立历史栈（`path_history` 范式：`push_path_history:288`、`update_top_path_history:295`、`undo_path:303`、`can_undo_path:327`）；
- `interaction != None` 才算"正在编辑"（`line_tool.rs:16-45` + `impls/editor_impl/commit.rs:21-39`），**待确认（Pending）不算编辑中**——否则 Ctrl+Z 会被 `undo()` 的 `is_editing()` 拦截（`impls/editor_impl/history.rs:30-33`）。

### 4.2 数据模型（建议）

```rust
// crates/editor/editor-state/src/editor_state/brush_tool.rs（新增，flat 文件 + 子目录 tests）
pub struct BrushStroke {
    pub points: Vec<(f32, f32)>,   // 逻辑坐标折线；tick 自由（raw），key 已吸附整数
}
pub enum BrushInteraction { None, Drawing { stroke: usize }, Dragging { stroke: usize } }
pub struct BrushToolState {
    pub strokes: Vec<BrushStroke>,
    pub interaction: BrushInteraction,
    pub drag_start_raw: (f32, f32),
    pub drag_orig: Vec<(f32, f32)>,
    pub path_history: Vec<Vec<BrushStroke>>,   // 与 LineToolState.path_history 同构
    pub path_history_index: usize,
}
```

- **点列只存几何**，粗细度/音轨在"预览"和"√ 确认"时按当时 `BrushConfig` 解释——与现状一致，且使"改粗细度后预览立即变化"成为自然行为（§7 决策 8）。
- 层与音轨解析沿用 `brush_track_for_level`（搬到 `Editor` 或 `editor_state` 层，保持语义）。

### 4.3 覆盖算法（断墨修复 + 生成共用）

```
cover_cells(points, snap) -> Vec<(i64 tick_cell, u16 key)>   // 去重后的格集合
  out = OrderedSet
  for (a, b) in points.windows(2):
      for cell in dda_cells(a, b, snap):     // 线段栅格化：按 Δtick_cell / Δkey 主步进
          out.insert(cell)
  out.insert(last_point_cell)                // 单点笔画兜底
```

关键点：

1. **复杂度 O(覆盖格数)**，与采样点数、采样频率无关——拖多快都连续，且没有"抽稀导致漏格"的风险；
2. 只在**生成/预览需要时**调用；相邻采样点重复格由集合去重（快速拖动时同格重复次数自然很高）；
3. 去重键用 `(tick_cell as i64, key)`，避免 f32 不能 Hash（与 `line_tool/confirm.rs:83-86` 同款做法）；
4. 层展开：`for level in 0..thickness { key + level }`，`>255` 截断（保留现状 `brush.rs:72-74`）；
5. `√` 生成：`tick = cell * snap`、`length = snap`（保留现状 `brush.rs:69`）。

### 4.4 生成时机与历史（一次撤销记录）

复用 `confirm_line_tool` 的成熟链路（`crates/editor/ui-editor/src/interaction/line_tool/confirm.rs:17-119`）：

```
√ → 遍历全部笔画 → cover_cells → 按 (track, 排序后) 分组
   → 逐音符 insert_note_with_id（当前轨自动记 NoteDeltaEvent）
   → CreateOp { track_id, note } 收集
   → history.push_note_create(create_ops)     ← 一条撤销记录（多轨合并在一组）
   → mark_current_track_changed / mark_track_notes_changed_for(全部受影响轨)
   → brush_tool.reset() + mark_notes_changed()
```

性能补充（大 K 时）：`insert_note_with_id` 每笔都会 `partition_point` + 推 `NoteDeltaEvent` + bump gen（`editor_state/.../accessors/write.rs:31-65`）。当 K 很大（如 5k 格 × 10 层 = 5 万音符）时，建议改走批量归并 `batch_insert_events_to_track_with_ids`（O(N+M) 单次 `extend_sorted`，`note_store_ops/insert.rs:67-85` + `audio/midi-model/src/document_edit.rs:58-79`），**但批量 API 只标记当前轨**（`insert.rs:54-57`），跨层多轨时必须显式补 `mark_track_notes_changed_for(Some(受影响轨集合))`，否则洋葱皮增量漏刷新。阈值建议做成常量，由 bench 标定（§9.4）。

### 4.5 渲染方案选型（结论：canvas 叠加层）

> ⚠️ **本节"圆头圆尾粗线条 + 聚合端帽"的方案已被 §15.2 取代**（任务提出者第二轮要求：
> 去掉圆头圆尾、改方形、所见即生成）。选型结论（canvas 叠加层）与"每帧几何成本必须有上界"
> 的原则仍然有效，几何形态改为**覆盖格方块**。阅读 §4.5 / §7 决策 2、3 / §14 第 1-3 项时请以 §15 为准。

选型对比：

| 方案 | 依据 | 结论 |
|---|---|---|
| **canvas 叠加层**（参照 `grid/line_tool_box.rs`） | 覆盖层已有完整范式：`program_impl/draw.rs` 挂层、`line_button_rects` 命中路由、`confirm_buttons::draw_button` 复用；圆头/圆角可用 `Stroke::with_line_cap(LineCap::Round)` / `with_line_join(LineJoin::Round)`（iced 0.14 已导出：`iced_widget/src/canvas.rs:58-59`、`iced_graphics/src/geometry/stroke.rs:41-48`） | ✅ 推荐 |
| GFX 实例化路径 | 走 GPU 需新建 renderer/管线/流式上传，且要在 UI 线程↔渲染线程间同步"拖动中每帧变化"的几何；收益仅在大批量常驻图元场景 | ❌ 本卡不必要 |

渲染要点：

1. **线宽 = thickness × zoom_y**（`ViewState::key_to_y` 使用 `zoom_y` 作为单 key 高度，`crates/core/core/src/view_state.rs:74,98-101`）→ 缩放/滚动时几何每帧按当前视图重算，天然跟随；
2. **端帽聚合**：整条笔画只画一对圆头/圆尾，半径 = 总宽/2，**不按层各画**。实现建议（按层硬切换颜色且帽唯一）：
   - 逐层构造"笔画带 ∩ 该层 key 带"的**填充多边形**（CPU：中心线两侧偏移 ±总宽/2 得带轮廓 → 用两条水平带边界做 Sutherland–Hodgman 裁剪 → 端部补半圆折线），逐层 `frame.fill`；
   - 简化版（可接受的降级）：逐层画 butt 端帽粗线 + 整笔一对端帽圆（首尾点、半径总宽/2）叠画，端帽内颜色取端部所在层的颜色。差异仅在端帽内部的层切换，视觉几乎不可辨。
3. **颜色**：层 L 的颜色 = 该层音轨的**音符显示色 × 0.6**（"加深 40%"，口径见 §7 决策 4）。取色单源 = `lumino_extras::palette::current_track_color_f32(doc_track)`（`palette/state.rs:22-44`），与卷帘音符实例色同源（`crates/editor/ui/src/host/render/onion_skin/stream.rs:70`、`shaders/note.wgsl:103-200` 的 per-instance `key_color`）→ 调色板变更后下一次重绘即变色，无需缓存失效（需确认重绘被触发，见 §7 决策 5）；
4. **硬切换**：层颜色按 key 边界切，不做渐变——用 §4.5.2 的带裁剪天然满足（裁剪线就是 key 边界）；
5. **抽稀/分块（性能硬约束）**：
   - 生成用的点列**不抽稀**（覆盖正确性不依赖采样密度）；
   - 预览用的点列做**视口裁剪 + 屏幕空间抽稀**（相邻点像素距离 < ~0.5px 时合并，共线点合并），并设上限（如 512 点/笔画，超出按等距抽稀）——保证单帧几何构建成本有上界，不随笔画长度线性劣化；
   - 拖拽中每帧都会变（追加点），不必上 `canvas::Cache`；**非拖拽帧**（Pending 静置）可用 `iced_widget::canvas::Cache` 缓存，仅在笔画/视图变化时失效（可选优化）。
6. **纵向卷帘**：几何用 `tick_key_to_pos_f32`（`ui-editor/src/coords.rs:94-111`）或 `line_pos_screen_pos`（`interaction/line_tool/hit_test.rs:147-158`），两者都已纵向转置；按钮命中路由需要在 `grid/vertical_program.rs:133-152` 补同款分支（见 §7 决策 1）。

### 4.6 交互细节

| 交互 | 规则 |
|---|---|
| 落笔 | key 取整吸附（`pos_to_key`，`coords.rs:65-74`）；tick 建议取 raw（覆盖计算时再落格），与曲线中间锚点自由定位同源（`line_tool.rs:57-60`） |
| 拖动中 | 追加点 + 预览重算；**零 document 写** |
| 松手 | 进入 Pending；多笔画共享**一对** √/×（位置 = 全部笔画屏幕包围盒右侧，钳制在 `content_bounds` 内，照抄 `line_tool_box.rs:47-110`） |
| √ | 全部笔画一次性应用（一次历史记录），清空笔画与笔画历史 |
| × | 全部丢弃 |
| 拖动笔画 | 命中"实心区"= 点到折线段的屏幕距离 ≤ 总宽/2（沿用 `hit_test` 的屏幕距离判定范式）；X 自由（raw dtick）、Y 整数 key（round），松手仍 Pending |
| 切工具 | 视为 ×（`EditorState::set_tool` 已有集中落点：`editor_state.rs:196-207`） |
| Conductor | 落笔拦截（对齐 `pressed.rs:53-57`）；√ 是否拦截见 §7 决策 10 |

## 5. 性能现状与目标模型

### 5.1 现状成本（每进入一个新格）

| 成本项 | 位置 | 说明 |
|---|---|---|
| ≤ thickness 次 `insert_note` | `brush.rs:71-80` | 每次 = `ChunkedList::insert`（O(块内) 内存搬移）+ `partition_point` + 推 `NoteDeltaEvent` + bump gen |
| `HashSet` 构造 + 每层 insert | `brush.rs:70-79` | 每格一次堆分配 |
| `mark_notes_changed()` | `brush.rs:81` | 置脏 + `max_note_len` 失效；命中/渲染路径会触发 `ensure_spatial_index`（`spatial.rs:101-120`，>200k 音符建树，>2M 跳过） |
| `mark_track_notes_changed_for` | `brush.rs:82-84` | 每格一次 |

即：**拖得越久，写库次数 = 经过格数 × 粗细度**，且中间逻辑（历史、事件、脏标记）全部跟着格数走。

### 5.2 目标

| 阶段 | 目标 | 保障手段 |
|---|---|---|
| 拖拽期间 | 单帧成本与"已画长度"**解耦**（仅与"本帧新增 + 抽稀后可见点数"相关） | 零 document 写；预览点抽稀 + 视口裁剪 + 点数上限 |
| √ 应用 | 一次遍历 + 一次归并写入 + 一次脏标记（不产生"每格一次全局标记"） | `cover_cells` O(覆盖格数)；批量归并路径；收尾只调一次 `mark_notes_changed` |
| 空间索引 | 拖拽期间绝不触发重建 | 拖拽期间不碰 `mark_notes_changed`（回到 §4.1 的 Pending 不置脏） |

> 口径说明：生成 K 个音符天然是 O(K)，卡面"生成不得随笔画长度线性劣化"应理解为**不得有额外的线性放大**（每格 HashSet、每格全局标记、每音符合并历史、每帧 O(全部点)）。本方案按此口径设计（§7 决策 3 附验收口径）。

## 9. 调研副产品（冰山）

### 9.1 既有问题（本卡顺手可修，建议 PR 说明中列出）

1. **`can_redo()` 漏了笔画/曲线路径重做**：`impls/editor_impl/history.rs:314` 只查 `data.history.can_redo()`，未查 `line_tool.can_redo_path()`（对照 `can_undo()` `:309`）。`redo()` 本身会先尝试 `redo_path()`（`:137-142`）——即"能重做但 UI 查询说不能"。当前全仓无 `can_redo()` 消费方（仅测试），影响面小，但加笔画历史时**必须一并补全**，否则同一处再欠一笔债。
2. **`LineToolConfirm` / `ShapeToolConfirm` 未列入高精度洋葱皮脏标记判定**：`crates/editor/ui/src/host/editor_ops/query.rs:113-126` 只列了 Delete/Cut/Paste 与 Pressed/Released/DoubleClicked/Undo/Redo → 曲线/形状 √ 生成的音符可能不刷新高精度贴图。新增 `BrushConfirm` 时应归入 definite mutation，并建议顺手补上曲线/形状（本卡范围外，可单列）。
3. **画刷在 Conductor 轨会写入他轨**：`brush.rs:92-115`（当前轨 = 0 → `pos_in_normal = 0` → 目标轨 1..N）。卡面已要求对齐曲线拦截，修复后该路径不可达。

### 9.2 死代码/一致性

## 10. 验证方案

### 10.1 单元测试（新增 `interaction/brush/tests*.rs`，用 `Editor::new()` + `tests::test_helpers`）

1. **断墨**：一次 `Pressed(0,60)` 后直接 `Moved` 到 `tick=10*snap`（跨 10 格）→ `√` → 断言 10 格全部有音符（逐格存在性检查，无空洞）。
2. **不写库**：`Drawing` 期间与 `Moved` 多次后，`document` 音符数恒为 0、`can_undo()` 为 false。
3. **一次撤销**：`√` 后 `push_note_create` 恰好 1 条（多轨合并），`undo()` 一次后全部音符消失、各轨恢复原状。
4. **多层多轨**：`thickness=3` + `set_track` 显式分配 → 断言三层分别落到指定轨、key 递增、`>255` 截断。
5. **颜色**：`darken(color, 0.6)` 单测；洋葱皮轨（非当前轨）取色 = `current_track_color_f32(track)`（含变轨后重算）。
6. **端帽聚合**：几何函数单测——帽数量 == 2（每笔画），半径 == `thickness*zoom_y/2`；层数变化不增加帽。
7. **拖动**：`Dragging` 平移 `(dtick=1.7 自由, dkey=+2)` → `√` 后音符位置 == 预览位置（同一函数换算，断言落格一致）。
8. **Conductor**：当前轨 = 0 时 `Pressed` 不产生笔画、不写 document；已有待确认笔画时 `×` 仍可丢弃。
9. **切工具 = ×**：`set_tool(Tool::Pencil)` 后笔画清空、历史清空。
10. **按钮**：多笔画只有一对 rect；包围盒越界时 rect 被钳制在内容区内（照抄 `grid/line_tool_box/tests.rs` 的断言风格）。
11. **覆盖算法边界**：单点笔画、重合点、垂直段（同 tick 多 key）、反向拖动（t1<t0）、`key+thickness>255`。

**标题**：`feat(editor): 画刷改为自由笔画两阶段交互（矢量预览 + √ 确认），修复快速拖动断墨`

- 画刷从「边拖边盖音符」改为**两阶段**：拖动只记录**矢量笔画**（圆头圆尾粗线条实时预览，横向 + 纵向卷帘），

  （≤2048 音符逐笔增量、超过则按轨批量归并 O(N+M)）并精确标脏；
- **顺手修复**（评审请一并确认）：`can_redo` 漏路径历史（与 `can_undo` 对称化）、
  曲线/形状/画刷 √ 确认未触发高精度洋葱皮刷新（`query.rs` mutation 归类）。

### 需要评审确认的口径（6 条）

1. **"加深 40%" = 各通道 × 0.6**（屏幕上"更暗 40%"的常规语义）；与 gfx 走带 `BORDER_DARKEN_FACTOR = 0.4`（乘数命名）不同口径，已单测锁死 `LAYER_DARKEN = 0.6`。
2. **色源 = 调色板** `current_track_color_f32(doc_track)`（与卷帘音符实例着色同源，洋葱皮轨同规则）；侧栏"每轨自定义色"目前**只**渲染在侧栏/走带泳道，不参与卷帘音符着色，本次**未**打通（如需打通请另立卡）。
3. **预览几何与生成结果连续但非像素级一致**：预览 = 圆头圆尾粗线条（端帽半径 = 总宽/2，整笔仅一对，按层带切色）；生成 = 覆盖格阶梯（每格向上 `thickness` 层，长度 = 吸附精度）。差异 ≤1 格 tick / ≤1 key。
4. **撤销粒度**：√ 走 `history.push_note_create`，与 300ms 内的上一条 Create 合并（与曲线/形状/文字一致），未强制起新分组；即"√ 产生恰好一条记录"的前提是 300ms 内无其他创建操作。
5. **Conductor（track 0）**：仅拦截**落笔**；待确认笔画的 √/× 在 track 0 **仍显示可用**（若照抄曲线工具的隐藏规则，用户切轨后笔画会被卡死，既不能 √ 也不能 ×）。
6. **卡面之外新增**：笔画记录**落笔基准轨**（`BrushStroke.base_track`），默认层分配以它为基准 → "画完 → 切轨 → √"不会把音符落到与预览不一致的音轨（含单测）。

## 15. 第二轮补丁（2026-10-01）：抖动修复 + 方形/所见即生成 + 笔画历史补全 + 两个性能真问题

### 15.1 Bug①「画到一定长度后整条笔画抖动」— RCA 与修复

| 层 | 事实 / 证据 |
|---|---|
| 现象 | 笔画画到一定长度后，**整条**笔画开始抖动（不是末端抖动） |
| 复现（探针实测） | 旧折线渲染 `preview_points` 超过 `MAX_PREVIEW_POINTS = 512` 后走 `uniform_sample(out, 512)`，其索引为 `i * last / (max - 1)`：**n=1500 → 512 个取样点；n=1501 → 仍 512 个点，但只有 256 个与前者位置相同**（探针输出）→ 追加一个点就让半边折线的顶点全部换位 → 每帧整笔重采样 = 抖动 |
| 直接原因 | 等距重采样把"当前长度"当分母，索引随长度漂移（增量不稳定） |
| 根因 | 用**屏幕折线 + 顶点抽稀**表达笔画；顶点集合不是"只增不改"的量 |
| 修复（架构级，非参数微调） | 按新需求改为**覆盖格方块**渲染（§15.2）：方块来自格集合，而格集合**只增不改**（追加采样点只新增格、绝不移动已有格），抖动在结构上不可能出现 |
| 回归测试 | `test_preview_runs_are_stable_while_stroke_grows`：追加采样点后，此前每个行段必须仍在（逐段精确相等）；旧实现过不了该断言 |

### 15.2 视觉口径变更：去掉圆头圆尾 → 方形，**所见即生成**

- **预览 = 逐覆盖格方块**：`x ∈ [格起 tick, 格起 + 吸附精度)`、`y ∈ [key, key+1)`，
  与 √ 生成的音符**逐格一致**；无端帽、无圆角、无线宽膨胀。
- **同源保证**：预览与 √ 写入共用 `Editor::brush_pending_notes()`（唯一权威源），
  不是"两套几何各画一遍"。测试 `test_preview_runs_match_confirmed_notes_exactly` 断言
  "预览行段展开集 == √ 实际写入 document 的音符集"。
- **行段合并**：同一 `(音轨, key)` 行内连续格合并为一个矩形（`brush_preview_runs`），
  单遍 256 槽直接索引、无排序无哈希（见 §15.4）。
- **视口剔除**：绘制前先按**格区间**剔除、再按屏幕矩形剔除，长笔画滚出视口后零矩形构建。

  （`preview_points` / `uniform_sample` / `cap_segment_path` / 各自测试）一并移除。
- **一处已知的着色差异（几何一致、明暗可能有细微差别）**：方块为**平涂**色
  （轨音符显示色 × 0.6）；生成后的音符由 `note.wgsl` 渲染，含一圈按

### 15.4 性能门控抓出的两个真问题（第二轮）

**(1) 预览每帧全量重建：70.2 ms/帧 → 7.4 ms/帧（病态）/ 0.33 ms/帧（真实）**

- 根因：每帧对 `覆盖格 × 层` 的**全部音符项做 HashSet 去重 + 全局排序**
  （病态负载 34 万项 → 70 ms/帧，远超 2 ms 线）。
- 修复：预览改为**单遍开行段**——256 槽数组按 key 直接索引"当前打开的 run"，
  连续格延长、跨 key 重现则拆段；**无排序、无哈希、无分配**（除输出 Vec）。
  代价：多笔画重叠时预览会重复填同色矩形（视觉无差别），而 √ 写入仍走精确去重路径。
- 顺带：绘制前加**格区间剔除**，长笔画离屏部分零成本。

**(2) `CreateOp` 撤销是逐 op 删除：35.1 s → 0.24 s（145×），0.68 µs/音符**

- 根因：`apply_create_ops(inverse=true)` 逐 op `position_of` + `remove_note`，
  而 `remove_note` **每次都 `rebuild_index()`**（O(块数) + 2 次分配）+ 块内搬移。
  一笔画刷 √ 生成 34 万音符 → 34 万次删除 → 实测 **35 053 ms**。
- 修复（跨模块，收益覆盖全部工具）：
  - **undo**：按轨收集索引（`position_of_unused` + 每轨 `used` 集合，保持"同值多份按份数"语义）
    → `remove_notes_merged` **一次性区间合并删除**（块内单遍压缩 + 单次索引重建，
    并正确分流被删音符的段内/区间增量事件）。
  - **redo**：按轨分组 `batch_insert_notes_sorted`（O(N+M) 单次归并），替代逐 op `insert_note`。
- 影响面：铅笔/曲线/形状/文字/协作等**所有**走 CreateOp 的撤销重做一并提速；
  已跑 `lumino-editor-state`(282) + `lumino-ui-editor`(595) + `lumino-ui`(357) + message/extras 全量测试无失败。

## 16. 第三轮修复（2026-10-01）：笔画被裁剪到「顶部 3 个 KEY + 左侧」— 裁剪区错位 RCA

### 16.1 现象（用户实测）

> 使用画刷工具绘制的笔画会被错误地裁剪掉**顶部 3 个 KEY** 和**左侧部分**。

关键特征：**只在左上角缺**，右下角正常；缺的位置与"鼠标拖到哪"无关，与"画布在窗口里的位置"有关
（**这一条是根因的第一性判据**：缺的区域是画布左上方的固定条带，不是笔画形状问题）。

### 16.2 RCA：`Program::draw` 的 `bounds` 是窗口坐标，帧内坐标是画布局部坐标

| # | 事实 | 证据 |
|---|---|---|
| 1 | iced 传给 `Program::draw` 的 `bounds = layout.bounds()`，随后 `renderer.with_translation(Vector::new(bounds.x, bounds.y), ..)` 才让**帧内局部坐标**落到正确窗口位置 | `iced_widget-0.14.2/src/canvas.rs:292-308` |
| 2 | 因此帧内**所有**绘制坐标 = 画布局部坐标（原点 = 画布左上角）；`bounds.position` = 画布组件在窗口里的偏移 | 同上 |
| 3 | 本项目自己就是这么理解的：拿到鼠标位置必须 `position - bounds.x/y` 才能当局部坐标用 | `grid/program_impl.rs:29,51`、`grid/vertical_program.rs:79,101`、`grid/program_impl/mouse_interaction.rs:28` |
| 4 | 该偏移的**真实量级**：左侧栏宽 +（走带模式再加音轨列表 160）、工具栏高 + 标题栏 30 | `host/render/viewport.rs:16-27`、`root/handlers/sidebar.rs:287-290` |

**旧实现（错）**：`grid/brush_tool_box.rs` 把 `bounds` 当局部矩形用——

```rust
let corner_a = Point::new(bounds.x, bounds.y);                     // ← 窗口坐标当局部坐标
let corner_b = Point::new(bounds.x + bounds.width, bounds.y + bounds.height);
...
if !rect.intersects(&bounds) { continue; }                        // ← 局部矩形 vs 窗口矩形
```

于是"可见窗口"实际变成了 `[offset_x, offset_x+w] × [offset_y, offset_y+h]`（局部坐标下），
即**整体右移 `offset_x`、下移 `offset_y`**，左上角一条 L 形区域被判为"视口外"整段剔除：

```
顶部被裁 key 数 ≈ (offset_y − ruler_height) / zoom_y
  例：offset_y = 84px（标题栏 30 + 工具栏 54）、zoom_y = 20、ruler = 24
      → 顶行 key 127 可见，但旧窗口顶边落在 key 124 → 125/126/127 共 3 个 KEY 被裁 ★用户实测"顶部 3 个 KEY"
左侧被裁宽度 ≈ offset_x − keyboard_width
  例：offset_x = 240px（左侧栏）、keyboard_width = 120
      → tick 格 0..3（x ∈ [120, 240)）整段剔除 ★用户实测"左侧部分"
```

**量化证明**（单测 `test_old_window_from_widget_offset_proves_clipping`，断言值即上表）：

```
局部坐标下真正可见：最顶行 key = 127、最左格 = tick 0
旧窗口（bounds.position 当局部）：key_hi = 124 → 顶部 3 个 KEY 被剔；cell_lo = 4 → 左侧被剔
新窗口（只用 size()）           ：key_hi = 128 ≥ 127、cell_lo = −6 ≤ 0 → 全部保留
```

### 16.3 修复

`grid/brush_tool_box.rs`：

1. 新增 `pub fn brush_visible_window(editor, bounds) -> BrushVisibleWindow`——**只读 `bounds.size()`**，
   `position` 显式忽略并在文档注释里说明"这是有意为之"（附 iced 契约出处，防止后人"顺手改回去"）；
2. 新增 `pub fn brush_run_screen_rect(editor, window, canvas_bounds, run) -> Option<Rectangle>`——
   把"逻辑窗口剔除 → 屏幕矩形剔除 → 内容区裁剪"三级过滤收敛成一个可测函数，绘制与测试**同一条管线**；
3. `draw()` 里 `bounds` 只用于 `bounds.size()`：`canvas_bounds = Rectangle::new(Point::ORIGIN, bounds.size())`；
4. **顺带补齐 WYSIWYG**：方块再裁剪到 `content_bounds`（键盘列 / 标尺带）。
   音符在键盘列与标尺带是被键盘、标尺覆盖层遮住的（键盘层是不透明底色，且在画刷层**之前**绘制），
   预览若不裁剪就会把方块画到钢琴键和标尺上面——那才是"所见 ≠ 生成"。

## 17. 第四轮修复（2026-10-01）：长笔画 UI 掉帧 —— 每帧成本 O(笔画长度) → O(视口)

### 17.1 现象与量化（先拿曲线，再动手）

用户体感："笔画很长的时候，UI 层明显出现掉帧。" 体感不能进 PR，先把它变成曲线——
`ui_brush_stroke_bench` 新增 **C 增长曲线**（[`growth`] 模块）与 **C2 同一笔边画边测**。

修复前（病态锯齿 / 粗细度 20，`LUMINO_BENCH_CYCLES=2`）：

| 点数 | 覆盖格 | 行段(全量) | 每帧(ms) | 单帧分配(MB) | 判定 |
|---|---|---|---|---|---|
| 1000 | 3790 | 36572 | 2.53 | 4.38 | ✗ 超预览线 |
| 2000 | 7590 | 73949 | 4.42 | 8.77 | ✗ |
| 5000 | 18990 | 185947 | 10.60 | 17.53 | ✗ |
| 10000 | 37990 | 373154 | 20.76 | 35.06 | ✗ **已超 60fps 帧预算** |
| 20000 | 75990 | 747855 | 35.68 | 70.12 | ✗ **掉帧 2 倍** |

- 成本增长 **14.1×**（1000 → 20000 点）；C2：同一笔边画边测 `2.70 → 12.11 → 17.13 → 39.44 ms`
  —— **一笔越画越卡**，10000 点后就稳定掉帧，与用户体感完全一致；
- **96.73% 的行段在视口外**（747855 条里只有 24434 条可见）；
- 每帧重新分配 **70MB**（整笔 `Vec<覆盖格>` + `HashSet` 去重 + 行段表）。

### 17.2 RCA（5-Why）

1. 为什么掉帧？→ 每帧预览构建耗时随笔画变长线性增长，20000 点时 35.7ms ≫ 16.67ms。
2. 为什么随长度增长？→ `brush_preview_runs()` 每帧对**整笔**做覆盖计算与行段合并，成本 O(总覆盖格数)。
3. 为什么"整笔"？→ 预览被设计成"全量几何 + 逐段剔除"，剔除只省了**绘制**，没省**计算**。
4. 为什么计算不能只做视口内？→ 覆盖函数 `cover_cells` 是"全量栅格化 + 全局去重"语义，
   没有"窗口"概念；线段栅格化只能从头顺序步进。
5. 根因 → **预览的覆盖计算缺少视口窗口语义**：绘制前才知道窗口，而栅格化已经做完了。
   修法：把窗口下沉到栅格化之前 —— 线段先用二维裁剪裁到窗口矩形，只对裁出的那一段做 DDA。

### 17.3 修复：视口窗口化栅格化（预览专用，生成口径不动）

| 位置 | 改动 |
|---|---|
| `cov.rs` | 新增 `CellWindow`（格坐标闭区间 + `FULL` 全量窗口）与 `cover_cells_in_window` / `segment_cells_in_window`：Liang–Barsky 把线段裁到窗口矩形，**只对窗口内那一段**步进；窗口外整段只付一次裁剪判定（O(1)） |
| `cov.rs` | 栅格化核心拆出 `segment_cells_cell_space`（**格坐标 f64**）：窗口化路径全程不落地 f32 |
| `cov.rs` | 角点判定由绝对 EPS 改为**相对容差**（只由有限的 t 值计算），使覆盖集对"参数缩放"不敏感 |
| `cells.rs` | 新增 `brush_preview_runs_in_window(window)`：覆盖格缓冲区跨笔画复用（每帧零分配）；`brush_preview_runs()` = `FULL` 窗口（测试/等价性/需要整笔几何的调用方） |
| `brush_tool_box.rs` | `draw()` 改调窗口化版本；`brush_visible_window` 直接返回 `cov::CellWindow`（一个窗口概念，两处用途：剔除 + 栅格化范围） |

**语义分工**（关键设计，避免"为了快而改坏生成"）：

```
预览（每帧热路径）  cover_cells_in_window  O(段数 + 视口内格数)  可容忍重复/拆段
生成（√ 一次性）    cover_cells             O(总格数) + 全局去重  精确、不受视口影响
```

### 17.4 过程中被测试抓出的两个真问题（自我批判）

| # | 问题 | 症状 | 抓住它的东西 |
|---|---|---|---|
| 1 | Liang–Barsky 终点用**已裁剪起点**求值 | 窗口 [50,60] 的段被裁成 50..150 → 越窗吐格 + 丢格 | `test_window_keeps_visible_part_of_long_segment` |
| 2 | 裁剪窗口上界按 `cell_hi` 而非 `cell_hi + 1` | 闭区间格索引在连续坐标上占 `[hi, hi+1)`，按 `hi` 裁会切掉最后一格的右半格 → 丢 `(26,80)` | `test_window_never_loses_or_invents_cells`（严格集合相等） |
| 3 | 裁剪端点回落 **f32**（~1e-7 几何偏移）+ 角点判定用绝对 EPS | 精确穿格点的角点判定不再是 tie → 丢 1 格 supercover 对角线，**预览与生成不一致** | `test_window_keeps_corner_diagonal_cell` + 渲染层严格等价测试 |

> 这三条都不是"跑一下看看"，而是**先写"窗口化 == 全量 ∩ 窗口"的严格等价测试**才暴露的。
> 只写"性能变快了"的 bench 会把它们全部漏掉。

### 18.2 RCA：`Frame::fill` 是"每块一次"的完整细分

证据（`iced_wgpu-0.14.0/src/geometry.rs:157-183`）：

```rust
fn fill(&mut self, path: &Path, fill: impl Into<Fill>) {
    let mut buffer = self.buffers.get_fill(&style);      // ← 每次调用按颜色查 buffer
    let options = FillOptions::default()...;             // ← 每次调用构造选项

}
```

## 19. z-order 闪烁修复：预览层改为「按提交序直绘」（2026-10）

### 19.1 现象与根因（RCA，不修症状）

**现象**：§18 搬到 wgpu 预览通路后，同一格上出现多个预览矩形时，重叠区**逐帧闪烁**
（胜者在两个颜色之间来回跳）。

**根因链（三环，缺一不成）**：

1. **深度平局**：`shaders/note.wgsl:150-157` 预览分支（哨兵）**深度恒为 `0.0`**，
   而文档音符深度 = 「区域起点 + 全局源索引」（跨帧稳定）⇒ **预览层内部任意两个
   重叠矩形深度完全相等**。
2. **平局由随机顺序裁决**：音符管线是 `depth_write_enabled=true` + `LessEqual`
   （`constants.rs:46-54`）⇒ 同深度「**后画者胜**」；而「后」= 可见索引缓冲中的位置，
   该缓冲由 `shaders/cull.wgsl` 每 workgroup 线程 0 **抢占式 `atomicAdd`** 分配槽位
   —— **顺序由 GPU 调度决定、帧间不稳定**（`depth_tests.rs:3-6` 早已记载）。
3. **重叠矩形真实出现**：`ui-editor/src/interaction/brush/cells.rs:142-157` 的行段
   合并守卫是 `if t == track && end == cell` —— 守卫带**同轨条件**；多笔画 /
   多音轨（`brush_track_for_level` 按粗细层映射音轨）落在**同格不同轨**时守卫失效，
   落入 `_` 分支再开一个新 run ⇒ 两个几何完全重叠、**颜色不同**、深度同为 `0.0`
   的实例 ⇒ 颜色逐帧翻转 = 闪烁。

**为什么现在才暴露**：`note.wgsl` 深度契约有明文免责声明 ——「预览哨兵恒为 0.0
（同批次多个哨兵仍共享深度，**实际路径单哨兵**）」。§18 把预览实例数从 1 个
（铅笔 hover/drawing）抬到**视口内 24,947 个**（长笔画实测），该声明作废；而
`init.rs` 的直绘管线门控（`is_onion && needs_depth`）又把预览层排除在「顺序确定」
的直绘通路之外 → 预览层只能走随机序 cull 路径。

### 19.2 修复：预览层走 VS 直绘（实例索引升序 = 提交序）

| 文件 | 改动 |
|---|---|
| `shaders/note.wgsl` | 新增 `vs_direct`：实例索引取 `@builtin(instance_index)`（**不读可见索引缓冲**），可见性判定搬进 VS（谓词与 `cull.wgsl` 逐字一致），深度/取色公式与 `vs_main` 逐字一致 |
| `note_renderer/pipeline.rs` | `create_direct_pipeline` 增 `alpha_blend` 参数（洋葱皮仍 `opaque_target`；预览层 `alpha_blended_target` —— 预览必须与下方文档音符混合，哨兵分支 70% alpha） |
| `note_renderer/init.rs` | 直绘管线门控由 `is_onion && needs_depth` 改为 **`needs_depth`**：预览层也建；混合模式取 `!is_onion` |
| `render_thread/.../render_pass.rs` | 预览层（`renderers.note`）横向分支由 `draw` 改 **`draw_direct`** |

**为什么这样修就对了**：`draw_direct` 按 chunk 顺序 `draw(0..4, 0..chunk_len)`，
实例索引即源索引升序 = **提交序**（`cells.rs` 生成行段的顺序 = 笔画创建顺序）⇒
后提交的矩形后到，深度同为 `0.0` 时 `LessEqual` 通过 → **覆盖先到者 = 后来者居上**，
且**跨帧稳定**（不再依赖 cull 调度）。副产品：预览层不再需要 compute cull pass。

### 19.4 已知边界（记录在案，不掩盖）

- **纵向卷帘已补齐（2026-10）**：`note_vertical.wgsl` 增 `vs_direct`（转置坐标，
  深度/取色与 `vs_main` 逐字一致），`NoteRenderer` 增 `vertical_direct_pipeline`

  「后来者居上」。洋葱皮纵向仍走 cull 路径（与既有 `vs_cull_mode` 只在横向生效一致）。
- **性能口径（直绘 vs cull 的取舍，有实测依据）**：本项目实测「直绘要为全部实例各跑
  一遍 VS（≈0.65 ns/实例），compute cull 只扫一趟（≈0.10 ns/实例），放大档下直绘慢
  8 倍（1.5 万可见 / 1600 万总数），**仅当可见占比 > 90% 才占优**」
  （`render_pass.rs:133-139`）。预览层的可见占比 **≈ 100%**（实例由 §18 视口窗口生成
  + `brush_run_screen_rect` 过滤内容区），落在门控甜区，因此预览层恒直绘**符合既有
  实测口径**；同时准备阶段由 `prepare_pass`（含每帧一次 cull compute dispatch）改
  `prepare_direct`（只写相机 uniform），**净省一次 compute pass 的提交开销**。
  洋葱皮（千万级实例、可见占比低）不受影响，仍走 cull + `vs_cull_mode` 闸门。
- **重叠矩形仍存在**（只是顺序确定）：`cells.rs` 行段守卫仍带同轨条件，同格不同轨
  产出两个重叠实例。因顺序已确定，视觉为「后画者覆盖」，与 `brush_pending_notes()`
  落盘语义一致；彻底消除几何重叠需「后写覆盖先写」的区间裁剪（代价：每格
  O(已开 run) 查找，病态长笔画下退化）。
