## 0. 如果只记三句话

第一，DSP 的验收标准不是「跑通了」，而是「逐位一致、听感正确、块长无关」三件事同时成立；
只要有一件不成立，这个改动就不算完成，哪怕 CI 全绿。

第二，这个仓库里真正需要手搓的 DSP 只有两块：LGS 的那套 GPU 内核（外加它依赖的
Rust 侧系数与状态管理），以及导出链路里那套独立的限幅器。CPU 的合成内核根本不在
这个仓库里，它在 `PenguinBMDevs/xsynth-Lumino` 这个 fork 里。

第三，AI 可以在 DSP 外围做很多高价值的事——写判定器、做数据层、改控制面、补基准；
但实时内核属于「只读区」。任何情况下，AI 都不能在没告诉你的前提下改动它，
哪怕是「看起来行为不变的重构」。

## 1. 本仓库里的「DSP」到底在哪

要讲清楚边界，得先把「DSP」这个词拆开。它在这个项目里不是一个目录，而是三个同心圆。

最里面一圈是 LGS 的实时内核。它由三个 WGSL 着色器（`render.wgsl`、`mix.wgsl`、
`mix_reduce.wgsl`）和一组 Rust 侧的系数/状态代码组成：`synth/dsp/sinc.rs` 生成
窗函数 sinc 表，`filter.rs` 算 RBJ 双二阶低通系数，`envelope.rs` 描述七段包络，
`voices.rs` 把 SF2 的 zone 装配成 GPU 参数。这一圈决定了「每个样本长什么样」。

第二圈是「让第一圈能正确运转」的时间与增益轨迹：`engine/limiter.rs` 的前视限幅、
`audio/resample.rs` 的设备采样率转换、`engine/voice_alloc.rs` 的声部分配与抢占、
`engine/trim.rs` 的复音裁剪与淡出、`engine/cc.rs` 的 CC 到 DSP 参数映射。
这一圈不直接写样本，但它决定样本在什么时刻、以什么增益、以什么包络被算出来。
它和第一圈一样属于「听感边界」，错一处就是可闻的爆音、断音或音量跳变。

第三圈是仓库外面的东西。`xsynth-core` 是 CPU 合成内核，负责实时兜底和 CPU 离线导出；
`xsynth-realtime` 是它的实时驱动；`xsynth-soundfonts` 是 SF2 解析，LGS 也在用它。
这三者都来自 fork `PenguinBMDevs/xsynth-Lumino`（LGPL-3.0，隔离在独立仓库，
通过 workspace 的 `[patch.crates-io]` 钉在固定 rev）。再外面还有 Maestro——
它是运行时加载的外部合成器库，DSP 完全不在我们这边。

所以「完善 XSynth 还是完善 LGS」这个问题的真实形状是：**仓库内的手搓面积约两三千行，
集中在 LGS；仓库外还有一个我们正在维护私有补丁的 CPU 内核**。这两件事的成本结构完全不同，
不能混在一起谈。

## 2. 这些代码为什么长成这样

理解「为什么不能随便改」，比记住「哪些文件不能改」更重要。下面每一条都是踩过坑之后
写进代码注释的结论，我把现象、原因和「改了会怎样」放在一起讲。

### 2.1 逐位一致不是洁癖，是唯一可自动化的验收

`synth/dsp.rs` 的开头写得很直白：这里的每个公式都精确镜像 XSynth 的实现，
目的是让 LGS 的渲染结果能和 XSynth 的渲染逐样本对比，从而和验收用的参考音频对上。
包络的七段、`f^8` 的凸曲线、`(1-f)^8` 的凹曲线、段与段之间「接上一个阶段最后输出的值」，
这些都不是随手写的，而是为了让两条后端在同一份 MIDI 上产出同一份波形。

这意味着一个看似无害的改动——比如把包络段边界改成「从 0 重新开始」——会让输出
整体偏移一个极小的量。自动化测试如果只比 RMS 或者只比长度，很可能放过它；
但人耳在密集段落里听到的就是一层薄薄的毛刺。更麻烦的是，这种偏差会让
「与 XSynth 对拍」这条唯一的自动化验收链路失效，从此以后所有性能优化都失去参照。

### 2.2 并行化必须先固化「顺序」，再谈并行

`mix.wgsl` 里有一段注释值得完整读一遍。大意是：旧版内核是一个线程遍历所有声部，
在 5080 上 block 512 只有 4 个 workgroup，单块耗时约 11.5 毫秒；新版为了提速，
不是简单地把求和拆开并行，而是先在 CPU 侧按「通道 + 是否已释放」建立稳定的声部桶，
桶内保持原来的声部升序，然后一个线程负责一个 (帧, 通道) 对，按原顺序累加，
最后再用一个很小的归约 pass 按通道升序相加。注释明确写了这么做的原因：
**既要并行度，又要保持完全相同的浮点累加顺序**，否则输出就不再逐位一致。

`mix_reduce.wgsl` 的注释同样在强调这一点：归约必须按通道升序，
因为旧版单线程内核就是这个顺序。

这条经验可以推广成一句话：在音频 DSP 里，浮点加法不满足结合律，
所以「怎么并行」本质上是一个数据结构问题，而不是线程数问题。任何试图用
workgroup 树形归约或原子累加来「优化」混音的做法，都会改变求和顺序，
进而改变输出。这种改动在图像渲染里通常无害，在音频里就是验收失败。

### 2.3 限幅器的窗口必须和渲染块解耦

`engine/limiter.rs` 里定义了 `LIMITER_WINDOW = 512`，注释解释了为什么：
限幅器的增益轨迹必须只依赖「信号本身」和「样本的绝对帧位置」，不能依赖渲染块怎么切。
原因是前视限幅需要在窗口末尾把「未来」的样本回退成整窗峰值来算增益；
如果窗口边界跟着渲染块走，那么块长从 512 变成 2048 时，同一个音频文件会得到
不同的增益曲线。REF-LGS-008 的实测是：开限幅时，512 与 2048 的第一处差异出现在第 304 帧，
96% 的样本不同。

这件事的连锁影响比看起来大得多。正是因为先修好了「块长无关」，REF-LGS-009 才敢
把离线导出的默认块长从 512 提到 2048，性能才有了那次提升。也就是说，
**块长无关不是锦上添花，它是「敢调块长」的前提**。

### 2.4 状态回读不能降频，因为那等于「重播」

`synth/engine/types.rs` 里 `STATES_SYNC_EVERY` 的值是 1，注释写得很不客气：
这个值必须保持很小，因为已经结束的声部只有在回读之后才会被清理；如果为了省一次
map/poll 把它调大，声部会从「过期的状态」恢复，表现为音频被重播——这是明确禁止的。
注释最后一句是「Kept at 1 for exactness ... which the user forbade」。

这条约束经常被误读成「一个可以调的参数」。它不是。它是「状态由谁拥有」这个设计问题的
外在表现：目前 CPU 是状态的权威副本，GPU 每块把推进后的状态交回来，CPU 再合并回写。
在这套所有权模型下，回读频率就是正确性的一部分。要真正省掉这次往返，
需要把所有权改成「GPU 持有状态、CPU 只读结束标志」——那是一次结构性改造，
而不是把常量从 1 改成 4。

### 2.5 静态表和动态表的边界是「会不会变」，不是「大不大」

`gpu/layout.rs` 把声部参数拆成两张表：静态表 64 字节，只在分配槽位时上传一次；
动态表 52 字节，每块上传。`pool.rs` 和 `slot.rs` 里还有一整套槽位分配、回收、
脏区间合并的逻辑。这套设计（REF-LGS-010）把每声部每块的上传量从 250 字节压到 120 字节
（动态 52 + 状态 68），A/B 实测墙钟提升 10% 到 20%。

但真正值得记住的不是数字，而是注释里那句「这些字段都会在生命周期内变化」：
`speed` 会被弯音改，`sample_offset` 要等采样上传后才解析出来，`env_*` 会随包络
阶段和淡出改写，`release_at` 会随 NoteOff 变化。凡是会被改写的字段，就只能待在动态表；
把它们挪到静态表意味着必须在每一个改写点打脏标记，漏一处就是错音。
这就是为什么 REF-LGS-010 的卡面设计里把 `sample_offset*` 和 `speed` 算成静态，
而实现时把它们留在了动态——实测推翻了设计假设。

### 2.6 重采样必须跨块，因为截断就是混叠

`audio/resample.rs` 用的是 polyphase FIR，截止频率放在输出 Nyquist 的 0.9 倍，
并且是「因果地跨一个块」：每次 `process` 输出的是上一个输入块，当前块只提供
滤波器需要的「未来」抽头。注释解释了原因：如果不这样做，滤波器会在每个块边界被截断，
高频内容折返到可听频段，在密集的高频素材上听起来就是噼里啪啦的爆裂声——
而且这种爆裂经常和渲染耗时无关，最容易误导排查方向。

### 2.7 裁剪淡出是 5 毫秒，不是 1 毫秒

`types.rs` 里 `FADE_OUT_MS` 的注释记录了一次真实的听感回归：最早用 1 毫秒淡出，
在密集裁剪时多次淡出会叠加成「电锯音/噼啪」，于是改成 5 毫秒线性衰减；
同时每块允许新建的淡出组数有预算（`MAX_TRIM_FADES_PER_BLOCK`），
超出预算的裁剪留到后续块，把「同块批量硬切」摊成多块的小批量。

这条说明了一个容易犯的错误：直觉上「淡出越短越不容易被听出来」，实际上
短淡出叠加起来反而更刺耳。数值上都叫「淡出」，听感上完全是两回事。

## 3. 反面清单：看起来像优化，实际是事故

下面这些都是在别的项目里常见、在这个仓库里绝对不该出现的「优化」。我把它们列出来，
是因为它们每一个都足够合理，合理到如果不提前写下来，下一个人（或 AI）一定会尝试。

第一，把混音里的按序累加换成并行归约。提速是真的，逐位一致没了也是真的。
一旦没了，你就失去了与 XSynth 对拍的资格，后续所有性能数字都变成孤证。

第二，把 `STATES_SYNC_EVERY` 调大来省一次 map。省下的可能是几百微秒，
代价是音符尾部被重播，而且这种问题只在密集段落偶发，极难复现。

第三，让限幅器窗口跟着块长走。块长是用户可调的，等于让输出依赖用户的导出设置，
同一份工程导出两次可能不一样。

第四，在音频回调里加锁或分配内存。`ui_sfx.rs` 的模块注释把纪律写死了：
回调里零锁、零分配，只读两个原子量并搬运样本。实时线程一旦优先级反转，
表现出来就是 dropout，而 dropout 在测试里通常不可见。

第五，为了性能删掉淡出或缩短淡出。参考 2.7，听感会直接劣化。

第六，把两套限幅器「统一」成一套。LGS 内部是前视峰值限幅，导出链路是
LoudMax 风格的压缩/限幅（独立的 threshold、attack、release）。它们本来就不是
同一个算法，硬合并等于同时改变两条链路的输出。真要统一，正确做法是先写对拍，
量化差异，再决定以哪一套为准，而不是直接删掉一套。

第七，在 xsynth fork 上加效果链。fork 现在的补丁面是音频设备节奏和输出流 owner，
属于「为了让它能在我们的宿主里跑」的必要适配。往上面加特效，等于把一个外部依赖
变成第二套自研 DSP，而且是最难维护的那种——既要跟上游 rebase，又要自己验听感。

第八，用近似数学换性能。比如把 sinc 插值降阶、把双二阶换成单极点近似。
这类改动在波形上看不出问题，在频谱上很明显，在听感上就是「糊」或「刺」。
如果没有频谱对比和人工听感，根本不该动。

## 4. 为什么「自己写 DSP」不是一个决定，而是一串决定

很多人把「去 XSynth 化」理解成「写一个新的合成器」。实际上它至少要拆成四个决定，
而且这四个决定的风险和收益完全不同。

第一个决定是数据层。SF2 的解析、zone 匹配、采样打包，这一层被 LGS 和 XSynth 同时依赖，
是唯一「去掉它就能同时解除两条后端依赖」的部分。它不跑在实时线程里，可以用
现有 SF2 素材做确定性对拍，属于可以工程化推进的部分。如果只做一件事，就应该做这件。

第二个决定是 CPU 实时内核。这是 xsynth-core 的位置，也是「必须手搓」的核心。
它跑在实时线程、没有自动化 oracle、听感只能靠人。要不要替换、什么时候替换，
是一个人的决定，不是一个排期的决定。

第三个决定是默认后端。现在 `SynthBackend` 的默认值是 XSynth（`enums.rs` 里
`XSynth` 标了 `#[default]`）。只要默认还是它，XSynth 就是主路径，LGS 的可靠性问题
（比如重建耗尽后的降级、首播懒重采样的卡顿）就只是「可选后端的问题」。
把默认切到 LGS，等于宣布 XSynth 进入维护模式，这个决定需要 LGS 的可靠性卡先落地。

第四个决定是许可证边界。xsynth 系是 LGPL-3.0，现在的做法是 fork 放在独立仓库里隔离。
如果自研数据层，必须按 SF2 规范独立实现，不能复制它的代码；否则隔离边界失效，
整个项目的许可证结构都要重新评估。

这四个决定里，第一个可以马上做，第二个只能由人主导，第三个依赖前两个的进度，
第四个是法律问题不是技术问题。把它们混成一个「DSP 重构」的大卡，是最容易烂尾的做法。

## 5. 人机分工：谁写什么，为什么

### 5.1 为什么实时内核不能交给 AI

不是因为「AI 不会写 DSP」。而是因为这类代码的失败模式，恰好是 AI 最不擅长的验证方式。

实时音频内核的验收依赖三件事：逐位一致、听感、以及真实硬件上的时序行为。
逐位一致可以自动化，但它只能证明「和参考实现一样」，不能证明「好听」；
听感只能靠人，而且往往要在特定素材上（密集黑乐谱、长音尾、单端口素材）才能暴露；
时序行为依赖驱动、缓冲区、系统负载，测试环境里根本复现不出来。
REND-015 的 1 毫秒淡出改成 5 毫秒，就是一个典型：数值上「正确」，听感上是电锯。

再加上一个现实约束：这类代码一旦写错，症状通常是「偶发爆音」「尾音消失」「某个音源上才有」，
排查成本极高，而且很容易被归因成「用户环境问题」。让一个无法长期驻留、无法亲耳验证、
无法在目标硬件上跑负载的协作者去改这块，是把风险转移给未来的维护者。

### 5.2 AI 真正高价值的三件事

第一件是判定器。`hash_render`、`lgs_ab.py`、黄金哈希矩阵、分相统计——这些是把
「人工内核」变成「可回归」的唯一杠杆。REF-LGS-013 已经铺好了地基，但夹具覆盖、
失败诊断、CI 编排还有很大空间。这件事 AI 做得比人快，而且错了不会伤到音频。

第二件是数据层。SF2 解析、zone 表、采样打包、缓存与生命周期。它不实时，有确定性
oracle，而且一旦做好，LGS 和未来的 CPU 内核都能受益。这是「去依赖」里唯一
可以工程化推进的部分。

第三件是控制面。事件路由、端口映射、ProgramChange 的分发、SysEx 的解释、
配置与 UI、统计与诊断。这些是「协议层」，不是「数学层」，改错了是功能不对，
不是音质不对，回滚成本低。

### 5.3 一个可执行的协作流程

第一步，先把「要什么」写成规格，而不是直接写代码。比如「CC91 的混响深度应该如何映射到
参数」「ProgramChange 在单 SF2 多 preset 下的路由规则」，这些是跨后端的语义，
应该由人确认，AI 起草。

第二步，规格确定后，由人实现内核（如果是 A 级），或者由 AI 实现控制面（如果是 C 级）。
中间的 B 级（加载期数学、参数装配）由 AI 起草、人逐行复核。

第三步，无论谁写，验收都必须包含三件事：黄金哈希逐位一致、`lgs_ab.py` 的 2% 门控、
以及在真实素材上的人工听感抽查。缺一件就不算完成。

第四步，把这次改动的原因、影响面、对拍数据写进卡面和文档。不是为了流程好看，
而是为了让下一个人在改同一块代码之前，知道哪些假设是验证过的。

## 6. 影响分析：违反边界的代价

如果 AI 在没人知道的情况下改了实时内核，最轻的后果是逐位一致失效，
性能优化失去参照；中等后果是某个音源上出现偶发爆音或断音，用户报障后
排查方向被引向渲染、驱动、甚至用户的设备；最重的后果是实时线程出现锁或分配，
在低配机器上表现为持续的 dropout，而这种问题在开发机上永远复现不了。

如果 AI 在不了解许可证边界的情况下「参考」了 xsynth 的实现写自研解析器，
后果不是技术问题，而是整个项目的许可证结构需要重新评估，这属于法律风险。

反过来，遵守边界的收益是复利式的：判定器让性能优化可回归，数据层让两条后端共享
同一份解析，控制面让语义问题集中在一处。这些收益不会立刻体现在帧率上，
但会让后面每一次改动都更便宜。

## 7. 落地建议与改动面

这次要落地的东西，按风险从低到高分三档，建议分批做。

第一档是文档，也就是本文和配套的 AI 规则。改动面为零，只是新增两份 Markdown，
不碰任何代码。建议立刻做掉，后面所有讨论都以它为准。

第二档是把规则挂进 `AGENTS.md` 和 skill。这一档的改动面是「所有未来 AI 任务」，
所以需要你确认措辞。建议做法是在 `AGENTS.md` 里加一节「DSP 只读区」，指向 AI 规则文件，
而不是把整份规则复制进去——复制会漂移。skill 侧可以加一个很小的
「DSP 任务开工前先读规则并声明是否触碰只读区」的步骤。工作量大约半天，
风险是措辞过严会挡住合理的重构，过松等于没写。

第三档是机器强制。比如加一个路径检查脚本，PR 改动 A 级文件时要求显式的人工批准标签；
或者在 CI 里跑一个「A 级文件变更检测」。这一档工作量和维护成本都更高（一两天起），
而且需要设计豁免机制，否则会误伤真正的人工改动。我的建议是等前两档跑一段时间、
看实际发生几次「需要改 A 级」的情况，再决定要不要上机器强制。

至于「开卡」，我建议先开一张总卡（暂名 `REF-DSP-000`），把四个决定写进去，
下挂三张子卡：数据层自研、默认后端切换、跨后端语义规格。但这件事应该等第一档
文档落地、并且你确认优先级之后再做，避免又变成一张长期挂着的卡。

## 8. 产品边界：内置音频只做预览

先把一个容易混淆的前提说清楚。MIDI 本身并不「支持效果」，它只传输「发送量」：
CC91 是混响发送量，CC93 是合唱发送量，CC94 是延迟发送量；至于混响用什么算法、
房间多大、衰减多长，规范里没有定义，完全由设备自己决定。所以当我们在内置合成器里
实现一个混响时，那不是在「补上 MIDI 兼容性」，而是在定义 Lumino 的声音——这是合成器的
特性，不是 MIDI 的义务。反过来，不实现这些发送量也不是缺陷，而是一个需要被明确
写下来的产品决定。

目前 LGS 就是这样：`synth/engine/cc.rs` 处理 CC7/10/11、CC64、CC71/72/73、NRPN
这些直接影响声音的参数，但不处理 91/93/94。而 KDMAPI、系统 MIDI、Maestro 这些
外部后端是原样转发 CC 字节的，专业用户接上外部合成器或 VST 宿主后，这些发送量会
正常到达对方。换句话说，专业路径本来就存在，只是产品上没有把它说清楚。

从投入产出看，内置效果链的成本从来不在「写那个算法」上。第一是身份分裂：LGS 一套、
XSynth 一套、导出链路再一套，混响尾巴长度、预延迟、增益结构只要有一处不同，
「同一份工程试听和导出不一致」的报障就会出现，而这正是「两套限幅器」问题的放大版。
第二是实时与离线的一致性：效果器有延迟、有尾巴，块长一变、导出块长一调，
输出就得重新对拍，等于把已经修好的「块长无关」契约再破一次。第三是参数与 UI：
发送量怎么映射、有没有预设、能不能按端口分轨、和限幅器谁先谁后——这是 DAW 级别的
功能面。第四是验收：效果链没有自动化 oracle，只能靠人耳，而它恰好是「听起来差不多、
其实全是问题」的重灾区。

所以这条边界建议写成明确的产品非目标，而不是一句口头共识：**内置音频服务于
「画的时候能听见、导出视频时有条能听的音轨」，不服务于专业制作。** 音色与效果交给
外部后端或 DAW；在应用内做通用效果链、VST 宿主、路由矩阵，都不属于 Lumino 的核心。

不过这并不意味着可以「交出去就不管」。多工具工作流能不能被接受，取决于一件事：
**Lumino 交出去的 MIDI 能不能让 DAW 精确复现这里的音符语义**。端口与通道的映射要能
原样导出，ProgramChange 与鼓通道的语义要正确，每端口音色库的指向要能表达，
CC 与 SysEx 要原样透传，tempo 与拍号要保真。这些不是效果，是「响的是哪个音」的
正确性问题。也正因如此，卡面处置应该分开：纯效果链（REND-012）暂时保留为待办，
不关闭也不排期（2026-11-25 决定，等产品边界最终拍板后再处置）；
ProgramChange/打击乐对齐（REND-013）、每端口音色库（REND-005）、GS/XG 鼓通道重指派
（REND-007）应当保留，因为它们决定音符落在哪件乐器上。

最后，内置后端忽略 CC91/93/94 这件事应该在设置页或文档里明说。不是道歉，是交代边界：
用户知道「要空间感请走外部合成器或 DAW」，就不会把它当 bug 报。

## 9. MIDI Clip 与性能主线（研究结论，尚未立项）

讨论中还提出过一个方向：不再按轨道、通道甚至端口来对待 MIDI，而是像现代 DAW 那样
把 MIDI 当作「对象」来读写，也就是 Clip。这个方向的痛点判断是准确的：现在的数据模型
是轨道导向的——`MidiDocument` 里每条轨一个音符列表，`control_events` 是**文档级**的
一条全局列表（事件里带通道号）；播放侧的 mute/solo 是「取事件时过滤」，
而不是「装载时就不取」；历史上甚至有一个 `SetSkipTracksInCache` 被移除，注释写着
留给未来的 disk cache。也就是说，你的直觉和这个仓库的历史设计是吻合的，只是从来没有
走到「对象级」。

但这里要先把目标与手段分开。**性能收益主要来自索引与裁剪，而不是来自把东西叫 Clip。**
给对象换个名字不会让 CPU 变快；真正让 CPU 变快的是三件事：按时间区间建索引、
每块只遍历活跃区间、冻结/离线内容在装载阶段就被排除。这三件事可以在一套「轨道 + 区间」
的模型上先做完，不需要先做完整的对象模型迁移。REAPER 的 item 模型之所以快，
是因为它背后有成熟的事件调度与缓存，而不是因为 item 这个概念本身。

如果要做 Clip，有三个问题必须先有答案，答不上来就不该动模型。第一，CC 隔离靠什么
实现？MIDI 的 CC 是通道级的，两个 clip 要各自独立，要么各自占一个通道（通道预算够不够？
黑乐谱本来就吃端口和通道），要么引入「虚拟通道 / 每 clip 控制器状态」——后者要改
合成器与播放侧的语义，不再只是编辑器的事。第二，重叠 clip 怎么办？重叠区域的事件顺序、
CC 合并、轨道流如何拼接，都要定义清楚，REAPER 自己在这块也有历史包袱。第三，SMF 的
导入导出怎么映射？MIDI 文件是轨道的，clip 是对象的，导出时要么合并回轨道并给出告警，
要么定义一套工程格式，这牵扯到文件兼容与协作同步。

因此建议分三步走。第一步先做「激活集」：给每条轨或每个区间维护时间轴上的活动索引，
调度只遍历当前块覆盖的区间；冻结/离线轨在装载或视图构建阶段就排除；mute/solo 从
「取事件时过滤」前移到「装载时排除」。这一步不改对象模型、不改文件格式，收益是调度与
解析的直接下降，风险低，而且完全落在数据/控制面。这里有一个必须处理的幽灵问题：
静音期间被跳过的事件会让通道控制器状态发生偏移（比如静音前发过 CC7），取消静音时
要做一次显式状态重建，否则会出现「取消静音后音量不对」。第二步再谈 Clip 作为编辑对象，
先解决 CC 隔离、重叠语义、SMF 映射三个问题。第三步才是按 Clip 寻址的播放与导出，
到那时候事件流不再按轨道拼，性能收益才真正兑现，但播放引擎、导出管线、协作同步、
撤销都要跟着改。

与这条线并行的是「巨量音符处理」本身。建议把它拆成四个可测的面：编辑面（选中、拖动、
批量操作、撤销，瓶颈通常在数据结构与索引）、渲染面（GPU 常驻、可见性裁剪、瀑布流，
已有成熟基准）、调度面（每块事件取出、mute/solo/冻结裁剪、通道状态维护，正好是
第一步的靶点）、导出面（守住块长无关与逐位一致，不为了速度牺牲一致性）。这四块里，
编辑与调度最值得投入，因为它们直接决定画板的手感；渲染已经很强；导出守住契约即可。
DSP 不在这四个面里，它只对应一条「预览质量门槛」：不爆音、不丢音、延迟可接受，到此为止。

## 10. 一句话原则

**人负责「声音对不对」和「产品做什么」，AI 负责「怎么证明它一直对」。**

如果某件事既影响声音、又无法被自动证明，那它就落在只读区；
如果某件事会改变产品定位（比如内置效果链、VST 宿主、路由矩阵），那它就需要
人先拍板，而不是被当成一次「顺手优化」。不是不信任谁，而是这类决定的代价与
验证方式，和写代码的节奏根本不匹配。
