# GPU 检测缓存回写与回退适配器按需收集 · 调研报告

- 调研日期：2026-10-03
- 调研对象：卡「设置页手动检测结果回写缓存 + `enumerate_fallback` 按需收集」（卡面未标注编号，本报告按内容命名；关联 #27 / UI-008）
- 分支：`dev`（HEAD `43ca4ed9`，工作区干净，尚未动工）
- 调研方式：源码逐条对质 + **实测 A/B 探针**（临时探针代码与临时 example 已全部还原，`git status` 干净；复现命令见 §9）
- 结论：**卡面的两处问题都属实，量化后价值高于卡面描述**——通过路径每次白花的回退枚举约 **0.4–0.6 s**，占全量检测耗时的 **58%–88%**。但卡面有 **2 处会直接跑偏的缺陷**：①「检测入口加一个 `collect_fallback` 布尔量」与卡面自己写的「失败报告也要收集」互相矛盾（布尔量在通过/失败判定**之前**就已决定，通过路径的浪费一分不少）；②`GpuCheckFinished` 事件**不携带适配器指纹**，卡面第 2 步的 `persist_gpu_check_cache(fingerprint, passed)` 拿不到 `fingerprint`，必须扩事件载荷。修正后实施成本约 **5 文件 / 45–60 行 + 6 项测试**。

### 2.1 缺口 a：手动检测不回写缓存

对照：启动门控是唯一的缓存写入方（`src/runner/lifecycle/device_gate.rs:112-120 / :137 / :156 / :198`），

### 2.2 缺口 a 的两种真实触发场景

**场景 1（卡面描述）**：门控本次没跑到全量检测 → 手动检测通过后无处落地 → 下次启动照旧全量检测。具体是：

- `gpu_last_check_time` 超过 TTL 7 天（`device_check_policy.rs:27`）→ 门控直接落回全量检测（`:57-69`）；
- 上次检测失败（`cached_passed != Some(true)`）；
- 旧配置缺 `gpu_last_check_time`。

⚠️ 补充口径：若用户把「每次启动时检查 GPU 兼容性」关掉，门控在 `device_gate.rs:41-45` 直接返回，
**下次启动也不会检测**，此时「手动通过省下次启动」不成立。卡面没说这个前提。

**场景 2（卡面未提，危害更大）**：门控已写入 `passed=true` 的缓存（TTL 内）→ 用户手动检测**失败**
（驱动异常 / 超时 / 渲染失败）→ 缓存仍是 `true` + 指纹仍是这个适配器 →
下次启动 `cache_hit` 命中（`device_check_policy.rs:88-95`）→ **直接跳过检测放行**。
即：缓存会把用户刚刚亲眼看到的失败吞掉。这是「手动结果不回写」最坏的一面，卡面只说了「不刷新」。

### 2.3 缺口 b：通过路径的回退枚举与它的消费者

```
run_check_with_timeout(DEFAULT_TIMEOUT)  (check.rs:31-59)
  └─ check_gpu_support() → check_inner() (check.rs:75-177)
```

`fallback_adapters` 的全部消费者（全仓 grep 只有 3 个文件）：

|---|---|---|
| `GpuCheckReport::detail()` | `report.rs:128-133` | 拼成「其他可用后端（回退参考）」文本 |

卡面「白建一个 `Backends::all` 实例」的描述准确，但**没写出代价有多大**，见 §3。

## 3. 实测：回退枚举到底值不值这个改动

### 3.1 环境

| 项 | 值 |
|---|---|
| OS / GPU | Windows 11 / NVIDIA GeForce RTX 2060（驱动 32.0.16.1062）+ GameViewer Virtual Display Adapter |
| 要求后端 | Vulkan（`required_backend_name()`），实测枚举到 **1** 个适配器 |
| 回退后端 | 实测枚举到 **4** 个：2×`RTX 2060 [Dx12]`、`Microsoft Basic Render Driver [Dx12] Cpu`、`RTX 2060/PCIe/SSE2 [Gl]` |
| 探针 | 临时 `#[cfg(test)]` 探针 + 通过路径临时改为 `fallback_adapters: Vec::new()`（**已还原**，§9） |

### 3.2 单次 `enumerate_fallback()` 自身耗时

| 构建 | 进程内首次（冷） | 后续（热，3 次） | 对照：要求后端枚举 |
|---|---|---|---|
| debug | **977.7 ms** | 469.3 / 576.8 / 588.2 ms | 40.7 / 34.7 ms |
| fast-release | **1193.1 ms** | 456.1 / 491.8 / 525.4 ms | 21.8 / 18.3 ms |

→ 回退枚举比要求后端枚举贵 **约 25×**（fast-release 热态）；成本主体是 DX12/GL 后端加载，不是适配器数量。

### 3.3 A/B：通过路径去掉回退枚举后的整份全量检测

`run_check_with_timeout(DEFAULT_TIMEOUT)`，括号内为报告自报的 `duration_ms`：

| 构建 | 现状（收集回退） | 通过路径不收集 | 热态 Δ |
|---|---|---|---|
| debug | 856.8 ms（810）／720.5 ms（679） | 462.9（428）／193.6（148）／166.2（129） | **−527 ~ −554 ms** |
| fast-release | 1024.2 ms（990）／734.5 ms（691） | 470.8（417）／122.3（84）／114.5（69） | **−612 ~ −620 ms** |
| 进程内首次 Δ | debug −394 ms｜fast-release −553 ms | | |

### 3.4 结论口径

- 通过路径**每跑一次全量检测**白花 **0.55–0.62 s**（热态）／**0.39–0.55 s**（进程内首次）；
- 回退枚举占全量检测报告耗时的 **81%–88%**（热态）；
- 全量检测墙钟耗时：debug 720 ms → 166–194 ms；fast-release 734 ms → 114–122 ms（**约 4–6×**）；
- 收益场景：①启动门控缓存未命中时（用户可见的「启动慢」，UI-008 记录的启动路径正是这里）；
  ②设置页手动检测（「检查中…」每次少等 ~0.5 s，且这是**人一直在等**的交互）。

### 3.5 口径说明（防过度外推）

- 本机带虚拟显示适配器，回退枚举可能比单 GPU 机器更贵；但要求后端枚举只要 18–41 ms，
  说明 **wgpu 框架自身开销很小**，成本在驱动侧后端加载，与适配器数量弱相关；
- debug 与 fast-release 两种构建量级一致，故该结论不是「debug 才有的开销」；
- 本机是独显台式场景，老/弱驱动机器上 DX12/GL 加载更慢是常见现象，**不构成收益缩水**的理由。

## 4. 卡面缺陷（按严重度）

### P0-1「单一 `collect_fallback` 布尔量」与卡面自己的设计说明自相矛盾

卡面写：**「`fallback_adapters` 只在人看得到的场景（设置页手动检查、**失败报告**）收集」**，
同一条又写：**「启动门控路径传 `false`」**。

问题：布尔量是**检测开始前**传进去的，而「通过 / 失败且要弹窗」是**检测结束后**才知道的。
门控传 `false` ⇒ 失败路径也不再收集 ⇒ 警告窗（`device_gate.rs:145-152`）与原生提示框
（`:155`）失去「（检测到其他可用后端：Dx12，可能仍可运行）」这句**给人看的**文案，
`failure_detail` 的回退分支（`:283-296`）连同它的 2 个单测（`:311-332`）一起变成死代码。

两个可选落地：

| 选项 | 语义 | 代价 |
|---|---|---|
| **A（本报告推荐）** | 三态：`Never` / `OnFailure` / `Always`。门控 = `show_warning ? OnFailure : Never`；手动检查 = `Always` | 通过路径 **0 次**枚举（要省的都省了）；失败且要弹窗时保留 1 次 —— 这正是卡面写的「失败报告」场景 |
| B（卡面字面） | 门控一律 `Never`，手动 `Always` | 通过路径 0 次、失败路径也 0 次；但**回归一处用户可见文案**，且要删 `failure_detail` 回退分支 + 2 个单测。需卡主明确接受该文案回归 |

**注意**：选项 A 下，验收标准第 1 条需改写为「启动门控的**通过路径与静默失败路径**不再调用
`enumerate_fallback`」——因为默认配置（`show_warning=true`）下失败弹窗路径仍会调用一次，
且这一次正是被人消费的。若卡主要求「启动门控**完全**不调用」，请选 B 并同步改验收口径。

### P0-2 事件不携带指纹 → 卡面第 2 步没有数据源

`GpuCheckFinished { passed, detail }`（`events/window.rs:31-36`）里没有 `fingerprint`，
而 `spawn_gpu_compatibility_check`（`menu/window.rs:43`，**关联函数、无 `self`、在后台线程**）
是唯一能拿到 `report.fingerprint` 的地方。三种落地：

| 选项 | 做法 | 判定 |
|---|---|---|
| **A（推荐）** | 载荷加 `fingerprint: Option<String>`：改变体（`events/window.rs:31-36`）+ 改构造器（`:61-63`）+ 改唯一 emit 点（`menu/window.rs:51`） | ✅ 与既有约定一致（`Runner::pending_gpu_cache: Option<(Option<String>, bool)>` 就是「带指纹跨阶段传递」的先例，`src/runner/inner.rs:60`） |
| B | 在 `spawn_blocking` 里 `Storage::new()` 自己落盘 | ❌ **禁止**：`config.json` 是**整文件写**（`src/storage/config.rs:90-105`），而主线程持有同一个文件的另一份内存副本，`save_storage()`（`src/runner/inner/persist.rs:229-292`）随后会把它覆盖回去 → 回写丢失；且多一次读盘 |
| C | 全局静态槽暂存指纹 | ⚠️ 可行但绕开事件契约，与项目既有风格不符 |

**体积守卫已实测**（`crates/core/message/src/types/message.rs:253-260` 断言 `Message ≤ 200` 字节）：
加 `Option<String>`（24 字节）前后实测均为
`Message = 128`／`events::Event = 128`／`window::Event = 112`（`GpuCheckFinished` 变体尺寸 56 < 112，不构成最大变体），
**不触发体积守卫**。

### P1-1 回写必须走主线程的**同一个** `Storage` 实例

`RunnerInner.window_state.storage`（`src/runner/inner.rs:66-68`）就是主线程那份；
`menu/window.rs` 的处理器在主事件循环线程执行（`src/runner/menu.rs:19-22` 从全局事件缓冲取事件），
因此在这里 `persist_gpu_check_cache` 与 `save_storage()` 天然串行、无竞态。
另：`save_storage()` 只逐字段 patch `config.ui`（`persist.rs:229-288`），**不会**整体覆盖 `ui`，
所以它不会清掉刚写入的 `gpu_last_*`。

### P1-2「启动静默路径上这份诊断无人消费」不准确

- 静默失败路径：`device_gate.rs:129-132` 的 `tracing::warn!` 仍会渲染含回退后端的 `detail()`；
- 弹窗失败路径：`failure_detail()` 拼进警告窗（`device_warning.rs:77-84` → `Host::new_device_warning(..., detail)`）给人看。

准确表述应为：**通过路径上无人消费（只落进一行 info 日志）；静默失败路径只落进一行 warn 日志；
弹窗失败路径给人看**。这直接影响 P0-1 的选项选择。

### P2-1「约 20 行」偏低

实际改动面（含注释/文档/测试）：

| 文件 | 改动 |
|---|---|
| `crates/editor/gfx/src/device_check/check.rs` | 三态枚举 + 3 个入口函数拆 `_with` 变体 + `check_inner` 透传 + 3 处收集点 + 纯函数决策体 + 单测 |
| `crates/editor/gfx/src/device_check.rs` / `lib.rs:54-57` | 新类型与 `_with` 入口的再导出 |

### P2-2 失败回写会把上次的指纹清成 `None`（语义需在卡面写清）

`NoAdapter` / `Timeout` 两类失败的 `report.fingerprint` 是 `None`（`check.rs:103-108`、`run_check_with_timeout` 超时分支 `:50-52`），
回写会写 `gpu_last_fingerprint = null` + `gpu_last_passed = false`。
这与门控既有行为完全一致（`device_gate.rs:137` 同样写 `fingerprint.as_deref()`），
且 `cache_hit` 要求 `cached_passed == Some(true)`，所以后果只是「下次启动必然全量检测」——**可自愈**，不是缺陷。
但卡面所说的「共用同一缓存键，语义统一为『最近一次检测结果』」应把这条边界写进去。

## 5. 建议实施方案（修正后）

> ⚠️ **实施偏差（2026-10-03）**：正文建议「旧签名保留 = 永远收集」以避免误伤其它调用方；
> 实施时全仓核对确认**并无其它调用方**，故按五步纪律删除旧签名、改为**必填策略参数**
> （`check_gpu_support(when)` / `run_check_with_timeout(timeout, when)`），
> 理由与证据见实施记录 §3.2。其余方案与此处一致。

### 步骤 1：`check.rs` 按需收集（三态 + 可注入插桩）

```rust
/// 回退后端诊断的收集时机
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum FallbackDiagnostics {
    /// 从不收集（启动静默路径）
    Never,
    /// 仅在检测失败时收集（启动失败警告窗需要"可能仍可运行"提示）
    OnFailure,
    /// 始终收集（设置页手动检查：通过/失败都要展示与复制诊断）
    Always,
}

/// 决策与枚举分离：`enumerate` 可注入，使「通过路径不得触发枚举」成为**可确定性断言**的行为
fn fallback_adapters_with<F>(when: FallbackDiagnostics, passed: bool, enumerate: F)
    -> Vec<GpuAdapterSummary>
where
    F: FnOnce() -> Vec<GpuAdapterSummary>,
{
    match when {
        FallbackDiagnostics::Never => Vec::new(),
        FallbackDiagnostics::OnFailure if passed => Vec::new(),
        FallbackDiagnostics::OnFailure | FallbackDiagnostics::Always => enumerate(),
    }
}
```

入口拆 `_with` 变体，旧签名保持「永远收集」以避免误伤其它调用方：

```rust
pub fn check_gpu_support() -> GpuCheckReport { check_gpu_support_with(FallbackDiagnostics::Always) }
```

## 7. 风险与遗留

- **语义变更（需卡主确认）**：手动检测失败会覆盖此前 `passed=true` 的缓存 → 此后每次启动都会全量检测，
  直到某次检测通过。这是卡面想要的「刷新缓存」，且能修掉 §2.2 场景 2 的失败掩盖；但它是**行为变更**，
  应在实施记录里明确写出，避免被当成回归。
- **默认构建的口径**：本报告实测为 debug 与 fast-release；release（`lto=true`）未测，
  但成本在驱动侧，量级应一致。
- **阻塞枚举的遗留**：`enumerate_fallback` 是**无条件阻塞**调用（新建 `Backends::all` 实例 + 枚举），
  与 UI-008 处理的 `probe_adapter_fingerprints` 一样存在「驱动异常则挂起」的理论风险；
  本次按需收集顺带**缩小了它的触发面**（通过路径不再执行）。若卡面要顺手收口，
  可考虑后续把 `enumerate_fallback` 也收紧为「仅可在检测线程内调用」（同 UI-008 的 API 收紧手法）。
- **本卡不处理**：`enumerate_fallback` 内部仍会加载**要求后端**（Vulkan）适配器再过滤掉，
  若想再省几十毫秒，可改为只枚举非要求后端（`Backends::all() & !required_backends()`）——
  量级远小于本卡收益，建议不开卡。

## 8. 泛化检查（同类问题扫描）

| 检查项 | 结论 |

| 还有谁在用 `Backends::all()`？ | `crates/editor/gfx/src/context.rs:100-106`（主渲染上下文）与 `crates/audio/gpu-synth/src/gpu/context.rs:29`（LGS GPU 合成器）。**都是真实选适配器**，且用户点了「放我进去」后必须能落到 DX12/GL —— **不改** |
