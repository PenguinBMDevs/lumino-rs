# REF-SIMPLIFY-013：cpu-onionskin 示例与 lumino-cpu-onion 漂移清单

> 日期：2026-11-26
> 分支：`ref/cross-crate-single-source`
> 范围：`examples/cpu-onionskin`（独立 demo）与 `crates/editor/cpu-onion`（产品内核）
> 结论先行：两者是**同源分叉**，不是逐字复制。本期只记录漂移与可共享候选，
> 不做整目录合并；卡面提到的 −930 / −260 行在类型与签名对齐前不能计入收益。

## 1. 为什么要单独记录

示例的定位是**可独立运行的演示**：`examples/cpu-onionskin/Cargo.toml` 不依赖
`lumino-cpu-onion`，它重复实现了一套「索引 → 密度金字塔 → SIMD 栅格化」以展示
纯 CPU 方案。产品内核则承载编辑器所需的增量索引、区域渲染、输出合成等能力。
两边都在演进，函数签名和类型已经分叉；如果直接按行数估算合并收益，会在对齐阶段
被类型改造吃掉。因此先列清单，再决定哪些内核值得下沉。

### 4.1 `masked_fill_row` 等价性说明（本期唯一逐行核对的内核）

两边 AVX2 路径结构一致：8 路 `u32`、按 `owner <= owner_limit` 掩码、
`_mm256_maskstore_epi32` 写回，标量回退路径逐像素相同。差异集中在三处：

1. **统计开关**：示例 `count_coverage: bool` 为 `false` 时不统计；crate 始终统计
   并返回 covered。调用方对返回值的依赖不同。
2. **长度契约**：示例要求 `row.len() == owner.len()`（debug 断言）；crate 允许
   长度不等并按较短者截断。
3. **可见性**：示例 `pub`（demo 内部使用）；crate `pub(crate)`。

因此**不能**用「把示例的函数搬进 crate」来实现共享；需要先决定：
统计开关保留在哪一侧、长度契约取严格还是宽松、共享 crate 的可见性。
这三项都属于 API 决策，不适合在纯清理卡里顺带改。

## 5. 结论与后续顺序

1. **本期不合并**：示例保持独立可运行，crate 保持现有行为；不删除任何示例独有路径。
2. 若后续要做真正的单一源，建议顺序：
   1. 把 `SimdLevel` 与 `masked_fill_row`（含 `fill_row`）抽到一个无宿主依赖的
      `cpu-onion-kernel` 小 crate，先统一长度契约与统计开关；
   2. 示例与 `lumino-cpu-onion` 都改为依赖该内核，各自保留编排层；
   3. 再评估密度金字塔（`DensityLevel` 布局 + `keys` 维度）是否值得共享。
3. 行数收益：完成第 1 步预计共享 ~120–180 行（SIMD 原语 + 测试）；
   第 2 步（密度金字塔）需先对齐 `Camera`/`CanvasCamera` 与键数维度，收益重估，
   卡面的 −930 / −260 不可直接引用。
