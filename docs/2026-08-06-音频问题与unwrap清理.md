## 一、音频问题记录（单一权威源改造遗留）

### 问题 1：播放引擎跨线程 Arc 视图冲突（优先级：高）

**背景**：`EditorData.document` 已从 `Option<Arc<MidiDocument>>` 改为 `Option<MidiDocument>`（独占所有权），但 `PlaybackEngine` 在独立线程运行，需要 `Arc<MidiDocument>` 共享只读视图。

**现状**（Commit 1b 后的降级路径）：

```rust
// crates/ui/src/state/midi_state.rs
pub struct MidiState {
    /// 播放引擎/导出跨线程共享视图（恒 None，降级路径）
    pub document: Option<Arc<MidiDocument>>,
}
```

- `PlaybackEngine::set_document(Arc<MidiDocument>)` 接口保留，但 UI 侧 `midi_state.document` 恒为 `None`
- 播放**当前音轨**正常（走 `set_current_track_notes(Vec<NoteEvent>)` 数据拷贝）
- 播放**其他音轨**、音频/视频导出的"内存模式"走降级路径（数据可能缺失或需重建）

**根因**：同一份数据无法同时 owned（EditorData 独占）+ Arc（跨线程共享）且禁止深拷贝（黑乐谱 356MB）。

**候选方案**（三选一，需决策）：

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| A. 内部 Arc 化 | `MidiDocument.notes` 每轨改为 `Arc<[NoteEvent]>`，EditorData 持有 `Arc<MidiDocument>` 但通过 `Arc::get_mut` 写时复制（单引用时 O(1) 原地写） | 跨线程零拷贝共享；编辑时单引用无拷贝 | 需改造 MidiDocument 内部结构；与阶段二 ChunkedList 分块天然契合（分块本身可 Arc 共享） |
| B. 播放线程借 UI 文档 | 播放引擎改为持有 UI 线程句柄，每帧经 channel 拉取当前轨数据 | 无需改 document 结构 | 每帧拷贝开销；播放引擎与 UI 生命周期耦合 |
| C. 快照通道 | 编辑提交时把受影响轨道经 channel 推送给播放引擎（事件驱动） | 增量传输，无全量拷贝 | 需实现轨道级 diff 协议；复杂度高 |

**推荐**：方案 A。理由：
1. 与阶段二 ChunkedList 分块改造天然契合——分块后每块本身是 `Arc<Vec<T>>`，编辑只 COW 被修改块
2. `Arc::get_mut` 在 EditorData 独占（无其他引用）时 O(1) 原地写，零拷贝
3. 播放/导出线程持 Arc 视图，与编辑线程互不阻塞

**依赖**：本问题修复依赖阶段二（ChunkedList）落地，建议在阶段二完成后一并处理。

### 问题 3：`total_ticks` 不随编辑更新（优先级：低）

**现状**：`MidiDocument.total_ticks` 在加载时计算，编辑插入/删除音符后不刷新。影响：
- 走带视图滚动范围（`arrangement_max_tick_end` 已有缓存按 `track_notes_gen` 失效，可补偿）
- 导出时 duration 计算（导出路径重新遍历 document，实际不依赖 total_ticks）

**建议**：阶段二 ChunkedList 落地时，`replace_track_notes` / `insert_note` 内增量维护 `total_ticks`（O(1) max 比较），消除不一致隐患。

### 任务定义

**目标**：消除测试代码中的裸 `unwrap()`，替换为可读的断言/错误传播，提升失败诊断质量。

**验收标准**：
- [ ] 测试代码 `unwrap()` 数量归零（`#[cfg(test)]` + `tests/`）
- [ ] 生产代码 `unwrap()` 逐处审查：保留合理处（加注释说明）、替换危险处
- [ ] 全部替换使用 `expect("有意义的失败上下文")` 或 `?` 传播
- [ ] `cargo clippy --all-targets` 零新增 warning
- [ ] `cargo test --workspace` 全绿

**替换模式**：

| 原代码 | 替换为 | 理由 |
|--------|--------|------|
| `x.unwrap()`（测试断言） | `x.expect("断言上下文：期望 Some 实际 None")` | 失败时输出上下文，快速定位 |
| `x.unwrap()`（测试且返回 Result） | `x?` | 传播错误，测试自动失败 |
| `Option::unwrap()` 后紧接断言 | `assert!(x.is_some(), "...")` 或 `let Some(v) = x else { panic!("...") }` | 显式断言 |
| `Result::unwrap()`（生产代码） | `match` / `map_err` / `?` | 生产错误必须可传播 |

**执行顺序**（按风险递增）：
1. **测试代码批量替换**（机械性，~220 处）：`unwrap()` → `expect("...")`，上下文文案从周围断言/变量名生成
2. **生产代码审查**（~80 处，逐处人工判断）：
   - `async_commit.rs` / `async_commit_streaming.rs` 的 25 处（有 `#[allow(clippy::unwrap_used)]` 标注的测试模块，先确认是测试还是生产）
   - `crates/ui/src/sidebar.rs` 7 处
   - `crates/ui/src/host/render/note_delta.rs` 5 处
   - `crates/export/src/project.rs` 5 处
   - `crates/note-core/src/batch_edit.rs` 5 处
   - 其余零星
3. 全量验证

**注意事项**：
- `#[allow(clippy::unwrap_used)]` 已在部分测试模块标注（note_store_ops/tests.rs），清理后删除 allow 标注
- 测试代码的 `expect` 文案用中文，与项目注释风格一致
- 生产代码 `unwrap()` 若确认不可达（如 `OnceLock::get().unwrap()`），保留并加 `// 不可达：...` 注释，避免为改而改
- 不改变任何业务逻辑，纯替换
