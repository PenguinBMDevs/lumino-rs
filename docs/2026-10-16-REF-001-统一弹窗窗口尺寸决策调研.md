# REF-001 统一弹窗窗口尺寸决策 · 调研报告

- 调研日期：2026-10-16
- 调研对象：卡「REF-001：统一弹窗窗口尺寸决策——打开时自动测量内容自然尺寸，去除 per-type 硬编码」
- 分支：`dev`（本调研仅新增本文档；工作区另有一处**先于本次会话**存在的改动：根 `Cargo.toml` 的 `[profile.fast-release]`，mtime 2026-10-14 23:10，与本卡无关）
- 调研方式：**源码逐条对质 + 独立探针实测**（iced 0.14 布局源码 / winit 0.30.13 源码 / 仓库对话框三阶段链路 / 17 种 dialog 视图逐类审计），探针在 `%TEMP%\iced_measure_probe` 独立 crate 复现（附录 A），共 12 组用例
- 结论：**卡面方向成立，但「测量一次自然尺寸」在 iced 0.14 的语义下有 3 个硬约束卡面没覆盖**——(1) 宽度对「文本 / 文本输入 / 进度条」类内容会被 `Limits::max` 自证（测得宽 = 你给的 max，不是内容宽）；(2) 含 `Fill` 主轴区域（滚动区 / 撑位占位）的对话框，测出的**高度必然等于 cap**，且其后的兄弟节点被压成 0；(3) 窗口尺寸落地必须在窗口"入册"之后，否则 `Resized` 会被误路由给主窗口，**主窗口下次启动会套用对话框的尺寸**。因此卡面 5 条方案里 **2 条可删、1 条需大改**，另有 **4 个 P0 + 3 个 P1** 需补。

> ## ⚠️ 实施后修正（2026-10-16，必读）
>
> 本报告已按实施落地，其中 **3 处判断被实测推翻**，以
> [实施记录](2026-10-16-REF-001-统一弹窗窗口尺寸决策实施记录.md) 为准：
>
> 1. **§1.2 探针用例 B / §1.4 结论 1「压缩测量可行且精确」不成立**：
>    探针树里没有文本。真实视图一旦含文本，**两轴同时压缩会把宽度压成 0**
>    （iced flex pass 2 用初值为 0 的 `cross` 当子节点 `max_width`），文本随即按 0 宽
>    折行 ⇒ 高度虚高（实测：保存确认提示文字 208px、内存监控说明 337px，
>    4 类对话框高度直接顶到工作区上限 1040）。
>    **修正口径：宽度必须是硬约束（`min = max = 声明宽度`），只压缩高度。**
> 2. **§1.4 结论 3「每个 Fill 主轴区域声明 preferred 上限」被更省的方案取代**：
>    改为「**窗口级高度上限**（声明上限 ∩ 工作区）+ 视图保持纯 `Fill`」。
>    语义等价，但零视图改动，且用户放大窗口时滚动区仍随之增长。
>    原计划的测量期开关模块（`height_cap` / `flex_spacer`）**写完即删**。
> 3. **新增第四类「钉死高度」**：含滚动区的对话框（设置 / 工程设置 / 云文件浏览 /
>    画刷设置）**连高度都不可信**——滚动区自己决定布局，压缩测量时其外层被压成 0
>    （实测设置面板菜单内容真实高 524，测量时外层 200×0，整块菜单丢失）。
>    这 4 类改为 `min_height = max_height` 钉死（= 原值），不依赖测量。
>
> 另：§1.4 结论 4「宽度不可测量驱动」与 §5.1 决策 D3（宽声明 / 高测量）**成立且已落地**。
> 第二轮补充：宽度从「纯声明」升级为**声明区间 + 自动求最小可用宽度**——判据不是
> 「横向溢出」（iced 不会溢出：`resolve(Fixed(n))` 会做 `n.min(max)`，过窄时控件被
> **压窄**；实测声明 `Fixed(120)` 的输入框在 247 宽度下只有 49），而是「与两个超宽
> 参考布局对比，内容驱动节点是否被压窄」。6 类对话框的宽度已完全自动，其余因内容是
> 流体或长文本需固定折行宽度而保留声明值。详见实施记录 §4.4。

## 0. 结论速览

| # | 卡面断言 / 隐含前提 | 源码或实验事实 | 判定 |
|---|---|---|---|
| 1 | `window.rs` 为 17 种 DialogType 各硬编码一组 (width, height) | `dialog/src/window.rs:53-72` 的 match 共 **17 个有效分支**（`DialogType` 含 `None` 共 18 变体，`ui/src/state/root_state.rs:20-58`），每个分支返回 `(width, height, title, resizable)` | ✅ 与卡面一致 |
| 2 | 视图根为 `Fill` ⇒ 内容无自然尺寸反馈通道 | 17/17 个视图根都是 `Fill×Fill`，**没有任何视图声明自身尺寸**；但 **`Fill` 根不是障碍**（见 #3） | ✅ 现象对，⚠️ 归因不完整 |
| 3 | 需要 probe widget 包一层、用 Shrink limits 量自然尺寸 | **机制不需要 probe widget**：`Limits::width(Length::Shrink)` 只置 `compression` 标志（`iced_core-0.14.0/src/layout/limits.rs:55-71`），`resolve()` 在 compression 下把 `Fill` 退化为 intrinsic（`limits.rs:160-170`）。探针实测 B：同一棵「根 Fill×Fill」的树，普通 limits → `800×600`（=窗口），压缩 limits → **`244×64`（=内容 220×40 + padding 12×2）** | ✅ 机制成立，❌ **probe widget 可删** |
| 4 | 需把 17 个视图根由 Fill 改 Shrink | 压缩标志由**第一个施加 Shrink 约束的祖先**置位并向下继承，与根声明什么无关；且 `Fixed` 会把该轴 compression 复位（`limits.rs:59-66`），固定尺寸子区域内的 Fill 仍正常铺满（实测 D） | ❌ **该方案可删**，但**替代品不是"零改动"**（见 #5/#6） |
| 5 | 「打开时测量一次」即可，尺寸对内容自适应 | **只有 4/17 个对话框**（custom_precision / speed_change / batch_edit / save_confirm）是 Fixed 驱动且静态，能直接靠压缩测量得到正确尺寸；**7 个**因含 `Fill` 主轴区域而高度必量到 cap；**3 个**因含零内在控件（text_input / progress_bar）宽度会塌到 0 | ⚠️ **测量法只对一部分对话框成立**，其余需视图侧补「测量友好」约束 |
| 6 | 尺寸可从内容自下而上推出 | `Text` 以 `limits.max()` 为排版宽再取 `min_bounds`（`iced_core-0.14.0/src/widget/text.rs:313-332`）⇒ 长句按 max 折行、测出的宽 ≈ max。**"自然宽度"对文本密集内容不是良定义量**：max 给 cap 则测得 cap，max 给 ∞ 则单行宽可超屏。宽度必须由**声明的偏好宽度**决定，不能靠测量 | ❌ **宽度不可测量驱动**，必须声明 |
| 7 | 「超长内容由各 dialog 自行套 scrollable」 | 压缩测量下 `scrollable` 滚动轴传 `f32::INFINITY`（`iced_widget-0.14.2/src/scrollable.rs:449-464`）→ 内容全长被 cap 夹住；且压缩下 flex 第一轮就布局 Fill 主轴子节点并递减 `available`（`iced_core-0.14.0/src/layout/flex.rs:111-141`），第三轮被跳过（`flex.rs:191-196`）⇒ 实测 I：`column[固定20, scrollable(Fill), 固定40]` → 测得 `600`（=cap），**末位 40 的"底部按钮行"被压成 `(0,0)`** | ⚠️ **必须补「Fill 主轴区域显式上限」**，否则量到 cap 且兄弟归零 |
| 8 | 「尺寸钳制上限（不超工作区）」 | **winit 0.30 不提供工作区 API**（`winit-0.30.13/src/monitor.rs:107-167` 只有 name/size/position/scale_factor/video_modes；`rcWork` 仅内部 `windows/event_loop.rs:1162-1181` 用于无边框最大化），全仓库零 Win32 工作区代码 ⇒ 必须自研 | ⚠️ **需新增平台代码** |
| 9 | `visible:false` → 测量 → resize → 显示，无闪烁 | 时序可行（阶段 3 到首次 present 之间零帧），**但 resize 请求不能在 `initialize_ui` 内发**：那时窗口未入册（`dialog/src/manager/lifecycle.rs:145-148` 才 insert），`Resized` 会被误路由给**主窗口**（`src/runner/lifecycle/handler.rs:150-157` + `dialog/src/manager/queries.rs:14-16`），并写进主窗口持久化的 `w/h/x/y`（`src/runner/window_manager.rs:150-159,190-201`） | ⚠️ **顺序必须重排**（P0-1/P0-2） |
| 10 | `window.rs` 无 per-type 尺寸 ⇒ 新增 DialogType 无需填数字 | 可达，但仍需 (a) 统一「种子尺寸」（隐藏窗口也要非零 client 面积，`initialize.rs:21-23` 零尺寸直接报错）、(b) 每个对话框的**偏好宽度**（文本折行所需）、(c) 每个 Fill 主轴区域的**偏好长度**（否则高度 = cap） | ⚠️ **数字没消失，是从 window.rs 搬到视图层**（见 §6 三路线） |
| 11 | resizable 的 5 个 dialog 仍可手动调整 | `with_resizable`（`window.rs:78`）与 Win32 拉伸边框（`platform/windows.rs:120-144`）都与尺寸数值解耦 | ✅ 无风险 |
| 12 | VideoExport 去最大化按钮（UI-004）不变 | 按钮掩码是独立表达式（`window.rs:82-86`），拆出四元组后原样保留 | ✅ 无风险 |
| 13 | 多显示器场景下 resize 后窗口位置正常 | 对话框**无 owner、无位置**（`window.rs:49,74-86`，`_parent_window` 被忽略；winit `CreateWindowExW` 四个参数全 `CW_USEDEFAULT`，`windows/window.rs:1366-1381`，且无 owner 时被置 `ON_TASKBAR`，`:1333-1342`）⇒ 系统层叠默认放置，可能与主窗口不在同一显示器，**初始 scale factor 也取放置那块屏**；`resize` 本身不移动窗口（`SWP_NOMOVE`，`windows/window_state.rs:465-479`） | ⚠️ **需新增 owner/定位/按目标屏 DPI 换算** |

**一句话**：方向对、机制通，但「自动测量」只能解决**高度**（且要在视图侧把 Fill 主轴区域加上限之后）；**宽度必须由视图声明**。改造重心因此从 `window.rs` 转到**17 个视图的"可测量化"**——这才是本卡真实的工作量。

## 1. 机制验证

### 1.1 compression 语义链（源码）

```
Limits::width(Length::Shrink)      → 只置 compression.<axis> = true，不动 min/max   (limits.rs:55-71)
Limits::width(Length::Fixed(n))    → min=max=n 且 compression.<axis> = false          (limits.rs:59-66)
Limits::resolve(Fill, ..)          → compression 为 true 时走 intrinsic 分支，
                                     再 .min(max).max(min)                            (limits.rs:160-188)
UserInterface::build(root, bounds) → Limits::new(Size::ZERO, bounds)，**不带 compression**(iced_runtime-0.14.0/src/user_interface.rs:104-108)
                                     ⇒ 渲染路径永远铺满窗口；测量必须另起一次 layout
UserInterface 不暴露布局节点       → 只能 into_cache / relayout / update / draw      (user_interface.rs:582-590)
```

### 1.3 三个「零内在 / 自证」控件（逐条亲验）

| 控件 | 源码 | 压缩下的行为 | 受害对话框 |
|---|---|---|---|
| `TextInput` | `limits.resolve(self.width, height, Size::ZERO)`（`iced_widget-0.14.2/src/text_input.rs:311-312`） | `width(Fill)` ⇒ intrinsic=0 ⇒ **宽 0** | project_settings（4 处）、collaboration Connect/RoomActions（6 处）、cloud_dialog 连接面板（6 处）、cloud_browser 新建/重命名（2 处） |
| `ProgressBar` | 默认 `length: Length::Fill`（`progress_bar.rs:83`）+ `layout::atomic(limits, w, h)`、`atomic` 传 `Size::ZERO`（`progress_bar.rs:164`、`iced_core-0.14.0/src/layout.rs:117-126`） | **宽 0**、高 = girth | export_progress、video_export overlay |
| `Text` | `bounds = limits.max()` → `paragraph.min_bounds()`（`iced_core-0.14.0/src/widget/text.rs:313-332`；默认 `width=Shrink`、`Wrapping::Word`，`:292`、`:186-188`） | 长句按 cap 折行 ⇒ **测得宽 ≈ cap**（自证） | draw_settings（`:31-34`，注释就写着"让长句在窗口宽度内自动折行"）、memory_monitor（`:86-90`）、recover_track（长 hint）、settings 各页长文案 |

另：`space().width(Length::Fill)` 推位占位（settings_dialog `:56`、batch_edit `:206`、memory_monitor `:132/:155`、recover_track `:338`）与 `space().height(Length::Fill)` 撑位（draw_settings `:49`）在压缩下都是**零内在**——前者塌了无害（实测 C），后者会吃光高度并压死后续兄弟（实测 I）。

### 1.4 四条硬结论

1. **压缩测量可行且精确**（B/D/G1/G2），但**前提是内容有内在尺寸**；`text_input`/`progress_bar`/`Fill` 占位没有。
2. **测量必须用真实字体渲染器**（F 证明 null 渲染器量不出文本）；仓库已有先例：运行时用 `Host` 自带的 `render_ctx.renderer`（`ui/src/host/render_ctx.rs:45-47,152`），单测用 `ui/src/root/draw_toolbar.rs:578-609` 的 `headless_renderer_with_font`。
3. **高度可测量驱动，条件是每个 Fill 主轴区域都有显式上限**（G1/G2 是正解，E/I 是反例）。
4. **宽度不可测量驱动**：文本折行以 max 为宽（自证），输入框/进度条 intrinsic 恒 0。宽度只能由视图声明，测量至多用于**校验溢出**。

### 2.2 三阶段真实时序（注释与实现不符）

`manager/lifecycle.rs:88-89` 注释写「每帧最多推进一个阶段」，实际是**同一帧连做阶段 1+2**（块 A `:102-120` 之后紧接着块 B `:123-131`），阶段 3 落在下一帧。故：

- 从「窗口已创建（hidden）」到「UI 就绪」**必然跨一个事件泵迭代**，期间窗口既不在 `dialogs`、也已不在 `pending`，只存在于 `initializing`（`manager.rs:39-47` 三个容器）。
- 这个「归谁管」的空档是本卡最重要的隐性战场（P0-1）。
- 阶段 3 内 `initialize.rs:50` 现场重读 `inner_size()` 并用它建 Host viewport ⇒ **若在阶段 3 之前把尺寸定好，viewport 自动正确**；阶段 3 之后再改尺寸则依赖 `Resized` 回程。

## 3. 卡面 5 条方案逐条判决

| 卡面条目 | 判决 | 依据 |
|---|---|---|
| **1. 测量探针**（dialog 视图根包一层 probe widget，layout 时用 Shrink limits 量自然尺寸） | ❌ **删除** | 探针的唯一作用是「让某次 layout 带上 compression」，而测量入口自己传压缩 limits 即等价（B/C/D）。引入 probe 反而污染渲染路径（渲染时压缩则内容不铺满窗口；只在测量时压缩则 probe 需要状态开关，复杂度更高） |
| **2. 显示时序改造**（`set_visible(true)` 移到「首次测量完成」之后） | ⚠️ **保留，但必须加两个约束** | (a) resize 必须在**窗口入册之后**（否则 `Resized` 误路由给主窗口，P0-1）；(b) 测量必须在**内容注入之后**（RecoverTrack 条目在入册后同帧才注入，P0-2）。二者合起来唯一解：**「入册后的首次 redraw」做测量 + resize + 显示** |
| **3. dialog 视图根由 Fill 改 Shrink** | ❌ **删除，并以「可测量化」替代** | 根 Fill 不影响测量（B）。真正要做的是给**零内在控件**补宽度、给 **Fill 主轴区域**补上限（§5-P0-3）。改根声明对测量零收益，却制造 17 个文件的无效 diff |
| **4. 尺寸钳制上限（不超工作区）** | ✅ **保留，但工作量被低估** | winit 无工作区 API，仓库零 Win32 工作区代码（P0-4）；「多显示器位置正常」还需 owner/定位/按目标屏 DPI |
| **5. 保留 per-type 非尺寸元数据** | ✅ **保留** | 三者与尺寸完全解耦（`window.rs:74-86`），UI-004 掩码是独立表达式 |

## 4. P0 / P1 清单

### P0-1 尺寸落地必须在「窗口已入册」之后（否则污染主窗口 + 自身 viewport 停在旧尺寸）

- **判定口**：`dialog/src/manager/queries.rs:14-16` `is_dialog_window()` 只查 `dialogs`；`initializing` 中的窗口不在其中（`manager/lifecycle.rs:145-148` 才 insert）。**分派口**：`src/runner/lifecycle/handler.rs:150-157`，「不是对话框 → 交给主窗口」。
- **后果 1（验收直接失败）**：在 `initialize_ui` 内 `request_inner_size`，回程 `Resized` 被主窗口消费，对话框自己的 `Host::resize` 不会被调用（`dialog/src/window/event.rs:13-21` 只在命中对话框时才走）⇒ 首帧仍按旧尺寸渲染，「无尺寸跳变」不成立。
- **后果 2（既有缺陷，会叠加）**：该 `Resized` 经 `src/runner/window_manager.rs:150-152 → 190-201` 写入**主窗口**持久化状态 `storage.ui_state.w/h`，`Moved` 写 `x/y`（`:153-159`），最终由 `src/runner/inner/persist.rs:354` 落盘。也就是说**今天**每次开对话框，窗口创建期的首个 `Resized/Moved` 就已经在污染主窗口尺寸/位置（下次启动可能套用对话框尺寸）。同源副作用还包括 `window_manager.rs:166` 无条件把该窗口事件喂进**主窗口**的 iced 事件队列。
- **建议**：(a) `DialogManager` 增「窗口归属认领」集合，阶段 1 建窗即认领，`is_dialog_window` 改查它（**不改动** `has_dialog_type` / `is_open_or_pending` / `first_dialog_id_of_type` 的「已就绪」语义）；(b) 尺寸落地时同步 `ui.resize` / `gfx.resize`（用回读的 `inner_size()`），不把正确性押在事件回程上。

### P0-2 测量时点 = 「入册后的首次 redraw」，不是 `initialize_ui` 末尾

- RecoverTrack 条目由 `handler.rs:237`（`about_to_wait_init_dialogs` 之后）经 `try_fill_recover_track_entries`（`src/runner/menu/window/track.rs:200-236`）注入 ⇒ 条目到达时间**晚于** `initialize_ui`。在 `initialize_ui` 内测量会量到「空列表」（视图只剩 80px 占位）→ 窗口过小 → 违反验收 1。
- **建议**：测量放进 `DialogManager::update()` 的首次遍历（`manager/lifecycle.rs:178-192`，由 `handler.rs:252` 驱动）——此时窗口已入册、同帧注入已完成、且尚未 `set_visible`（对用户不可见）。
- **附加成本**：`Root::view()` 会多构建一次（Settings 首次触发字体列表懒加载 `ui/src/root/view/overlays.rs:154-160`；MemoryMonitor 多捕一次快照）。需在实施记录里标注测量耗时。

### P0-3 尺寸语义三件套 + 视图「可测量化」

由实测 E/I 与 §1.3 直接推出：

```
宽度  = clamp(视图声明的 preferred_width , floor , 工作区 cap)     ← 不可测量驱动（TextInput/Text/ProgressBar）
高度  = clamp(measure_intrinsic(cap) ,  floor , 工作区 cap)        ← 可测量驱动
        其中每个 Fill 主轴区域必须包一层 container.max_height(preferred)
```

落地清单（每类改动都有实测支撑）：

| 改动 | 理由 | 实测依据 |
|---|---|---|
| `Fill` 主轴区域（scrollable / 撑位 `space().height(Fill)`）外包 `container(...).max_height(pref)` | 否则高度 = cap，且其后兄弟被压成 0 | E（600=cap）、I（末位 40 → `(0,0)`）、G1/G2（正解：420 / 320） |
| `text_input().width(Fill)` → `min_width(...)` 或显式宽度 | intrinsic 恒 0 ⇒ 宽 0 | `text_input.rs:311-312` |
| `progress_bar` → `length(Fixed(n))` / `min_width` | intrinsic 恒 0 ⇒ 宽 0 | `progress_bar.rs:83,164` + `layout.rs:117-126` |
| 长文案所在容器给显式宽度 | 否则测得宽 ≈ cap（自证） | `text.rs:313-332`；draw_settings `:31-34` 注释即"Fill 折行" |
| 统一下限 `MIN_DIALOG_SIZE` | 纯 Fill 无内在宽度内容会量出 0 | E（宽 0） |
| 非原生标题栏时高度须 +30px 且标题栏是最小宽度来源 | `view_dialog` 会前置 `titlebar.view_popup`，其高 `Fixed(30)`（`ui/src/titlebar.rs:126`），拖动区 `container(space().width(Fill))`（`:117`）在压缩下宽归零 | 源码 |

### P0-4 工作区上限与多显示器定位必须自研（Win32）

- winit 0.30 无工作区 API；`_parent_window` 被忽略（`dialog/src/window.rs:49`）；`CreateWindowExW` 位置参数全 `CW_USEDEFAULT`（`windows/window.rs:1366-1381`），无 owner 时置 `ON_TASKBAR`（`:1333-1342`）。
- **初始 DPI 陷阱**：窗口 scale factor 取创建时所在显示器（`windows/window.rs:1137-1138`）。主窗口在 150% 副屏而对话框落到 100% 主屏时，Host viewport 按 1.0 构建（`initialize.rs:50` + `builder.rs:37-38`），测量出的逻辑尺寸会换算出偏小的物理尺寸。
- **建议**：`MonitorFromWindow + GetMonitorInfoW().rcWork`（或 `SystemParametersInfoW(SPI_GETWORKAREA)`）取工作区；设 owner（`WindowAttributesExtWindows::with_owner_window`，`winit/src/platform/windows.rs:454-467`）；按主窗口所在显示器居中（`set_outer_position`，仓库当前零使用）。

### P1-1（既有 · **已并入本卡，非阻塞 TODO**）`ScaleFactorChanged` 无 viewport 重建路径

`dialog/src/window/event.rs:12-31` 与 `ui/src/host/event/window/events.rs:87-117` 都没有该分支，只把事件转成 iced `Rescaled` 入队。布局用旧 `viewport.logical_size()`（`ui/src/host/render/ui.rs:48`），坐标换算用新 `scale_factor()`（`events.rs:43`）。Windows 通常靠随后的 `SetWindowPos → WM_SIZE → Resized` 兜住，但 windowed-maximized 时 winit 令物理尺寸不变（`windows/event_loop.rs:2237-2238,2273-2280`）⇒ 可最大化对话框（Settings/ProjectSettings/BatchEdit/RecoverTrack/CloudBrowser）可能永久停留在旧 DPI。**与验收最后两条直接相关。**

### P1-2（既有 · **已并入本卡，非阻塞 TODO**）`UiState.w/h` 物理写、逻辑读

写：`window_manager.rs:150-152,190-201`（原样存 `PhysicalSize`）；读：`:296-302`（当作 `LogicalSize`）。非 100% DPI 下主窗口尺寸逐次放大。与 P0-1 的污染叠加在同一对字段上。

### P1-3（既有 · **已并入本卡，非阻塞 TODO**）注释与实现不符

`manager/lifecycle.rs:88-89` 声称「每帧最多推进一个阶段」，实际同帧连做 1+2。照注释推理「测量发生在哪一帧」会算错。

## 5. 设计路线与决策（已定 D3）

| 路线 | 做法 | 代价 | 证据结论 |
|---|---|---|---|
| **D1 纯测量驱动**（卡面原意） | window = `measure(compression, cap)` | 需先做 §P0-3 全部「可测量化」；即便如此，含长文案的对话框宽度仍 ≈ cap（自证） | ❌ **宽度侧结构上不可行** |
| **D2 纯声明驱动** | 每个视图导出 `preferred: Size`，window = `clamp(preferred, floor, cap)`；测量降级为**溢出校验** | 数字仍在，只是从 window.rs 搬到视图层；"内容改了必须改数字"的痛点未消除（但校验会**主动报错**，不再静默裁剪/留白） | ⚠️ 最稳，但没兑现卡面「无需填数字」 |
| **D3 混合（✅ 已采纳，见 §5.1）** | **宽**：视图声明 `preferred_width`（文本按此折行）；**高**：测量驱动（Fill 主轴区域声明 `max_height(pref)`、clamp 到 cap）；测量结果用于**溢出校验/日志**（debug 断言 + puffin） | 每个对话框仍要一个宽度（+ 滚动区偏好高），但高度侧完全自动；新增 DialogType 在**高度**上无需填数字 | ✅ **与 iced 语义一致**（高度可从内容推、宽度不能） |

### 5.1 决策记录（2026-10-16）

| 项 | 决定 | 影响 |
|---|---|---|
| 尺寸口径 | **采纳 D3 混合**：宽度由视图声明 `preferred_width`，高度由测量驱动（Fill 主轴区域声明 `max_height(pref)`），测量另承担溢出校验 | 卡面验收第 1 条改口径；「新增 DialogType 无需填尺寸数字」改为**高度侧达成、宽度侧必须声明** |
| P1-1 / P1-2 | **并入本卡范围，但记为非阻塞 TODO**（先完成主线阶段 A–F，除非阻塞否则不先动） | 见 §8 阶段 G |

**改口径后的验收表述**：窗口宽度 = 视图声明的偏好宽度（新增类型必须声明）；高度 = 内容自然高度（滚动区按偏好上限夹取），整体不超过工作区。

## 8. 建议实施方案（分阶段，每阶段独立可验收）

### 阶段 A —— 先修既有缺陷（P0-1）
1. `DialogManager` 增 `claimed: HashSet<WindowId>`；阶段 1 建窗即认领，关闭时释放。
2. `is_dialog_window()` 改查 `claimed`；`has_dialog_type` / `is_open_or_pending` / `first_dialog_id_of_type` 语义不动。
3. 单测：已建窗未就绪 ⇒ `is_dialog_window` true、`has_dialog_type` false（参照 `manager/queries.rs:139-158` 测试风格）。

### 阶段 B —— 测量入口（零渲染路径改动）
4. `lumino-ui` 新增 `Host::measure_content_size(cap: Size) -> Size`：`let Host { root, render_ctx, .. } = self;` → `root.view()` → `Tree::new` → `layout(&mut tree, &mut render_ctx.renderer, &Limits::with_compression(Size::ZERO, cap, Size::new(true, true)))` → `node.size()`。
5. 单测：把探针 B/C/D/E/G1/G2/I 仓库化；无 GPU 适配器时跳过（`draw_toolbar.rs:578-609` 先例）。

### 阶段 C —— 视图「可测量化」（本卡真正的工作量，逐类清单见 §6）
6. 5 个 ❌ 类：`text_input` 加宽（min/Fixed）、`progress_bar` 加长、长文案容器加宽。
7. 6+ 个 ⚠️ 类：Fill 主轴区域（scrollable / 撑位占位）外包 `container(...).max_height(pref)`。
8. 定义统一 `MIN_DIALOG_SIZE` / `SEED_DIALOG_SIZE`；声明每类的 `preferred_width`（D3）。

### 阶段 D —— 去硬编码 + 时序重排
9. `window.rs:53-72` 四元组拆成 `(title, resizable)`（+ 掩码），尺寸交给测量/声明。
10. `initialize_ui` 末尾的 `set_visible(true)`（`:163`）改为不显示；新增 `DialogWindow::apply_measured_size(target)`：`request_inner_size` → 回读 `inner_size()` → 同步 `ui.resize`/`gfx.resize` → `set_visible(true)`。
11. 在 `DialogManager::update()` 首次遍历执行（`measured: bool` 门控，幂等）。
12. 回退：测量失败用种子尺寸并**必须显示**。

### 阶段 E —— 工作区 + 多显示器
13. `dialog/src/platform/windows.rs` 增工作区查询，其它平台退化为 `MonitorHandle::size()`。
14. 用上 `_parent_window`：owner + 居中 + 按目标屏逻辑工作区算 cap + 按目标屏 DPI 换算。

### 阶段 F —— 点检
15. 17 类逐个打开截图；resizable 5 类拉伸；VideoExport 最大化按钮消失；100%/150% 混合双屏。
