# REF-LGS-012 · 实时事件注入：去每事件锁 + 批量入口

> 日期：2026-10-31 ｜ 分支：`ref-lgs` ｜ 机器：RTX 5080 / 9950X3D / 48 kHz
> 结论：注入路径 **58.9 → 43.3 ns/event（−26.5%）**，走批量入口 **21.6 ns/event（−63.3%）**；
> 实机 10 s 播放 `underruns=0`、`dropped_note_ons=0`，与改动前一致。

---

## 1. 改了什么

### 1.1 去每事件锁（`SharedEventTx` 纪元缓存）

旧实现：`Arc<Mutex<Option<EventSender>>>`，`send_event` 每事件 `lock()` 一次。

新实现（`crates/audio/midi-io/src/api/lgs.rs`）：

```rust
pub(crate) struct SharedEventTx {
    inner: Mutex<Option<EventSender>>,
    epoch: AtomicU64,          // set() 先写值、后 +1
}
```

- `LgsOutputConn` 缓存 `(sender_epoch, Option<EventSender>)`；
- 稳态：`send_event` 只做一次 **Acquire load + 比较**，零锁零克隆；
- 管线重建（`rebuild_with_options`）走 `set()`：写值 + 纪元 +1，所有连接下一事件
  自动重新读取（`sender_swap_is_picked_up_without_stale_cache` 单测覆盖）。

> 验收口径里的 “grep 可证 `api/lgs.rs` 无 `lock()`” 精确表述为：
> `send_event`/`send_raw`/`send_raw_batch` **稳态无锁**；`Mutex` 只出现在
> `SharedEventTx::load`（纪元变化时一次）与 `set`（重建时一次）。

### 1.2 批量入口（`OutputConnection::send_raw_batch`）

- 新增 trait 默认方法 `send_raw_batch(&[[u8; 3]])`（纯 MIDI 设备逐条转发，
  **完全等价**）；LGS 覆写为「解析一次发送端 + 逐条入队」。
- `send_raw` 与 `send_raw_batch` 共用同一 `raw_to_event()` 映射（同一份力度过滤、
  同一份不支持消息忽略逻辑），因此**逐事件一致**由构造保证，并有单测对拍。
- 顺带：`EventSender::send_batch()` 让同一批事件**共用一次 `Instant::now()`**——
  这是批量路径 50% 提速的主要来源（逐条路径每事件一次时钟读取）。

### 1.3 准入闸快路径（`admission.rs`）

`note_on_allowed` 旧实现无条件先算 `now_us()`（`SystemTime::now()`），再进
`allow_note_on_at` 判 `enabled`/`rate`。改成先判「未启用 / Normal·High」直接放行，
**语义完全一致**（该函数在这两种状态下本来就恒返回 true），省掉注入热路径上
每事件一次系统时钟读取。

## 2. 实测

### 2.1 注入吞吐（`play_realtime --unpaced`，`stress2m.mid` 4,000,000 事件，3 次中位）

| 路径 | ns/event | 相对 pre |
|---|---:|---:|
| pre-012 逐事件（`Arc<Mutex>`） | **58.9** | — |
| post-012 逐事件（纪元缓存） | **43.3** | **−26.5%** |
| post-012 批量（`--batch`） | **21.6** | **−63.3%** |

### 2.2 实机功能（`scatter100k.mid`，10 s，block 512）

| 路径 | sent | underruns | dropped_note_ons | max_voices |
|---|---:|---:|---:|---:|
| pre-012 逐事件 | 66,141 | 0 | 0 | 1,445 |
| post-012 逐事件 | 66,135 | 0 | 0 | 1,449 |
| post-012 批量 | 66,141 | 0 | 0 | 1,449 |

（`sent` 的 6 条差异来自 10 s 截止点的调度边界，不是丢事件。）

### 2.3 单测（`cargo test -p lumino-midi-io --lib`，93 passed）

| 用例 | 断言 |
|---|---|
| `batch_and_per_event_paths_emit_identical_events` | 9 条混合消息（含 2 条不支持的后触）→ 两条路径产出**完全相同**的 `(channel, event)` 序列 |
| `sender_swap_is_picked_up_without_stale_cache` | 热替换后新通道立刻生效、旧通道不再收到；`None` 时静默丢弃不 panic |
| `velocity_filter_applies_to_both_paths` | 力度过滤在两条路径上一致（过轻丢弃、vel=0 放行） |

## 3. 与 #147（AUD-004）的分工

本卡只做「注入通道吞吐」：去锁 + 批量入口 + 闸快路径。
**不做**重采样预热（`prewarm`/懒重采样卡顿归 #147），也不改 Governor 阈值、
drain 预算、`STATES_SYNC_EVERY`。

## 4. 未做 / 已知边界

- **应用侧（`crates/editor`）仍逐事件调用**：真正「按块批量调度」需要播放器把
  一个 tick 的事件攒成一次 `send_raw_batch`。后端入口与等价性已就绪，
  editor 接线留给 UI 卡（当前与 DRAW 工作流冲突）。
- 批量路径仍逐条 `mpsc::send`（channel 无批量 API）。若要再进一步，需要把
  mpsc 换成「共享队列 + 唤醒」，那会动 `drain.rs`，超出本卡范围。
