# Lumino 数据源冗余审计 —— 「单一权威源」符合性扫描

> 日期：2026-10-17
> 审计口径：**音符数据必须以 `MidiDocument` 为唯一权威源，任何组件不得私自二次拷贝存储；GPU 资源同理。**

## 一、🔴 P0：CC / PitchBend 双权威源（编辑会静默丢失）

### 事实链（全部带证据）

1. **加载时深拷贝一份出来**
   `crates/editor/ui/src/root/document.rs:18-21` → `EditorData::import_control_events_from_document`
   `crates/editor/editor-state/src/editor_state/editor_data/automation.rs:54-108`：
   `for ev in &doc.control_events { … }`（`automation.rs:65`）→ 按 `(track, kind, controller)` 分组 → `self.automation_lanes.push(Arc::new(lane))`（`automation.rs:107`）。
   **从这一刻起，CC/PB 同一逻辑数据存在两份：`doc.control_events`（加载时原值）+ `automation_lanes`（副本）。**

2. **编辑只写副本，绝不回写权威源**
   唯一写入口 `apply_automation_edit`（`automation.rs:116-283`）六个分支全部只动 `automation_lanes[idx]`（`automation.rs:131/156/200/221/243/274`）。
   全仓 grep 对 `doc.control_events` 的写入只有一处：`crates/editor/ui/src/root/editor_ops/track/channel.rs:51-63`——而且**只改 `channel` 字段，不动 tick/value**。

3. **读取端已经分裂**
   - 当前轨播放：读 lane。`crates/editor/ui/src/root/editor_ops/playback.rs:68-119`（CC/PB/RPN 全部来自 `automation_lanes`）。
   - 非当前轨播放：读 document。`crates/audio/midi-io/src/playback/engine/control/chase.rs:91` 读 `doc.control_events`。
   - PC（音色切换）：读 document。`playback.rs:122-127` 注释直言「ProgramChange 不存储在 automation_lanes 中…必须直接从 doc.control_events 提取」。
   - 屏幕 CC/Bend 面板：读 lane（`automation.rs:286-317`）。

4. **保存 / 导出全部读权威源（= 旧值）**
   - LMPJ 保存：`crates/core/project/src/project/conversion.rs:35` `for ev in &doc.control_events`。
   - MIDI 导出：`crates/tools/export/src/midi/extract.rs:27` 同上；且 `extract.rs:54` `_ => {} // Pitch Bend and others — not exported as PC/CC` —— **PitchBend 从 CC/PC 提取链里被显式跳过**。
   - 音频导出：`crates/tools/export/src/audio/event_stream.rs:67` `for ctrl in doc.control_events.iter()`。
   - 视频导出：走 `Arc<MidiDocument>` 快照（`video_export_handler.rs:247-256`），同源 document。

### 后果（代码级可推导，非猜测）

- **「听得到、存不下来」**：在 CC / 弯音面板画完曲线 → 实时播放听得到（读 lane）→ 保存 `.lmpj` / 导出 `.mid` / 导出音频全部写回加载时的原始 CC，**用户的 CC/PB 编辑被静默丢弃**。
- **PitchBend 编辑从头到尾不落盘**：lane 的 PB 只被实时播放采样（`playback.rs:89` `lane.sample_curve`），保存链路的 PB 透传读的是 `doc.control_events` 的原始 PB。
- **同一轨的 CC 听到的内容取决于它是不是当前轨**：当前轨走 lane，非当前轨走 document（`chase.rs:91`）。
- **内存 2×**：45.8 万条控制事件的素材（`automation.rs:44-45` 注释实测）加载后 CC 数据在内存中存在两份。
- **undo/redo 会进一步加剧分叉**：`history/apply.rs:270` `self.automation_lanes = snapshot.automation_lanes.clone();` 整组替换 lane，`control_events` 纹丝不动。

### 违反用户约束的原话

> 「MIDI 数据源必须要使用 mididocument 作为唯一权威源，任何组件不得私自二次拷贝存储」

`import_control_events_from_document` 就是一次**私自二次拷贝存储**，且拷贝后形成双权威。

## 二、🔴 P0：`track_max_end_ticks` 的共享 `Arc<Mutex>` 破坏快照隔离

`crates/audio/midi-model/src/document.rs:112-122`：

```rust
/// 每轨最大音符结束 tick 缓存（None = 脏，惰性重算）。
#[doc(hidden)]
pub track_max_end_ticks: Vec<std::sync::Arc<std::sync::Mutex<Option<u32>>>>,
```

`MidiDocument` 在 `document.rs:72` 是 `#[derive(Clone)]`，`Vec<Arc<...>>` 的 clone 是**指针拷贝**，不是深拷贝。

所有「快照」都基于 `MidiDocument::clone()`：
- 播放快照 `crates/editor/ui/src/root/editor_ops/playback.rs:40-41`
- 音频导出快照 `crates/editor/ui/src/root/handlers/dialog/audio_export.rs:81-84`
- 视频导出快照 `crates/editor/ui/src/root/handlers/dialog/video_export.rs:44` 与 `video_export_handler.rs:247`
- 协作上传快照 `src/runner/menu/window/collaboration.rs:131-141`

**结果**：所有快照与实时文档共用同一批 `Mutex<Option<u32>>` 缓存单元。主线程后续编辑把缓存置脏/更新（`document_query.rs:268-285` 惰性重算），**后台线程正在序列化的快照读到的 max_end 可能已经是编辑后的值** —— 快照的音符内容与 max_end 元数据不同世代。

这是「唯一权威源」改造里唯一没有被 `Arc` 化叙事覆盖到的可变共享状态：`ChunkedList` 用的是 COW（`chunked_list.rs:59-70`，写时复制，安全），而这里是**共享可变缓存**（读到的值随外界变化）。

即：**同一份 tempo 有两个权威，靠约定 + 六个出口补丁维持一致**。这正是用户要禁止的形态。

## 四、🟠 P1：`MidiDocument.tracks`（TrackManager）是写-only 死副本

`crates/audio/midi-model/src/track.rs:16-25` 的 `TrackView { name: String, visibility, solo }`，由 `MidiDocument.tracks: TrackManager`（`document.rs:107`）持有。

grep 全仓的读者：
- `MidiDocument::track_name()`（`document_query.rs:254-255`）读的是 **`track_names`**，不是 `tracks`。
- `TrackManager::get / get_mut / playable_tracks / has_solo / should_play`（`track.rs:81-117`）在生产代码中**只有 tests 调用**；`MidiDocument::tracks()` 访问器（`document_query.rs:19-21`）唯一命中是 `src/runner/menu/window/video_export/streaming.rs:116`，那是 `MmapSmf::tracks()`，与文档无关。

## 五、🟠 P1：CC/PB 播放键色索引靠「document 内存地址」判失效

`crates/editor/ui-editor/src/impls/playback.rs:117-128`：

```rust
let current_doc_addr = doc as *const MidiDocument as usize;
…
if self.playback_scan_state.doc_addr != Some(current_doc_addr) {
    self.rebuild_playback_key_index(...);
}
```

`PlaybackKeyIndex.index: NoteSpatialIndex`（`playback.rs:45-53`）是全轨合并索引，**只在这一个条件变化时重建**。

失效遗漏（代码可推导）：
1. **编辑后陈旧**：音符就地增删改只改 `MidiDocument` 内容，地址不变 → 索引不重建。此后任何触发全量重建的事件（seek > 5000 tick、tick 回退/循环回绕，`playback.rs:120-121`）会用旧索引涂键色：**已删/已移走的音符仍然着色、新增音符不着色**。
2. **换文件后陈旧**：打开新文件走 `document.rs:33` `data.document = Some(doc)` 原地赋值（旧文档 drop 后地址极可能复用），且 `clear_playback_key_colors`（`playback.rs:321-331`）与停止播放**刻意保留**索引；只有 `reset_internal_state`（`ui-editor/src/impls/config.rs:207`，仅由 `clear_editor` 调用）才重置。开启「播放键色」后连续打开两个工程，键色可能来自上一个文档。默认开关关闭（`lib.rs:152`）降低了暴露概率。

同类但更轻的问题：`Editor.spatial.note_index`（当前轨索引）在 `crates/editor/ui/src/root/editor_ops/track/deletion.rs:169-177` 恢复整轨时未调 UI 层 `mark_notes_changed()`，`track_notes_gen` 也没有到 `note_index_dirty` 的同步路径。

## 六、🟠 P1：MIDI 的「第二解析器」与导出文件模式

### 6.1 gpu-synth 自带一套完整 MIDI 解析 + 事件模型

`crates/audio/gpu-synth/src/midi.rs:12-23` `MidiEvent`、`:67-73` `TimedEvent`（8B 打包）、`:163-170` `MidiSequence { events: Vec<TimedEvent>, end_sample }`，由 `crates/audio/gpu-synth/src/midi/parser.rs:46-48` `MidiFile::load(path)` → `std::fs::read` + `Smf::parse` 产出。

即：**同一个 `.mid` 文件，项目里存在两条互不相干的解析链**——`lumino-midly` → `MidiDocument`（编辑器权威），以及 gpu-synth 自己的 parser → `MidiSequence`。

### 6.2 真实生效的违规点

| 路径 | 位置 | 数据来源 | 是否绕过 document |
|---|---|---|---|
| 音频导出 · GPU 文件模式 | `crates/tools/export/src/audio/gpu_backend/render.rs:224` `.render_midi_file(&config.midi_path)` → `synth/engine/offline.rs:41` `MidiFile::load` | 磁盘 `.mid`（`config.midi_path`，UI 字段） | ✅ **完全绕过** |
| 音频导出 · CPU 文件模式 | `crates/tools/export/src/audio/render_loops.rs:38-42` `File::open` + `Mmap` + `StreamingMidiPlayer::from_bytes` | 磁盘 `.mid` | ✅ **完全绕过** |
| 触发条件 | `src/runner/menu/window/audio_export.rs:213-219`（空文档回退）、`:236`（`document == None` 分支） | —— | 仅在这两个分支 |

内存模式（`render_audio_gpu_from_document`，`render.rs:13-16`）源仍是 document，但 `build_export_data(doc)` → `export_midi_to_bytes` → `render_midi_bytes` → `MidiFile::parse`（`offline.rs:52`）**又重建了一份 `MidiSequence`**。仓库自己在 `render.rs:171-178` 承认「与 `render_midi_file` 逐字节一致当前只有人工观测」，即这两条链的等价性无自动化保障。

补充：**同一次文件模式导出里，同一个文件被解析两遍**——`render_loops.rs:38-42` 先用 `mmap` + `StreamingMidiPlayer::from_bytes` 取端口/tempo（`render_loops.rs:46/78/79`），GPU 分支再 `MidiFile::load(config.midi_path)`（`gpu_backend/render.rs:224` → `offline.rs:41` `std::fs::read`）。

### 6.3 实时播放：无违规（已验证）

`PlaybackEngine.document: Option<Arc<MidiDocument>>`（`crates/audio/midi-io/src/playback/engine/control/core.rs:59`）+ `playback.rs:41` `manager.set_document(Arc::new(doc.clone()), …)`。`MidiDocument::clone()` 的 `ChunkedList` 是 O(块数) 指针拷贝（`chunked_list.rs:8-10`），**不是深拷贝**。实时播放没有第二条权威源。

### 7.2 🟠 `GpuNoteBuffer.instances`：CPU 全量镜像仍然存在

`crates/editor/gfx/src/gpu_note_buffer/types.rs:19-20`：

```rust
/// CPU 侧实例缓存（用于支持删除等操作）
pub(crate) instances: Vec<crate::NoteInstance>,
```

- 由 `upload_all` 整份建立并直接从镜像上传：`ops/upload.rs:76-84`（`self.instances.clear(); extend_from_slice(...); write_buffer(&self.instances)`）。
- 所有增量 API（`update_note/update_notes/add_note/remove_note/remove_at/insert_at`，`ops/update.rs:28-135`、`ops/incremental.rs:41-44`）都要**双写维护**这张镜像。

### 7.3 🟠 `MiditrailRenderer.resident_buffer`：3D 导出的第二份 GPU 全量缓冲

`crates/editor/gfx/src/miditrail_renderer/cull/lifecycle.rs:8-35` `seed_resident` → `label: Some("miditrail_export_resident")`，`queue.write_buffer(buf.inner(), 0, cast_slice(notes))`；注释（`:39`）自述「全量常驻缓冲（`seed_resident` 一次上传，**24M 文档约 370MB**）」。

于是 3D 导出期间，同一份文档音符在 GPU 上同时存在：

### 12.2 ✅ 已修：`onion_epoch` 记账（内容世代契约）

**问题**：`process_main_track_events` 的段内增量（等长原位写 / 段内删 / 段内插）改写常驻字节却不递增 `onion_epoch`；而拖动音符会改变 `(key, start_tick)` 排序键 → 任何按世代判定重建的派生索引（全局桶）会按旧序取数，**静默**漏音/错位。

**改动**：
- `onion_segments.rs`：新增 `bump_onion_epoch(renderers)` 单一入口，收口原先散落的 4 处 `wrapping_add(1)`；`process_main_track_events` 用 `bytes_changed` 标记，段内增量在批次结束后统一换代（`Reset`/`Clear` 仍由 `apply_onion_track_delta` 内部换代，不重复）；
- `onion_stream.rs`：全量会话完成走同一入口；
- `render_loop.rs`（`onion_epoch` 字段）与 `global_bucket.rs`（`BucketSource.epoch`）：把注释改成**真实契约**。原注释声称该世代来自 `Renderers::onion_epoch`，实参却是 `ResidentCull::seq`——注释与代码不符，后续照注释改动会引入真正的陈旧读取。

### 12.3 ⏸ 未改：3D 导出的 `resident_buffer` —— 不是可以盲删的重复

「改绑洋葱皮共享缓冲」的直觉方案被调研否决：`resident_buffer`（`collect_all_notes` + `pack_note_instances`）与洋葱皮常驻缓冲**内容语义不等价**，换源会改变渲染输出：

| 差异 | 导出常驻缓冲（现状） | 洋葱皮常驻缓冲 |
|---|---|---|
| 排序 | 先 `sort_visible_notes`（key 主序、start 次序、track 倒序 tiebreak）再打包 | 按音轨追加序（段表布局，tiebreak 不同） |
| `border_width` | `pack_note_instances(.., 0, ..)` → **0**；`render_from_instances` 派生 `track_idx: 0` | 高 16 位编码 track/深度区（`onion_note.wgsl:175/282/381` 据此算 `region_depth`） |
| 颜色 | 导出侧按 `current_track_color_f32(track_idx)` 重新 pack | 洋葱皮流上传时 pack 的调色板结果 |
| 内容范围 | 仅 `key < key_count`，窗口过滤交给 GPU cull | **含静音轨全部音符**，可见性靠 ViewState uniform（miditrail 自有管线不读 ViewState） |

即：换源 = 一次渲染语义变更，必须由像素等价 harness（`miditrail_renderer/tests/driven_equivalence/` 一类）在真机 + 真实黑乐谱夹具上量化验收，不能靠"看着一样"。本仓库既有纪律正是「集合等价 harness 保证，视觉 veto 不触发」——在缺少夹具（`.mid` 夹具被 `.gitignore` 排除）的前提下，风险 > 收益：省的是导出期 ≈370MB 重复显存（导出结束已 `release_export_resources` 释放），赌的是输出正确性。

**前置条件已完成**：本次 §12.2 把 `onion_epoch` 修成**可信的内容世代**——这正是换源后 cull 桶失效判定所需的前提。等夹具 + 像素 harness 就绪即可安全推进。
