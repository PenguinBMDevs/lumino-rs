> 日期：2026-10-17
> 审计口径：**音符数据必须以 `MidiDocument` 为唯一权威源，任何组件不得私自二次拷贝存储；GPU 资源同理。**

## 一、🔴 P0：CC / PitchBend 双权威源（编辑会静默丢失）

### 事实链（全部带证据）

1. **加载时深拷贝一份出来**
   `crates/editor/ui/src/root/document.rs:18-21` → `EditorData::import_control_events_from_document`
   `crates/editor/editor-state/src/editor_state/editor_data/automation.rs:54-108`：
   `for ev in &doc.control_events { … }`（`automation.rs:65`）→ 按 `(track, kind, controller)` 分组 → `self.automation_lanes.push(Arc::new(lane))`（`automation.rs:107`）。
   **从这一刻起，CC/PB 同一逻辑数据存在两份：`doc.control_events`（加载时原值）+ `automation_lanes`（副本）。**

2. **编辑只写副本，绝不回写权威源**
   唯一写入口 `apply_automation_edit`（`automation.rs:116-283`）六个分支全部只动 `automation_lanes[idx]`（`automation.rs:131/156/200/221/243/274`）。
   全仓 grep 对 `doc.control_events` 的写入只有一处：`crates/editor/ui/src/root/editor_ops/track/channel.rs:51-63`——而且**只改 `channel` 字段，不动 tick/value**。

3. **读取端已经分裂**
   - 当前轨播放：读 lane。`crates/editor/ui/src/root/editor_ops/playback.rs:68-119`（CC/PB/RPN 全部来自 `automation_lanes`）。
   - 非当前轨播放：读 document。`crates/audio/midi-io/src/playback/engine/control/chase.rs:91` 读 `doc.control_events`。
   - PC（音色切换）：读 document。`playback.rs:122-127` 注释直言「ProgramChange 不存储在 automation_lanes 中…必须直接从 doc.control_events 提取」。
   - 屏幕 CC/Bend 面板：读 lane（`automation.rs:286-317`）。

4. **保存 / 导出全部读权威源（= 旧值）**
   - LMPJ 保存：`crates/core/project/src/project/conversion.rs:35` `for ev in &doc.control_events`。
   - MIDI 导出 · CC：`crates/tools/export/src/midi/extract.rs:27` 同上。
   - MIDI 导出 · PitchBend：走**独立通道** `extract.rs:93-103`（kind==2 → `pass.pitch_bends`），由 `src/runner/menu/file/editor_midi.rs:156` 写入首轨。
     > ⚠️ **审计初稿误报更正（2026-10-17）**：初稿称「`extract.rs:54` 的 `_ => {}` 把 PitchBend 从导出链跳过了」——**错**。那条 `_ => {}` 位于 `extract_pc_cc_events`（PC/CC 专用，PB 本就不属于它的职责），PB 由 `extract_passthrough_events` 正常导出。误报已由集成测试 `crates/tools/export/tests/midi_cc_pb_roundtrip.rs` 证伪（PB 12288 无损往返）。
   - 音频导出：`crates/tools/export/src/audio/event_stream.rs:67` `for ctrl in doc.control_events.iter()`。
   - 视频导出：走 `Arc<MidiDocument>` 快照（`video_export_handler.rs:247-256`），同源 document。

   ⇒ 四个出口（LMPJ / MIDI / 音频 / 视频）**全部**以 `doc.control_events` 为准，因此 lane 不回写这一个根因即可解释全部丢失现象。

### 后果（代码级可推导，非猜测）

- **「听得到、存不下来」**：在 CC / 弯音面板画完曲线 → 实时播放听得到（读 lane）→ 保存 `.lmpj` / 导出 `.mid` / 导出音频全部写回加载时的原始 CC/PB，**用户的编辑被静默丢弃**。
- **PitchBend 同样丢**：lane 的 PB 只被实时播放采样（`playback.rs:89` `lane.sample_curve`），保存链路的 PB 透传读的是 `doc.control_events` 的原始 PB（通道本身是好的，坏的是值没同步）。
- **同一轨的 CC 听到的内容取决于它是不是当前轨**：当前轨走 lane，非当前轨走 document（`chase.rs:91`）。
- **内存 2×**：45.8 万条控制事件的素材（`automation.rs:44-45` 注释实测）加载后 CC 数据在内存中存在两份。
- **undo/redo 会进一步加剧分叉**：`history/apply.rs:270` `self.automation_lanes = snapshot.automation_lanes.clone();` 整组替换 lane，`control_events` 纹丝不动。

### 违反用户约束的原话

> 「MIDI 数据源必须要使用 mididocument 作为唯一权威源，任何组件不得私自二次拷贝存储」

`import_control_events_from_document` 就是一次**私自二次拷贝存储**，且拷贝后形成双权威。

## 二、🔴 P0：`track_max_end_ticks` 的共享 `Arc<Mutex>` 破坏快照隔离

> **状态：✅ 已修（2026-10-17，整改记录见 §十四）** —— 已用单元测试复现并锁定：
> 快照 `track_max_end_tick(0)` 返回了实时文档的 500，而快照里只有 end=200 的音符。

`crates/audio/midi-model/src/document.rs:112-122`：

```rust
/// 每轨最大音符结束 tick 缓存（None = 脏，惰性重算）。
#[doc(hidden)]
pub track_max_end_ticks: Vec<std::sync::Arc<std::sync::Mutex<Option<u32>>>>,
```

`MidiDocument` 在 `document.rs:72` 是 `#[derive(Clone)]`，`Vec<Arc<...>>` 的 clone 是**指针拷贝**，不是深拷贝。

所有「快照」都基于 `MidiDocument::clone()`：
- 播放快照 `crates/editor/ui/src/root/editor_ops/playback.rs:40-41`
- 音频导出快照 `crates/editor/ui/src/root/handlers/dialog/audio_export.rs:81-84`
- 视频导出快照 `crates/editor/ui/src/root/handlers/dialog/video_export.rs:44` 与 `video_export_handler.rs:247`
- 协作上传快照 `src/runner/menu/window/collaboration.rs:131-141`

**结果**：所有快照与实时文档共用同一批 `Mutex<Option<u32>>` 缓存单元。主线程后续编辑把缓存置脏/更新（`document_query.rs:268-285` 惰性重算），**后台线程正在序列化的快照读到的 max_end 可能已经是编辑后的值** —— 快照的音符内容与 max_end 元数据不同世代。

这是「唯一权威源」改造里唯一没有被 `Arc` 化叙事覆盖到的可变共享状态：`ChunkedList` 用的是 COW（`chunked_list.rs:59-70`，写时复制，安全），而这里是**共享可变缓存**（读到的值随外界变化）。

## 三、🟠 P1：Tempo / 拍号双份 + 出口补救

> **状态：✅ 已收口（2026-10-20，见 §二十一）** —— 六处出口补丁与装载往返全部删除，
> 「编辑写穿 document、出口只读 document」成为唯一路径，并已落回归测试。
> 字段本身（`tempo_points`/`time_signatures`）作为**编辑态缓存**保留：写入即写穿、
> 装载即只读刷新，出口一处都不读它 —— 不再构成"双权威"。

`crates/editor/editor-state/src/editor_state/editor_data.rs:126-129`：

```rust
pub tempo_points: Vec<TempoPoint>,          // 编辑态权威源
pub time_signatures: Vec<(u32, u8, u8)>,    // 编辑态权威源
```

`crates/audio/midi-model/src/document.rs:77/80`：

```rust
pub tempo_changes: Vec<(u32, f32)>,         // 「保存/播放权威」/ 权威镜像
pub time_signatures: Vec<(u32, u8, u8)>,
```

现状是**手工双向同步**：
- 写入侧：`editor_data/tempo.rs:57-65` `sync_tempo_to_document()`、`accessors/write.rs:19-21` 内联同步。改一处必须记得改另一处。
- **加载时做了一次毫无意义的往返**：`crates/editor/ui/src/host/editor_ops.rs:100-124` 先从 `doc.tempo_changes` 深拷贝出来（`:102-109`），`set_midi_document` 后立刻 `set_tempo_points`（`:118`）把它写回 `doc.tempo_changes`（`tempo.rs:59`）。数据没变，白拷两遍。
- **出口还在补救**：`save.rs:288-292`、`export.rs:101-103`、`cloud_save.rs:47-50`、`audio_export.rs:167-178`、`video_export_handler.rs:161-172`、`material.rs:62-63` 六处都写着「用编辑器 tempo_points 覆盖 doc 的加载时原始 tempo」。`crates/editor/editor-state/src/editor_state/editor_data/tempo.rs:6-7` 的注释自己承认这是「保存/导出出口依赖 `apply_tempo_points` 补救」的脆弱设计。

即：**同一份 tempo 有两个权威，靠约定 + 六个出口补丁维持一致**。这正是用户要禁止的形态。

## 四、🟠 P1：`MidiDocument.tracks` —— 半死副本 + 静音/独奏保存分叉

> **状态：✅ 已收口（2026-10-17，记录见 §十五）**
>
> ⚠️ **审计初稿误报更正**：初稿判定它是「写-only 死副本」——**错**。
> `crates/core/project/src/project/conversion.rs:122-141`（`from_midi_document`，
> 即 **`.lmpj` 保存**链路）读 `doc.tracks.get(i).visibility/.solo` 落盘，
> 它是静音/独奏的**保存源**。初稿 grep 只列了写者（conversion 加载侧 + 建轨 push），
> 漏了这个读者。
>
> 而真实缺陷比「死副本」更严重：UI 的静音/独奏只改
> `sidebar.tracks[].is_muted/is_soloed`，与这个保存源**零同步** ——
> **用户切静音 → 保存 `.lmpj` → 重开 → 静音丢失**（与 §一 CC/PB 同类）。

`crates/audio/midi-model/src/track.rs` 的 `TrackView { name, visibility, solo }`，由
`MidiDocument.tracks: TrackManager`（`document.rs`）持有。

**真正死掉的部分**（全库零调用，已删）：
- `TrackView.name` —— 与 `track_names` 重复，读取方一律走 `track_name()`；
- `TrackView.track_id` —— 即索引本身，唯一读者是同样已死的 `playable_tracks`；
- `TrackView::{with_name, should_play, should_render}`、`TrackManager::{get_mut, has_solo, playable_tracks, count}` ——
  生产代码零调用（「是否应播放」的活实现在 `PlaybackEngine::track_should_play`，
  读引擎自己的 `track_muted`/`track_soloed`，与此无关）；
- `MidiDocument::tracks()` 访问器 —— 唯一 grep 命中是 `MmapSmf::tracks()`，与文档无关。

**必须留下的部分**：`visibility` / `solo` 两个字段（`.lmpj` 持久化落点）。

于是音轨名在生产内存里有 **3 份**（`doc.track_names`、`doc.tracks[i].name`【已删】、
`Sidebar.tracks[i].name`）；静音/独奏有 **3 份**
（`Sidebar.tracks[].is_muted/is_soloed` UI 权威、`PlaybackEngine.track_muted/track_soloed`
跨线程快照、`doc.tracks[].visibility/solo` **保存源**）。

`crates/editor/ui/src/sidebar/core/types.rs:145` 的注释自我声明「静音/独奏仍由
`Track.is_muted / is_soloed` 作为单一来源」——但保存链路读的是 `doc.tracks`，
两条权威之间在本次修复前没有任何同步。

## 六、🟠 P1：MIDI 的「第二解析器」与导出文件模式

### 6.1 gpu-synth 自带一套完整 MIDI 解析 + 事件模型

`crates/audio/gpu-synth/src/midi.rs:12-23` `MidiEvent`、`:67-73` `TimedEvent`（8B 打包）、`:163-170` `MidiSequence { events: Vec<TimedEvent>, end_sample }`，由 `crates/audio/gpu-synth/src/midi/parser.rs:46-48` `MidiFile::load(path)` → `std::fs::read` + `Smf::parse` 产出。

即：**同一个 `.mid` 文件，项目里存在两条互不相干的解析链**——`lumino-midly` → `MidiDocument`（编辑器权威），以及 gpu-synth 自己的 parser → `MidiSequence`。

### 6.2 真实生效的违规点

| 差异 | 导出常驻缓冲（现状） | 洋葱皮常驻缓冲 |
|---|---|---|

**前置条件已完成**：本次 §12.2 把 `onion_epoch` 修成**可信的内容世代**——这正是换源后 cull 桶失效判定所需的前提。等夹具 + 像素 harness 就绪即可安全推进。

`tests_automation_sync.rs::sync_cost_diag` 构造 10 万条既有控制事件 + 1000 锚点 lane，
逐阶段打点（`lane` / `kept` / `bucket` / `sort` / `build`）：

| 阶段 | 优化前 | 优化后 |
|---|---|---|
| lane 扫描 | ~5 µs | ~6 µs |
| kept 过滤拷贝 | 1.0–2.1 ms | 0.55–0.78 ms |
| lane 入桶 | ~2 µs | ~7 µs |
| 稳定排序 | 1.0–3.0 ms | 0.55–0.85 ms |
| 分块构建 | 0.25–0.9 ms | **1.2 µs–0.13 ms** |

**改动二（已回退，留档教训）**：曾假设「`PackedControlEvent` 是 packed 结构，
`sort_by_key` 每次比较都要跨界取 `tick` 是热点」，改用 `sort_by_cached_key`——

原因是键提取本身很便宜，而缓存键多出的 `Vec<(K, usize)>` 分配 + 置换通行是净损失。
**数据推翻了直觉**，已回退，并把这段结论写进代码注释，避免后人重蹈。

**剩余边界（诚实）**：`kept` + `sort` 的 O(N) 是「整份重建」的固有代价。
按实测线性外推，45.8 万事件文档 ≈ **7.4 ms/次编辑**（60 fps 预算 16.6 ms 的 44%）。
要再降必须**不重建**：给 `ChunkedList` 加「按 `(tick, 谓词)` 二分定位 + 局部替换/删除」，
把每次编辑降到 O(log 块数 + k)。触发条件 = 真实用户反馈黑乐谱 CC 拖拽卡顿；
当前不做——正确性优先，且已有测量基线可对照回归。

## 十四、`track_max_end_ticks` 快照隔离整改（2026-10-17 实施）

### 14.1 先复现，再修

`document_write_tests.rs::test_clone_isolates_track_max_end_cache`（**先红后绿**）：

```
thread '...test_clone_isolates_track_max_end_cache' panicked at ...:
assertion `left == right` failed: 快照缓存被实时文档污染：快照返回了实时文档的 max_end_tick
  left: 500
 right: 200
```

复现路径（最小化）：
1. 让缓存变热：`doc.track_max_end_tick(0)` → `Some(200)`（插入路径对脏缓存保持脏，
   只有热缓存才会被 O(1) 增量更新）；
2. `snapshot = doc.clone()`；
3. 实时文档 `insert_note(0, end=500)` → 热缓存增量更新为 `Some(500)`；
4. `snapshot.track_max_end_tick(0)` 返回 **500** —— 而快照里只有 end=200 的音符
   （`ChunkedList` 的 COW 让插入只复制目标块，快照的块未被修改）。

即：**同一个缓存单元被多个文档实例（快照）共用**，谁最后写谁说了算。

### 14.2 根因与修法

根因：`#[derive(Clone)]` + `track_max_end_ticks: Vec<Arc<Mutex<Option<u32>>>>`
→ 派生 Clone 做的是 **Arc 指针拷贝**，快照与实时文档共享同一批可变缓存单元。

修法：`MidiDocument` 改**手写 `Clone`**：音符/控制事件仍走 `ChunkedList` 的块级 Arc
共享（O(块数)，块数据物理共址），但 `track_max_end_ticks` 按**当前缓存值**重建
独立单元（`Arc::new(Mutex::new(cached))`）：O(音轨数) 次小分配，不复制任何音符数据；
毒锁按脏（`None`）处理 —— 缓存失效只会导致一次惰性重算，绝不给出可能错误的值。

### 14.3 为什么不是其它三个方案

| 方案 | 否决理由 |
|---|---|
| 改 `Vec<Option<u32>>` + `Cell` | `Cell` **不 Sync**；文档经 `Arc<MidiDocument>` 跨线程共享（播放线程每块读 `tracks_max_end_tick()`），仍需 Mutex |
| clone 时把缓存全部重置为 `None`（冷缓存） | 播放引擎**每个音频块**都查该值；每次编辑后首帧对全部轨 O(N) 重算（1600 万音符 ≈30 ms 的既有实测）→ 每次编辑一次卡顿 |
| 单 `Arc<Mutex<Vec<Option<u32>>>>`（clone 只 1 次分配） | 收益是「N 次小分配 → 1 次」，代价是 ~50 处构造字面量要改、且打破既有「每轨独立单元」约定 → 改动面 ≫ 收益 |

### 14.4 行为影响（诚实）

- 播放「轨尾自动停止」**仍随编辑后移**：快照在每次编辑（`track_notes_gen` 变化）时
  重建，重建时拷贝的就是当时的最新值。
- 唯一差异是：编辑发生到新快照换入之间的几毫秒窗口内，播放引擎读到的是**自己快照**
  的值（内容一致），而不是实时文档的新值。这比原先「播着 A 快照却按 B 的内容停」
  更一致，属修正而非回归。
- `track_max_end_ticks` 在 `MidiDocument::clone()` 的代价从 O(1) 指针拷贝变为
  O(音轨数) 次小分配；典型 16–100 轨可忽略（未单独测量，量级 <10 µs）。

## 十七、当前轨空间索引 / 最长音符长度：手工标记 → 权威失效键（2026-10-17 实施）

> 表格第 6 行（§十六 遗留的那条「同类问题」）。这是「派生缓存靠手工标记判失效」
> 的第三个实例——前两个是 §十二 的 `onion_epoch`、§十六 的播放键色索引。

### 17.1 先复现三条（全部红了才改）

`crates/editor/ui-editor/src/tests/spatial_index_staleness.rs`：

```

  assertion: 音符已被删除，框选不得命中陈旧索引里的下标

```

复现方式与审计点名的路径同形：数据层整轨替换（`replace_track_notes` + bump
`track_notes_gen`，即 `root/editor_ops/track/deletion.rs:169-177`「找回删除音轨」的
做法），**不**调用 UI 层的 `Editor::mark_notes_changed`。

第二条（`left: 3`）就是用户可见的后果：框选返回**下标的音符已不存在**。

### 17.2 根因：失效信号在错误的层

`SpatialIndexState` 的两个派生缓存（`note_index` 空间索引、`max_note_len`
框选 lookback 上界）只由 UI 层布尔标记失效：

| 缓存 | 旧失效方式 | 谁会设置 |
|---|---|---|
| `note_index` | `note_index_dirty = true` | `Editor::mark_notes_changed`（UI 层）、`switch_to_track` |
| `max_note_len` | `= 0`（哨兵） | 同上 |

而**数据层**的写入路径（协作远端编辑、素材放置、整轨恢复…）只 bump
`EditorData::track_notes_gen`，从不碰 UI 层标记 → 缓存长期陈旧。反过来，
`Editor.spatial` 在 ui-editor、`track_notes_gen` 在 editor-state，跨层同步靠自觉，
必然会漏。

### 17.3 修法：失效键 = `(track_notes_gen, current_track)`，并保留显式失效通路

两个缓存各自记录构建时的权威键（`note_index_key` / `max_note_len_key`）：

- `track_notes_gen` —— 数据层所有音符写入路径的契约（`marks.rs`），自动覆盖跨层写入；
- `current_track` —— 索引与 lookback 都是「当前轨」的衍生结构，切轨必须失效
  （`switch_to_track` 因此不再需要手工置脏）。

**蓝军自检抓到的一个坑（必须同时保留显式通路）**：拖动热路径的增量接口
`restore_current_track_sorted_incremental` / `record_update_ranges_*`
（`interaction/released.rs` 拉伸提交）**刻意不 bump** `track_notes_gen`——每帧全量
同步代价过高，它们改用 `mark_current_track_changed` + 增量渲染事件。若只留世代键，
拉伸音符后空间索引会变成陈旧（比修复前更糟）。因此
`Editor::mark_notes_changed()` 保留「清空失效键」的显式失效能力：

```
数据层写入 → bump track_notes_gen ✓ 自动失效
UI 增量热路径 → mark_notes_changed() ✓ 显式失效（既有行为不变）
```

并加了一条**回归护栏**测试 `test_explicit_mark_still_invalidates_spatial_index`，
防止后人以为「世代键已足够」而删掉显式通路。

顺带清理：`host/editor_ops.rs`（装载后手工置脏，世代已覆盖 → 删除）、
`host/editor_ops/clear.rs`（改用 `SpatialIndexState::invalidate_spatial_caches()`）、
`rendering/visible_notes.rs`（`!dirty` → `has_clean_spatial_index()`）。

  ——把归档头唯一的时间字段参数化，形成"相同输入 ⇒ 逐字节相同"的确定性入口；
- 房间工程固定 `created_at = 0`，并把 metadata 的 `created_at` / `modified_at`
  归一到 RFC3339 纪元零点（两者都是写-only 字段，App 内无处读取，无展示影响）；
  **上传的就是被 hash 的那份字节**，不产生第二份口径，也不额外做一次压缩；
- `hash_bytes` 从 `DefaultHasher` 换成 FNV-1a 64：后者算法永久固定，
  不会因 Rust 版本升级悄悄改变而让跨客户端比对失效（`DefaultHasher` 明确不承诺稳定）；
- 回归断言：归档头/metadata 无墙钟字段、同一 doc 两次编码逐字节一致、
  同内容同 hash / 不同内容不同 hash、FNV-1a 公开测试向量；
- 同卡修掉 flaky 测试：`test_empty_shapes_archive_has_no_part_and_is_deterministic`
  的"两次 `save_to_archive` 字节一致"改为按 `encode_archive_with_time` 断言确定性。
