# PREF-002：CPU（XSynth）离线导出提速 —— 实现与效果记录

> 记录日期：2026-09-23 ｜ 关联 Issue：[#43](https://github.com/PenguinBMDevs/lumino-rs/issues/43)
> 关联 PR：#61（P0）/ #62（P1+profile+文档）/ #63（验收更新）/ #64（测试 flake）/ #65（设置补正）
> 素材：`Night Voyager-18906416-By IMT11D&TheAtomicBomb.mid`（153 MB / 130 轨 / 1920 PPQN / 3827 万事件 / 334.87s，**7 端口**）
> 音源：`F:\CathanConcertGrand-1.1.1\1. Cathan Concert Grand - Concert Presets\Cathan Concert Grand.sfz`
> 构建口径：release（48 kHz / 立体声 / WAV / 限幅开 / 通道+按键多线程 Auto，除特别注明）

## 一、问题与结论速览

Issue 原始测量（debug、逐事件渲染）：**4 h 55 m** 完成 334.87s 音频（0.019× 实时），
观测到"利用率随进度下降、工作集 10.8→14.2 GB"——典型"每事件固定开销 + 声部堆积"特征。

| 场景 | 结果 |
|---|---|
| 修复后（release，**应用默认口径**） | **165 s（应用实测）/ 239 s（无头复核）**，≈1.9×/1.3× 实时 |
| 验收初目标（release ≤30 min） | ✅ **达成**（余量 3.6×~10.9×） |
| 修复后（每键复音 = 0 无限制口径） | 59.3 min（0.090×）——"能跑完但代价不可接受" |
| 修复后（key 级并行关闭） | 投影 ≈4.2 h（24 min 仅渲染 32.1s 音频，中断） |
| 分片同配置对照（250-260s，复音无限 + 无限幅） | 20.59s → 13.73s（**1.50×**） |
| 分片同配置对照（key 级并行关闭） | 78.03s → 36.13s（2.16×） |
| 听感验收（用户） | ✅ 通过 |

**一句话机制**：把 CPU 导出从"每个 MIDI 事件调用一次合成引擎"改为
**"事件按 B 帧块聚合、块首一次性投递后整块渲染"**，调用次数从"事件数（百万级）"
降到"音频帧数 / B（万级）"；同时 tick→时间换算改为 O(1) 摊还游标、多轨取事件改为堆归并。

## 二、修复前的瓶颈分析（定位结论）

CPU 导出链路：`render_loops` → 每事件 `MidiEventProcessor::process_midi_event`
→ `advance_to(tick)` → `render_duration(delta)` → `channel_group.read_samples`。

| # | 环节 | 位置 | 性质 |
|---|---|---|---|
| 1 | `advance_to` 每次调用**两次全段线性扫描** tempo 表 | `export/audio/tick_conv.rs` | O(事件数 × tempo 段数)；且逐事件 `(delta×sr) as usize` 截断累积漂移 |
| 2 | **每事件一次引擎调用**（哪怕 delta=0~5 采样）：16 通道 × 128 键簿记、`load_program`、声部维护、两层 Rayon `pool.install` | `export/audio/event/processor.rs` | 调用次数 = 事件数（百万级），固定开销 >> 实际 DSP |
| 3 | 声部维护按调用次数放大（`remove_ended_voices` 等） | fork `xsynth-*` | O(调用次数 × 声部数) |
| 4 | `next_event` 每事件线性扫描全部轨道取最小 tick | `midi-loader/src/streaming_player.rs` | O(轨道数)/事件：130 轨 × 3827 万 ≈ 50 亿次比较 |
| 5 | debug 下导出/加载胶水为 opt-0（仅 `xsynth-*` 有 opt-level=3） | 根 `Cargo.toml` | debug 可用性进一步恶化 |

## 三、实现（2 个功能 PR + 3 个收尾 PR）

### P0-2 `TickToTime` 游标化（PR #61，`922c06f5`）

- 结构：`tempos: Vec<(tick, bpm)>` + `prev_tick` + **`seg_idx` + `secs_at_cursor`**；
- `seconds_at(&mut self, tick)`：从游标位置只向前跨段累加，O(1) 摊还；`advance_to` 改为
  "游标绝对秒之差"；`tick_to_seconds(&self)`（慢路径）保留给一次性换算（总时长/进度）；
- 帧域以"累计秒 × 采样率"取整替代逐事件截断——**修掉亚采样时基漂移**
  （实测：12s 片段修复前少渲染 5280 帧 ≈ 0.11s / 1.1%）；
- 单测：游标与慢路径**逐点数值等价**（跨段 / 同 tick 去重 / 重复 tick / 回退 tick / 大跳）。

### P0-1 CPU 块式渲染调度（PR #61，`fedcd5a5`）

- 新增 `audio/block_scheduler.rs`：`RenderCursor`
  - `frames_before(frame)`：块模式把事件目标帧**向下对齐到块首**，返回"投递前需渲染帧数"；
    精确模式（B≤1）直接对齐到事件帧；
  - `add_rendered`（`note_force_end_delay` 的额外渲染计入采样时钟）、
    `finish_remainder`（收尾补齐到"最后一个事件的精确帧"，**输出长度与旧实现一致**）；
- `event/processor.rs` 拆出 `event/render.rs`：帧域批量渲染（上限 4096 帧/批）+ Vec 缓冲池；
  `dispatch_event`（只投递不推进时间）/ `frame_at_tick`（游标换算）取代逐事件驱动；
- 配置项 `block_frames`（默认 **256**；`0/1` = 逐事件精确模式；UI 暂未暴露，走默认）；
- **语义保真清单**：
  - `note_force_end_delay > 0` → 强制精确模式（延迟渲染语义要求精确时间推进）；
  - 暂停/中止：按块检查（≤4096 帧粒度），与旧实现同量级；
  - 尾部：`finalize`（AllNotesOff/ResetControl + 静音检测）未改；块模式差异仅为
    **每音符 ≤B 帧（256 帧 @48kHz = 5.33ms）的确定性量化**（对齐 GPU 后端 512 帧块语义）。

### P1-4 多轨归并（PR #62，`1c0c236e`）

- `StreamingMidiPlayer::next_event`：每轨游标 + `BinaryHeap<Reverse<(tick, track_idx)>>` k 路归并，
  消费后立即把该轨下一事件重新入堆；
- 保持旧"逐轨线性扫描取严格最小"的**稳定语义**：同 tick 事件按轨号升序（新增回归测试
  `test_same_tick_events_follow_track_index_order`）。

### dev profile（PR #62，`5f67326f`）

- `[profile.dev.package.lumino-export]` / `lumino-midi-loader` 加 `opt-level = 3`：
  debug 构建下导出/加载胶水不再 opt-0 裸奔。

## 四、效果（基准数据）

### 分片：块大小（B）扫描（250-260s，Auto+Auto，限幅开）

| B | 墙钟 | ×实时 |
|---|---|---|
| 1（精确） | 20.85s | 0.575 |
| 64 | 16.56s | 0.725 |
| 128 | 14.97s | 0.802 |
| **256（默认）** | **13.96s** | **0.860** |
| 512 | 13.59s | 0.883 |

> B=512 仅比 256 快 ~2.6%，但量化上界翻倍 → 默认取 **256**（issue 建议 64–256），可配。

### 分片：并行口径对照（250-260s）

| 配置 | 旧（逐事件） | 新（B=256） |
|---|---|---|
| key=None（非默认） | 78.03s | 36.13s（2.16×） |
| key=Auto（**应用默认**） | 20.59s | 13.96s（1.50×） |

**关键互补发现**：块式调度让 key 级并行**真正有活可干**——逐事件模式下每块只有 0~5 帧，
并行调度开销大于 DSP；块化后同配置 key=Auto 比 key=None 快 **2.6×**（分片）、
全曲上快 **4.2×**（59.3 min vs key=None 投影 4.2 h）。

### 全曲（334.87s 素材）

| 配置 | 墙钟 | ×实时 | 备注 |
|---|---|---|---|
| **应用默认（每键 32 + 限幅开 + Auto+Auto）** | **165 s（应用）/ 239 s（无头）** | 1.94× / 1.33× | 输出 116.95 MB / 1532.9 万帧 |
| 每键 0（无限）+ 无限幅 | 59.3 min | 0.090 | 口径对照 |
| key=None | 中断于 32.1s 音频 / 24.1 min | 0.022 | 投影 ≈4.2 h |

> 165s（应用）与 239s（无头，流式路径）差异来自路径（内存文档 vs mmap 流式）与机器状态，同一数量级。

## 五、正确性证据

1. **精确模式（B=1）与被替换实现对照**（真实小素材 150-151s，119 事件）：
   最佳对齐仅 **3 帧**（≈0.06 ms，来自漂移修复）、对齐后 corr **0.989**、
   1 ms RMS 包络 corr **0.996** → 重构未引入行为变化；
2. **块模式差异 = 每音符 ≤B 帧的确定性量化**（5.33 ms @48kHz，对齐 GPU 512 帧语义）；
   逐样本相关系数对亚毫秒平移极敏感，不构成质量判据——A/B 结论以包络与**听感**为准；
3. **引擎确定性**：同代码两次渲染 corr = 1.000、自比较 corr = 1.000；
4. **单测**：游标逐点等价、`RenderCursor` 5 例（块对齐/精确模式/回退/收尾/额外渲染）、
   `render_frames` 帧数守恒（6000 帧 × 2 通道）、同 tick 轨号顺序回归；
5. **语义**：暂停/中止按块检查、`finalize` 未改、`note_force_end_delay` 保真（见 §三）；
6. **听感验收**：用户确认无问题 ✅。

## 六、过程中发现（超出原 Issue 范围，均已记录）

1. **多端口渲染缺失（重要）**：本素材是 **7 端口文件**（FF 21 ×129，端口 0–6 分布
   `15/16/16/33/15/18/16`），而引擎只有 16 通道 → 端口合流：
   - Port A ch1 与 Port B ch1 的 CC/PB/PC/延音互相串台；
   - "每键 32"实际被多端口共享（杀音更激进）；设为 0 则声部无上限堆积（见 §七）；
   - 加载/工程链路**保留** port（`MidiDocument.track_ports`、`TrackMeta.port`），
     仅合成层（CPU/GPU/播放）忽略；**MIDI 导出**还会丢 FF 21（`export/src/midi/tracks.rs`）。
   - 建议另开"多端口渲染支持"议题（方案：`SynthFormat::Custom{channels}` + `port*16+ch` 映射，
     GPU 侧需扩 `key_voices/[16*128]` 硬编码；或每端口一引擎实例）。
2. **每键复音（layers）是陷阱选项**：实测曲线（分片）：32 → 3.42s、64 → 4.74s、128 → 7.04s、
   256 → 23.7s、0（无限）→ 13.3s（分片）/ **59.3 min（全曲，21×）**；
   → 已在音频导出对话框**补正**（PR #65）：建议文案 + `0=不限` 红色警告行，不改语义。
3. **测试 flake**：
   - `palette::tests::test_unlock_after_lock_allows_palette_switch`（全局状态并行污染）→ 已修（PR #64，串行锁）；
   - `midi-io` 的 `test_solo_plays_only_soloed_track_engine`（`sleep(20ms)` 时序假设，macOS runner 偶发）→ 待修。

## 八、后续建议（按价值排序）

1. **多端口渲染支持**（正确性议题，建议新开）：影响 CPU/GPU/播放/导出四处；
   修好后同 layers 值会保留更多层、音色不再串台，同时负载形态变化需重定基线；
2. **fork 侧继续提速（可选）**：P1-3 `remove_ended_voices` 去分配、P1-5 键级负载均衡
   （只调度有声音的键 / 单键切分）、P2 三段流水线——如需把 165s 再压缩再排期；
3. **外部对照（可选）**：OmniConverter（XSynth 模式，同机同音源）作为参考基线；
4. `midi-io` solo 时序 flake 修复（小 PR）。
