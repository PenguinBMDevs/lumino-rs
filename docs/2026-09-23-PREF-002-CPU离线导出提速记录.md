# PREF-002：CPU（XSynth）离线导出提速记录

> 记录日期：2026-09-23 ｜ 关联 Issue：#43 ｜ 分支：`perf/pref-002-cpu-export-speed`
> 素材：`Night Voyager-18906416-By IMT11D&TheAtomicBomb.mid`（153 MB / 130 轨 / 1920 PPQN / 3827 万事件 / 334.87s）
> 音源：`F:\CathanConcertGrand-1.1.1\1. Cathan Concert Grand - Concert Presets\Cathan Concert Grand.sfz`

## 一、结论速览

| 场景 | 结果 |
|---|---|
| Issue 原始测量（**debug**，逐事件渲染，channel/key 均 Auto） | **4 h 55 m**（0.019× 实时） |
| 本轮修复后（**release**，B=256 块式渲染，Auto+Auto） | **59.3 min**（0.090× 实时） |
| Issue 验收初目标（release ≤30 min） | ❌ **未达标**（差约 2×，剩余瓶颈见 §五） |
| 分片对照（250-260s 片段，同为应用默认 Auto+Auto） | 20.59s → 13.96s（**1.48×**） |
| 分片对照（250-260s，key 级并行关闭时） | 78.03s → 36.13s（2.16×） |

**核心机制**：CPU 导出原为"逐事件驱动"——每个 MIDI 事件都调用一次合成引擎（16 通道 × 128 键
簿记、声部维护、并行池调度）。本修复把事件按 B 帧块聚合、块首一次性投递后整块渲染，调用次数
从"事件数（百万级）"降到"音频帧数 / B（万级）"；同时 t ick→时间换算改为 O(1) 摊还游标。

**关键互补发现**：块式调度让 **key 级并行真正有活可干**——原逐事件模式下每块只有 0~5 帧，
并行调度开销大于实际 DSP；块化后同一配置下 key=Auto 比 key=None 快 **2.6×**（分片），
全曲上快 **4.2×**（59.3 min vs key=None 投影 4.2 h）。

## 二、实现（两个 PR）

### PR #61（已合并，merge `acd3ec6c`）

1. **P0-2 `TickToTime` 游标化**（`922c06f5`）
   - `advance_to` 原每次调用两次全段线性扫描（O(tempo 段数)），改为段索引 + 累计秒游标，O(1) 摊还；
   - 顺带以整数帧域累积替代逐事件 `(delta×sr) as usize` 截断，修掉亚采样时基漂移
     （该素材 1.1% 的渲染时长误差：修复前少渲染 5280 帧/12s 片段）。

2. **P0-1 CPU 块式渲染调度**（`fedcd5a5`）
   - 新增 `crates/tools/export/src/audio/block_scheduler.rs`（`RenderCursor`：块对齐 / 精确模式 / 收尾补齐）；
   - `event/processor.rs` 拆出 `event/render.rs`（帧域批量渲染 + 缓冲池），
     `dispatch_event` / `frame_at_tick` 取代逐事件驱动；
   - 配置项 `block_frames`（默认 **256**，`0/1` = 逐事件精确模式）；
   - `note_force_end_delay > 0` 强制精确模式（语义保真）；暂停/中止按块检查；
     收尾补齐到"最后一个事件的精确帧"，输出长度与旧实现一致。

### PR #62（本 PR）

3. **P1-4 多轨归并**（`1c0c236e`）：`StreamingMidiPlayer::next_event` 原每事件线性扫描全部轨道
   （O(轨道数)/事件，130 轨 × 3827 万事件 ≈ 50 亿次比较），改为每轨游标 + 最小堆 k 路归并；
   同 tick 事件保持"轨号升序"稳定语义（新增回归测试）。
4. **dev profile**：`[profile.dev.package.lumino-export]` / `lumino-midi-loader` 加 `opt-level=3`，
   避免 debug 构建下导出不可用（原 debug 差距的另一来源）。

## 四、正确性证据

1. **精确模式（B=1）与被替换实现对照**（真实小素材 150-151s，119 事件）：
   最佳对齐仅 **3 帧**（≈0.06 ms，漂移修复）、对齐后 corr **0.989**、1 ms RMS 包络 corr **0.996**。
2. **块模式的差异是"每音符 ≤B 帧（256 帧 @48kHz = 5.33 ms）的确定性量化"**（对齐 GPU 后端
   512 帧块语义）；逐样本相关系数对亚毫秒平移极敏感，不构成质量判据——A/B 结论以包络与听感为准。
3. 引擎确定性验证：同代码两次渲染 corr = 1.000、自比较 corr = 1.000。
4. 单测：`TickToTime` 游标与慢路径逐点数值等价（跨段/重复/回退 tick）、`RenderCursor` 5 例、
   `render_frames` 帧数守恒、同 tick 轨号顺序回归。
5. 进度/暂停/中止/尾部语义：按块检查（≤4096 帧粒度），`finalize` 逻辑未改。

## 五、未达标原因与后续（fork 侧，本卡范围外）

全曲耗时分布显示剩余成本集中在 **声部（voice）路径**而非调用次数：

- 修复后 key=Auto 与 key=None 相差 **4.2×**（59.3 min vs 投影 4.2 h）→ 并行度/负载均衡是主因；
- 素材后 1/3 是热点（250-300s 区间 50s 内 1564 万事件，占全文件 41%）；
- Issue 原始分析指出的 fork 侧项（未做）：
  1. **P1-3 `remove_ended_voices` 去分配**（每次调用 new `VecDeque` + 全量 drain/push）；
  2. **P1-5 负载均衡**（键级只调度"有声音的键"；单键声部极多时切分该键）；
  3. **P2 流水线**（事件摄入 / 块渲染 / 写盘三段）。

这些改动位于 `PenguinBMDevs/xsynth-Lumino`（fork），需发版 + bump rev，且与实时播放共享路径，
需要人耳验收，故按计划留待后续单独排期。
