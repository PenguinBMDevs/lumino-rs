# Lumino 重构方案 —— 文档一：总体架构诊断与重构蓝图

> 版本：v0.1
> 审查基准：commit `7a083890`
> 代码规模：153,166 行 Rust / 866 个 .rs 文件 / 26 个 crate

---

## 一、架构诊断：当前问题全景

### 1.1 Crate 数量过多，边界模糊

当前 26 个 crate 的划分存在明显的"过度拆分"问题：

| 层级 | 现有 Crate | 问题 |
|------|-----------|------|
| 核心层 | `core`, `event`, `message`, `extras` | 4 个 crate 职责重叠，`message` 反向依赖 `midi-loader` |
| 音频层 | `midi-io`, `midi-loader`, `midi-model`, `midiplayer`, `note-core`, `playback`, `xsynth` | 7 个 crate 但音频管线是单向的，拆分过细导致编译依赖链长 |
| 编辑层 | `editor-state`, `ui-editor`, `ui-settings`, `ui-core`, `dialog` | `editor-state` 和 `ui-editor` 都直接操作 `EditorData`，边界不清 |
| UI 层 | `ui` (host + root) | 一个 crate 依赖 17 个内部 crate，成了事实上的上帝对象 |
| 网络层 | `cloud`, `collaboration` | 两个 crate 都依赖 `ui`，但 cloud 的协议逻辑和 UI 耦合 |
| 工具层 | `export`, `extras` | `export` 依赖 `project` 和 `midi-model`，但 `extras` 又依赖 `export` |

**关键矛盾**：`lumino-ui` 作为 UI 入口，同时依赖了音频 (`midi-io`, `playback`)、网络 (`cloud`, `collaboration`)、导出 (`export`)——UI 层穿透了所有业务层。

### 1.2 状态管理：三层嵌套 + 散布式同步

当前状态结构：

```
Host (窗口/事件循环)
  └── Root (UI 组件树)
        └── EditorState
              ├── ViewState (滚动/缩放)
              ├── CanvasState (画布)
              ├── InteractionState (交互)
              ├── EditorData (20+ 字段)
              │     ├── document: Option<MidiDocument>
              │     ├── history: History
              │     ├── track_notes_gen: u64
              │     ├── onion_dirty_tracks: Option<HashSet<usize>>
              │     ├── note_delta_events: Vec<NoteDeltaEvent>
              │     ├── note_delta_dirty: bool
              │     ├── cc_data: CcData
              │     ├── automation_lanes: Vec<Arc<AutomationLane>>
              │     ├── tempo_points, time_signatures, key_signatures...
              │     └── ... (还有 10+ 个字段)
              ├── Tool
              ├── AutoScrollConfig
              ├── ImageToMidiState
              └── LineToolState
```

**问题清单**：

1. **混合职责**：`EditorData` 同时管理文档数据、GPU 增量队列、历史记录、视觉映射——一个 struct 承担了 4 种不同生命周期的东西
2. **同步地狱**：12 个 `sync_*` 函数散布在 `ui/src/root/editor_ops/`、`editor-state/src/`、`dialog/src/` 中，改一个状态要手动触发 3-5 个同步
3. **深层访问**：获取当前音轨音符需要 `editor_state.data.document.as_ref().unwrap().track_notes(track)`——5 层嵌套
4. **版本号爆炸**：`track_notes_gen` 用于缓存失效检测，但 `onion_dirty_tracks`、`note_delta_dirty`、`note_delta_events` 三个字段都在处理"什么变了"的语义，互相重叠

### 1.3 消息系统：枚举爆炸 + 集中式分发

`crates/core/message/src/` 下有 **16 个独立文件**，每个定义一个 `*Action` enum：

```
audio_export.rs    → AudioExportAction  (5 个变体)
batch_edit.rs      → BatchEditAction    (4 个变体)
cloud_action.rs    → CloudAction        (6 个变体)
collaboration.rs   → CollaborationAction (5 个变体)
context_menu.rs    → PianoRollContextMenuAction (5 个变体)
editor.rs          → EditorAction       (20+ 个变体)
...
```

**问题**：
- 新增一个面板操作需要新增一个文件 + 一个 enum + 在 `Message` enum 中加变体 + 在 `process_message` 中加分支
- 没有统一 trait，无法泛化处理（比如"所有 Action 都可以撤销"这个语义无法表达）
- `context_menu.rs` 一个文件里有 5 个 enum，说明文件粒度划分不合理

### 1.4 渲染管线：重复代码 + 无统一抽象

`crates/editor/gfx/src/` 下 6 个 renderer，每个都手写 pipeline 创建：

```rust
// arrangement_renderer/init.rs
let pipeline_layout = device.create_pipeline_layout(&wgpu::PipelineLayoutDescriptor {
    label: Some("arrangement_pipeline_layout"),
    bind_group_layouts: &[&bind_group_layout],
    push_constant_ranges: &[],
});
let pipeline = device.create_render_pipeline(&wgpu::RenderPipelineDescriptor {
    label: Some("arrangement_pipeline"),
    layout: Some(&pipeline_layout),
    vertex: wgpu::VertexState { module: &shader, entry_point: Some("vs_main"), ... },
    fragment: wgpu::FragmentState { module: &shader, entry_point: Some("fs_main"), ... },
    ... // 还有 15+ 个字段
});

// cc_bar_renderer/core.rs —— 几乎完全相同的代码
let pipeline_layout = device.create_pipeline_layout(&wgpu::PipelineLayoutDescriptor {
    label: Some("cc_bar_pipeline_layout"),
    ...
});
```

**统计**：全 gfx crate 有 **27 处** `create_pipeline_layout`/`create_render_pipeline` 调用，其中 20+ 处是相同模板。

`gpu_resource_tracker` 是全局函数模块，每个 renderer 手动调用：
```rust
gpu_resource_tracker::add_buffer(&buffer);   // 创建时
gpu_resource_tracker::sub_buffer(&buffer);   // 销毁时
```
**问题**：漏调用 `sub_buffer` 会导致内存泄漏统计偏差，而这是手动维护的。

### 1.5 代码质量：规则写在纸上，代码无视规则

| 规则 | 配置位置 | 实际状态 |
|------|---------|---------|
| 文件不超过 400 行 | `clippy.toml` | ❌ 20+ 文件超 1000 行，最大 4642 行 |
| 零 unwrap | 团队规范 | ✅ 生产代码确实零 unwrap |
| 函数不超过 100 行 | 隐含规范 | ❌ `KDMAPI::find_omnimidi_paths` 1119 行 |
| 每个 crate 有测试 | 隐含规范 | ❌ `audio` 目录下多个 crate 无测试 |
| 文档覆盖率 | 隐含规范 | ⚠️ 3686 行 doc comment / 153166 行代码 ≈ 2.4% |

## 二、重构蓝图：目标架构

### 2.1 新 Crate 结构（12 个）

```
lumino-app/          ← 唯一入口：窗口、事件循环、全局状态机
  ├── 合并：原 ui/src/host/ + 原 ui/src/root/ 的协调逻辑
  ├── 职责：持有 Editor + Gfx + Audio + Network 的实例，转发事件
  └── 不直接包含任何业务逻辑

lumino-editor/       ← 编辑器核心：UI 组件 + 状态管理 + 编辑操作
  ├── 合并：原 editor-state/ + ui-editor/ + ui-settings/ + ui-core/
  ├── 职责：所有用户交互、状态变更、撤销/重做
  └── 对外暴露：Editor 结构体 + Action trait

lumino-gfx/          ← 渲染引擎（保留，内部重构）
  ├── 合并：原 gfx/ 所有 renderer
  ├── 新增：PipelineBuilder 抽象、统一资源管理
  └── 对外暴露：GfxContext trait（Editor 通过 trait 调用渲染）

lumino-audio/        ← 音频引擎
  ├── 合并：midi-io/ + midi-loader/ + midi-model/ + playback/ + note-core/
  ├── 保留：xsynth/（fork 版本，独立维护）
  └── 对外暴露：AudioEngine trait（播放/暂停/seek/导出音频）

lumino-project/      ← 工程文件（保留）
  ├── 职责：.lmpj 格式序列化/反序列化、自动保存
  └── 依赖：仅 lumino-core

lumino-network/      ← 网络与协作
  ├── 合并：cloud/ + collaboration/
  ├── 职责：云存储同步、实时协作协议
  └── 对外暴露：NetworkClient trait

lumino-export/       ← 导出工具（保留）
  ├── 职责：MIDI/视频/音频导出
  └── 依赖：lumino-core + lumino-project

lumino-core/         ← 核心数据类型与基础设施
  ├── 合并：原 core/ + event/ + message/ + extras/
  ├── 职责：NoteEvent、TempoMap、Config、i18n、错误类型
  └── 原则：零业务逻辑，纯数据 + 工具函数

lumino-dialog/       ← 对话框系统（保留）
  ├── 职责：模态/非模态对话框管理
  └── 依赖：仅 lumino-core + iced

lumino-memtrace/     ← 内存追踪（保留）
  ├── 职责：TaggedAlloc、GPU 资源统计
  └── 独立 crate，无内部依赖

lumino-tests/        ← 集成测试（新增）
  ├── 职责：跨 crate 的集成测试、性能基准
  └── 依赖：所有内部 crate
```

### 2.3 状态管理：事件驱动架构

**核心思想**：用不可变事件流替代直接状态修改。

```rust
// lumino-core/src/event.rs
pub enum DocumentEvent {
    // 音符操作
    NotesInserted { track: usize, range: Range<usize> },
    NotesDeleted { track: usize, range: Range<usize> },
    NotesMoved { track: usize, delta_tick: i32, delta_key: i16 },

    // 轨道操作
    TrackAdded { index: usize, name: String },
    TrackRemoved { index: usize },
    TrackReordered { old_index: usize, new_index: usize },

    // 全局事件
    TempoChanged { tick: u32, new_tempo: u32 },
    TimeSignatureChanged { tick: u32, numerator: u8, denominator: u8 },

    // 选择操作
    SelectionChanged { track: usize, selected: Vec<usize> },
}

// lumino-editor/src/session.rs
pub struct EditorSession {
    document: Document,           // 纯文档数据
    view: EditorView,             // 纯视图状态
    history: History,             // 撤销栈
    gfx_queue: GfxDeltaQueue,     // 渲染增量（自动推导）
}

impl EditorSession {
    /// 唯一的状态变更入口
    pub fn apply(&mut self, event: DocumentEvent) -> Result<(), EditError> {
        // 1. 应用到文档
        self.document.apply(&event)?;

        // 2. 记录历史（自动推导反向操作）
        self.history.record(&event);

        // 3. 推导渲染增量（自动，无需手动 sync）
        self.gfx_queue.push(&self.document, &event);

        // 4. 推导音频增量（自动）
        self.audio_queue.push(&self.document, &event);

        Ok(())
    }
}
```

**消除的代码**：
- 所有 `sync_*` 函数（12 个）
- `note_delta_events`、`note_delta_dirty`、`onion_dirty_tracks` 等冗余字段
- `track_notes_gen` 版本号（事件流本身就是变更记录）

### 2.4 消息系统：统一 Action + Handler Trait

```rust
// lumino-core/src/action.rs
pub trait Action: Send + Sync + 'static {
    fn name(&self) -> &'static str;
    fn can_undo(&self) -> bool { true }
}

pub trait ActionHandler {
    fn handle(&mut self, action: &dyn Action) -> Result<(), ActionError>;
}

// lumino-editor/src/actions.rs
pub enum EditorAction {
    InsertNotes(InsertNotesAction),
    DeleteNotes(DeleteNotesAction),
    MoveNotes(MoveNotesAction),
    SetTool(Tool),
    SetZoom { x: f32, y: f32 },
    // ... 所有编辑操作
}

impl Action for EditorAction {
    fn name(&self) -> &'static str {
        match self {
            EditorAction::InsertNotes(_) => "editor.insert_notes",
            EditorAction::DeleteNotes(_) => "editor.delete_notes",
            // ...
        }
    }
}
```

**收益**：
- 16 个 `*Action` 文件 → 1 个 `actions.rs`（扁平化模块，无 mod.rs）
- 新增操作只需在一个 enum 中加变体
- 可以统一实现撤销/重做（`Action::reverse()`）
- 可以统一实现快捷键绑定（`Action::default_shortcut()`）

### 2.5 渲染管线：PipelineBuilder 抽象

```rust
// lumino-gfx/src/pipeline.rs
pub struct PipelineBuilder<'a> {
    device: &'a wgpu::Device,
    label: &'a str,
    shader: &'a wgpu::ShaderModule,
    vertex_entry: &'a str,
    fragment_entry: Option<&'a str>,
    bind_groups: Vec<&'a wgpu::BindGroupLayout>,
    vertex_buffers: Vec<wgpu::VertexBufferLayout<'a>>,
    targets: Vec<Option<wgpu::ColorTargetState>>,
    primitive: wgpu::PrimitiveState,
    depth_stencil: Option<wgpu::DepthStencilState>,
}

impl<'a> PipelineBuilder<'a> {
    pub fn new(device: &'a wgpu::Device, label: &'a str, shader: &'a wgpu::ShaderModule) -> Self {
        Self {
            device, label, shader,
            vertex_entry: "vs_main",
            fragment_entry: Some("fs_main"),
            bind_groups: vec![],
            vertex_buffers: vec![],
            targets: vec![],
            primitive: wgpu::PrimitiveState::default(),
            depth_stencil: None,
        }
    }

    pub fn vertex_entry(mut self, entry: &'a str) -> Self { self.vertex_entry = entry; self }
    pub fn bind_group(mut self, layout: &'a wgpu::BindGroupLayout) -> Self { self.bind_groups.push(layout); self }
    pub fn vertex_buffer(mut self, layout: wgpu::VertexBufferLayout<'a>) -> Self { self.vertex_buffers.push(layout); self }
    pub fn color_target(mut self, target: wgpu::ColorTargetState) -> Self { self.targets.push(Some(target)); self }

    pub fn build(self) -> wgpu::RenderPipeline {
        let pipeline_layout = self.device.create_pipeline_layout(&wgpu::PipelineLayoutDescriptor {
            label: Some(&format!("{}_layout", self.label)),
            bind_group_layouts: &self.bind_groups,
            push_constant_ranges: &[],
        });

        let pipeline = self.device.create_render_pipeline(&wgpu::RenderPipelineDescriptor {
            label: Some(self.label),
            layout: Some(&pipeline_layout),
            vertex: wgpu::VertexState {
                module: self.shader,
                entry_point: Some(self.vertex_entry),
                buffers: &self.vertex_buffers,
            },
            fragment: self.fragment_entry.map(|entry| wgpu::FragmentState {
                module: self.shader,
                entry_point: Some(entry),
                targets: &self.targets,
            }),
            primitive: self.primitive,
            depth_stencil: self.depth_stencil,
            multisample: wgpu::MultisampleState::default(),
            multiview: None,
            cache: None,
        });

        // 自动注册到资源追踪器
        gpu_resource_tracker::track_pipeline(&pipeline);

        pipeline
    }
}
```

**使用示例**：
```rust
// note_renderer/init.rs —— 从 50 行压缩到 10 行
let pipeline = PipelineBuilder::new(device, "note_pipeline", &shader)
    .bind_group(&globals_layout)
    .bind_group(&note_layout)
    .vertex_buffer(NoteVertex::layout())
    .color_target(wgpu::ColorTargetState { format: surface_format, blend: Some(...), write_mask: ... })
    .build();
```

## 四、风险评估

### 4.1 高风险项

1. **状态管理重构**：`EditorData` 是核心数据结构，改动影响所有编辑操作。建议分阶段：先封装访问器，再迁移到事件流。
2. **Crate 合并**：合并过程中可能出现循环依赖。建议先用 `pub use` 重导出保持 API 兼容，再逐步迁移。
3. **音频层合并**：`midi-io` 有 KDMAPI FFI 代码，合并时需确保 unsafe 边界清晰。

### 4.2 低风险项

1. **PipelineBuilder**：纯新增抽象，不影响现有逻辑，可逐步替换。
2.**Action 合并**：只是代码组织变动，运行时行为不变。
3. **测试补全**：新增代码，不影响现有功能。

## 五、实施原则

1. **先诊断，后动刀**：每个重构项必须有明确的"问题 → 方案 → 收益"链条
2. **保持 API 兼容**：合并 crate 时先用 `pub use` 重导出，避免一次性改完所有调用方
3. **测试先行**：重构前先为目标模块补测试，确保行为不变
4. **小步快跑**：每次 PR 只做一个重构项，方便回滚和 review
5. **度量驱动**：重构前后对比代码行数、编译时间、测试覆盖率
