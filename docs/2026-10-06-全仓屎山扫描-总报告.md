## 🔍 详细发现

### C1. `drain_async_commit` 在 UI 线程无超时忙等 — Critical
- **问题描述**：`while self.editor_state.data.has_pending_commit()` 中 `None` 分支只 `std::thread::yield_now()`。若后台异步提交线程 panic/卡死（或 `has_pending_commit` 永不翻转），该循环永不退出：UI 线程 100% 占核且不可恢复。Save/Play/Export、框选内部按下、LeftEdge/RightEdge 拉伸、Undo/Redo 都会走到这里。
- **影响文件**：`src/impls/editor_impl/commit.rs:318-357`（另有 `interaction/pressed.rs:138,184,208`、`impls/editor_impl/history.rs:29,137` 等调用点）
- **证据**：commit.rs:350-353 `None => { // 避免忙等：让出时间片 std::thread::yield_now(); }`，无 dead-line/超时/失败回滚；`has_pending_commit` 由后台结果驱动。
- **严重程度**：Critical（UI 冻结，杀进程才恢复）
- **最小修复**：给 drain 加超时（如 2s 或 N 次 yield 后）→ 超时走 `tracing::error! + 丢弃 pending + mark_notes_changed` 的降级路径，绝不在 UI 线程无限循环。

### C2. 走带跨轨移动越界目标轨 → 源音符已删、目标插入失败，静默丢音 — Critical
- **问题描述**：移动释放时 `delta_tracks` 由鼠标位置直接取整、**不钳制到轨道数**；`collect_move_sources_and_dests` 计算 `dest_visual = visual_pos + delta_tracks` 后经 `track_visual_order.get(...).unwrap_or(dest_visual)` 得到可能不存在的文档轨索引；`apply_move_internal` 先按索引删源轨，再 `insert_note`，而 `insert_note` 对不存在音轨**返回 false 且被忽略**。
- **影响文件**：`src/arrangement_ops/move_notes.rs:150-192`（171-176 无上界）、`:109-148`（143 忽略返回值）；触发侧 `src/arrangement/interaction/pointer.rs:163-188`（`delta_tracks` 无 clamp）
- **证据**：`EditorData::insert_note` 注释与实现：“音轨不存在返回 false”（`editor-state/.../accessors/write.rs:72-74`，`insert_note_with_id` 返回 None）；move_notes 删源后无回滚。
- **严重程度**：Critical（音符数据丢失，且撤销步只记录部分状态）
- **最小修复**：`dest_visual = min(visual_pos + delta_tracks, track_count-1)`（负值已 max(0)），或在 `apply_move_internal` 对 insert 失败回滚已删项并 `discard_last_history`。

### H1. production 代码存在 `.expect()`（违反仓库硬规则） — High
- **问题描述**：`selection_cache` 快慢路径各一处 `expect`。运行时不变式目前成立（刚判 Some/刚写入），但规则禁止生产 `expect`；一旦未来有人在快路径与 map 之间插入可变借用改写，将 panic 且难定位。
- **影响文件**：`src/arrangement_ops/selection_cache.rs:115`、`:124`
- **证据**：`c.as_ref().expect("快路径已判定 Some，此处必然命中")` / `expect("走带选区缓存刚写入即应命中")`
- **严重程度**：High（合规红线 + 潜在 panic）
- **最小修复**：改用 `Ref::filter_map(...).ok_or` 或返回值改为 `Option<Ref<...>>`，或把缓存改为 `Rc` 返回（该文件 flat 已是 Rc，可直接 Rc::clone）。

### H2. Razor 切割忽略插入结果、仍计成功并广播 — High
- **问题描述**：切分时先 `remove_note`（源音符已删），随后 `let _ = insert_note_with_id(right/left)`。失败时 `split_count += 1` 照加、历史保留、`push_collab_transform_entries` 仍广播“删原+加左右”，对端出现本地不存在的音符；本地则净丢音符。
- **影响文件**：`src/arrangement_ops/razor.rs:116-117,145,147-149`
- **证据**：`let _ = self.editor_state.data.insert_note_with_id(track, right);`（左同理），与 H5 同源的“忽略写入结果”模式。
- **严重程度**：High（静默丢音 + 协作分叉）
- **最小修复**：检查两个 insert 的 `Option`，任一失败则把原音符原样插回并跳过计分/广播（或整体 `discard_last_history` + 返回 0）。

### H3. 粘贴内核忽略实际插入结果，按输入数计成功并广播 — High
- **问题描述**：`apply_clipboard_paste_entries` 与 `insert_grouped_notes` 均接住 `_ids` 但不用，`inserted_count`/`inserted` 直接按输入音符数累加；目标轨不存在时实际 0 写入，界面/日志仍报“已粘贴 N”、协作 `local_notes_added_batch` 广播 N 个本地不存在的音符。
- **影响文件**：`src/clipboard/paste.rs:49-58`、`src/clipboard/paste_interop.rs:171-206`
- **证据**：`let _ids = ...batch_insert_notes_to_track_with_ids(dest_track, &notes); for note in notes.iter() { inserted_count += 1; ... }`；`batch_insert_notes_sorted` 对无轨返回 0（editor-state/.../note_store_ops/insert.rs:95-106）。
- **严重程度**：High（虚假成功 + 协作幻影音符）
- **最小修复**：以 `batch_insert_*_with_ids` 实际返回或插入前后 `track_note_count` 差值为准计数/广播；为 0 的轨不广播。

### H4. first-writer-wins 判定 O(远端指纹 × 本地指纹)，本地指纹与 JSON 无界 — High
- **问题描述**：`is_locked_by_other` 双重嵌套遍历（远端 fingerprints × notes）；`emit_local_selection_changed(true)` 对全部选中调用 `selected_fingerprints()`（O(轨道) 顺序扫描 + Vec 全量）并转 JSON 广播。框选后若协作开启，每次提交路径都会执行；百万/千万级选中时是百 MB 级内存与秒级 UI 阻塞（与 `capture_selection_identity` 的 262,144 上限形成鲜明反差——该路径有上限，指纹路径没有）。
- **影响文件**：`src/note_ops/selection.rs:158-179,244-279,296-326`；调用点 `impls/editor_impl/commit.rs:117,221`、`note_ops/delete.rs:72`
- **证据**：`for sel in ... { for (rtrack,...) in &sel.fingerprints { for (track,...) in notes { ... } } }`；`selected_fingerprints` 直接 `Vec::with_capacity(selected.len())`。
- **严重程度**：High（协作开启 + 大选中 → 可感知卡顿/内存峰值）
- **最小修复**：给指纹/冲突判定设与 `MAX_CAPTURE_ENTRIES` 同源的上限（超出降级为“不锁定/仅基数比较”）；或按 (track,key,tick) 排序后做区间扫描替代双层全比。

### H5. 走带写路径每次手势全文档扫描 — High
- **问题描述**：`arrange_move_notes` / `arrange_delete_selected_notes` / `arrange_apply_speed_change` / `arrange_razor` 的收集函数都遍历 `0..track_count` 的全部音符做命中判定（读路径已有 version 三元组缓存，写路径没有）。19M 音符工程每次拖动释放/删除/变速都要 O(全文档)，是“读路径已优化、写路径仍线性”的结构性不对称。
- **影响文件**：`src/arrangement_ops/move_notes.rs:151-192`、`selection/batch.rs:146-165,245-270`、`razor.rs:61-78`
- **证据**：`for track_idx in 0..doc.track_count() { for (i, note) in editor_data.track_notes(track_idx).iter().enumerate() { if selection.contains(...) } }`；对比 `selection_cache.rs:129-193` 的缓存设计文档（明确承认“全量扫描 12.9ms/10.6ms”的读路径问题并修了）。
- **严重程度**：High（大工程交互级卡顿）
- **最小修复**：收集阶段复用 ArrangeSelection 的矩形范围对每轨做 `window_range` 预筛（选区内 tick 区间 + key 过滤），或让写路径也吃 selection_cache 的 by_track 结果（需在冻结/失效语义上对齐）。

### H6. 画刷/形状工具同一 tick 去重键不含长度，可能吞掉更长音符 — High
- **问题描述**：`confirm_shape_tool` 对切分结果按 `(tick/snap 四舍五入, key)` 去重，键不含长度；`chop_cells` 同行合并切分后首尾残段与后续图形若同 tick 起步、长度不同，`retain` 只保留先出现者（可能较短），生成的覆盖范围小于预览（违反“所见即生成”的宣称）。普通场景不易触发，但与文档承诺相悖。
- **影响文件**：`src/interaction/shape_tool.rs:164-168`（`seen_chopped.insert((...), p.1))` 无 length）
- **证据**：`chopped.retain(|p| seen_chopped.insert(((p.0 / snap_key).round() as i64, p.1)));`
- **严重程度**：High（低概率但直接违背 UI 承诺；属“自证式测试”盲区——预览/生成共用同一权威，测试测不出共享 bug）
- **最小修复**：去重键加 `(p.2 长度)`，或去重时同键保留更长者。

### H7. Ctrl 粘滞：双通道合并只置位不清除 — High
- **问题描述**：`handle_action(Pressed)` 执行 `set_ctrl_pressed(ctrl || self.ctrl_pressed())`。当窗口级 `CtrlKeyChanged(true)` 后因焦点丢失收不到 `false`、而 canvas `ModifiersChanged` 已报 false 时，本行会因 `self.ctrl_pressed()==true` 保持粘滞；后续拖动被误判为 Ctrl 复制，用户须再按一次 Ctrl 才能复位。无明显 UI 反馈。
- **影响文件**：`src/interaction.rs:35-43`（合并点）；`src/grid/state.rs`/`program_impl.rs:143-146` 注释自述该双通道为焦点丢失兜底
- **证据**：OR 合并仅能“置位”，无“双方均 false 则清除”的收敛逻辑。
- **严重程度**：High（交互状态机粘滞，非崩溃但普遍可感）
- **最小修复**：改为双通道独立存储 + `ctrl = window_ctrl || canvas_ctrl` 的每帧合成，或为该 Pressed 分支使用“以本次事件 ctrl 为权威、窗口通道仅补充 true”的策略并在 Release/Blur 时清除。

### H8. 浮动层互斥：右键菜单打开时文字输入覆盖层被静默吞掉 — High/Medium（结构隐患）

- **影响文件**：`src/rendering.rs:155-171,213-231`；状态位于 `edit_view`/`text_tool`
- **证据**：两个 `if` 顺序早退，无 `match overlay_priority` 或互斥断言；`@recent 改动`（浮动层互斥）仅体现为分支顺序。
- **严重程度**：High（结构性问题，新增浮动层必然踩坑）→ 实际用户影响偏 Medium
- **最小修复**：抽 `OverlayKind` 枚举与单一优先级函数（返回 `Option<Element>`），并在打开菜单时显式 `text_tool.end_editing()` 或反之禁止菜单；加一条“同帧至多一个 overlay”的 debug 断言。

## 三、详细发现

### 🔴 Critical

#### C1. 异步批量移动与「切换音轨」竞态：把 A 轨结果整轨写进 B 轨（静默数据损坏）

- **问题描述**：`apply_move_ops_async` 在启动时从**当时的 current_track** 克隆整轨并生成 MoveOps，但结果落盘 `poll_async_commit` 使用的是**轮询时刻的 `self.current_track`**，`PendingCommit` 不记录 track_id；而 `Editor::switch_to_track` 无任何 `has_pending_commit`/`is_editing` 守卫，侧边栏点轨 → Runner `TrackSelect` 直接切轨。用户在批量拖动松手后的异步窗口内点击另一条音轨，后台结果就会把旧轨的完整音符数组 `replace_track_notes` 到新轨，覆盖 B 轨全部音符；且 B 轨被覆盖没有对应的历史条目（历史只推入 A 轨 MoveOp），常规 Undo 无法找回。
- **file:line**：
  - `crates/editor/editor-state/src/editor_state/editor_data/async_commit.rs:56`（克隆旧轨）、`:115`（`replace_track_notes(self.current_track, result.notes)`）
  - `crates/editor/ui-editor/src/track.rs:16`（无守卫切轨）
  - `src/runner/menu/file.rs:225`（侧边栏 TrackSelected → `set_current_track(track_idx, true)`，无 is_editing 检查）
- **证据**：`has_pending_commit` 仅被用于拖拽手势/协作延迟/Undo 拦截（`ui-editor/src/impls/editor_impl/commit.rs:28,50,109`、`pressed.rs:137`、`released.rs:149`），全仓 grep 无「切轨时检查 pending commit」；`poll_async_commit` 五处使用 `self.current_track`，`PendingCommit` 结构体（async_commit.rs:34-39）只有 ops/receiver。
- **最小修复（二选一）**：
  1. `PendingCommit` 增加 `track_id: usize`（`apply_move_ops_async` 时捕获），`poll_async_commit` 用该字段写回；若 `track_id != self.current_track` 则更新对应轨并跳过/修正事件与历史语义；或
  2. `switch_to_track` 开头加 `if self.editor_state.data.has_pending_commit() { return; }`（或先同步 flush poll 完成再切），并在 Runner 层同时拦截。
  建议 1+2 都做（数据层自洽 + UI 守卫）。
- **影响面**：批量框选拖动（最常用大规模编辑）在 1600 万音符工程下异步窗口可达数百 ms，触发概率不低；后果是整轨不可逆丢失。

### 🟠 High

#### H1. `apply_move_ops`：删除成功但插入失败时静默丢音符；计数表达式恒等于 `deleted`

- **file:line**：`crates/editor/editor-state/src/editor_state/editor_data/history/ops.rs:130-144`
- **证据**：
  ```rust
  if self.remove_note(track_id, idx).is_some() { deleted += 1; }
  ...
  let inserted = ...doc.batch_insert_notes(track_id, news)...;
  modified += deleted.min(inserted.max(deleted)); // = deleted，恒等
  ```
  `batch_insert_notes` 在 `track_id >= notes.len()` 或 `notes.is_empty()` 时返回 0（`crates/audio/midi-model/src/document_edit.rs:58-79`）。当文档轨数因远端删除/工程状态变化少于 MoveOp 的 track_id 时，旧音符已被删除、新位置未写入，Undo/Redo 后音符永久丢失，且函数仍返回 `modified>0` 让上层认为成功。
- **最小修复**：插入返回 0 时回滚（把已删 `olds` 重新插回），返回错误/0 并 `tracing::error!`；同时把恒等式改为显式 `modified += deleted`（或 `deleted.min(inserted)`，按语义二选一），消除误导性表达式。

#### H2. `GpuNoteBuffer::upload_all` 忽略 `grow()` 失败，超硬件上限时越界写 buffer

- **file:line**：`crates/editor/gfx/src/gpu_note_buffer/ops/upload.rs:55-84`；`crates/editor/gfx/src/gpu_note_buffer/internal.rs:33-92`
- **证据**：`if instances.len() > self.capacity { self.grow(instances.len()); }`（返回值被丢弃）；随后无条件 `instance_count = upload_count` 并 `queue.write_buffer(buffer, 0, 全量数据)`。`grow` 的注释写「若超出硬件限制，create_buffer 会返回错误」，但 wgpu 的 `Device::create_buffer` **不返回 Result**（超限走 validation error/panic 通道）；一旦 `max_buffer_size` 或 binding 上限约束失败，仍会向旧的小 buffer 写超量数据 → wgpu 校验错误，整个渲染线程/进程风险。
- **最小修复**：`grow()` 返回 `false` 时必须截断/返回错误（或把 `upload_all` 改为返回 `Result<(), UploadError>`），禁止在容量不足时调用全量 `write_buffer`；把 `max_capacity` 超限分支改为真实早退。

#### H3. 生产代码 `expect()`（AGENTS.md 红线）：MidiConsole 回读超时/失败直接 panic

- **file:line**：`crates/editor/gfx/src/midiconsole_renderer/render.rs:300-302`
- **证据**：`rx.recv_timeout(30s).expect("map_async 回调未收到").expect("map_async 失败")`；该文件其余逻辑做了有界等待（正确），但失败路径是生产 `expect`。gfx 全仓生产代码仅此一处 `expect`（其余都在 `#[cfg(test)]` 内），属规范红线且发生在视频导出链路。
- **最小修复**：返回 `Result<Vec<u8>>`/`Option<Vec<u8>>`，失败记 `tracing::error!` 并交由导出管线报错；如需保留 panic 语义，至少在调用方捕获并转用户可见错误。附带：`let staging = device.create_buffer_init(...&vec![0u8; N])` 每帧新建 + `out` 全图 CPU 拷贝，可并入对象池（Medium）。

#### H4. `push_update_range` 用 `iter().skip(start).take(...)` 记录增量 → 大文档 O(start) 热路径

- **file:line**：`crates/editor/editor-state/src/editor_state/editor_data/accessors/write.rs:313-328`
- **证据**：`self.current_track_notes().iter().skip(start).take(end - start + 1)`。`ChunkedList::iter()` 返回 `impl Iterator`，未覆写 `nth`（`crates/audio/midi-model/src/chunked_list.rs:257`），标准 `Skip` 适配器逐元素推进。拖动/变速/翻转/批量编辑的 `record_update_ranges` 都会走这里；文档中另有 `push_update_range_event`（history/ops.rs:211）使用 `iter_window` 的 O(log+range) 正解，此处属遗漏。
- **最小修复**：改用 `iter_window(start, end + 1)`（与 ops.rs 同源），成本 O(块定位 + 区间)。

## 四、可疑但核实安全（防误报清单）

1. **`SwappableBuffer` 全部 unsafe 指针访问**（`swappable_buffer/unsafe_access.rs`）：三槽打包状态 CAS + writer/ready/reading 物理隔离 + 写端读端协议，调用契约与文档一致；测试覆盖 basic/多次 swap/持引用 swap/peek/三态不变量。结论：契约式安全；但依赖调用方遵守「唯一写者/唯一读者」，且未见 CI Miri 证据（模块头要求 Miri 扫描）——建议把 Miri 加入 CI，属流程改进而非缺陷。
2. **`export_pipeline/staging.rs:249,258` 的 `ptr::copy_nonoverlapping` + `set_len`**：拷贝前已校验 `result.capacity() >= total_unpadded`，padded 分支逐行 dst 偏移不超总量；读回对象池 `clear()` 后使用。结论：容量与生命周期前置成立。
3. **`automation_lanes: Vec<Arc<AutomationLane>>` 写时复制**：全仓 grep 确认所有变更路径均经 `Arc::make_mut`（`automation.rs:131,156,200,221,243,274`），快照 `clone()` 为指针拷贝。结论：COW 语义正确，历史测试有指针共享断言（tests_history.rs:58-73）。
4. **`grow_visible_buffer` 换 buffer 后 bind group 失效疑虑**：`prepare.rs:204-231` 在扩容后立即重建 cull/render bind groups 并重写 uniforms；`update_cull_info` 的调用点均聚集在 upload/绑定路径。结论：重建时序正确。
5. **note_renderer 深度区域化（0x00800000/0x1F800000 位模式）**：CPU 孪生 + shader 源码契约测试 + 64 帧顺序置换像素证据 + chunk_start GPU 折叠验证；软渲染适配器能力门控是有意跳过而非吞错。结论：当前实现自洽。
6. **`arrangement_instances` 视觉轨/文档轨映射**：ghost 取色经 `track_order` 映射回文档轨，泳道定位用视觉位置，测试覆盖非恒等映射/静音/越界；与 `selection_cache` 指纹、`track_visual_order` 全链路一致。结论：映射正确。
7. **`remove_notes_merged` 降序区间合并**：手工验证 `merge_descending_ranges` 与 `descending_ranges_from_selection` 在 [10,9,8,5,4]、跨段场景输出正确；越界裁剪逻辑完备。
8. **测试代码中的 unwrap/expect/panic**：全部位于 `#[cfg(test)]` / `tests/`，符合 AGENTS.md 豁免；生产代码 `.unwrap()` 扫描为 0。
9. **`miditrail_renderer`/`waterfall_renderer` 的 `rebuild_bind_group` 调用点**：均在 buffer 句柄可能变化后的 prepare/render 前置调用，调用点集中。
10. **`document_edit.rs` 的 `track_max_end_ticks` Mutex**（跨仓只读佐证）：双重 `lock()` 之间非原子但仅缓存写入，最坏多算一次 max_end，无正确性风险。

## 2. 🔴 Critical（立即处理）

### C1. 工程保存无原子性：写盘中途崩溃/断电即损坏现有工程文件

- **文件**：
  - `crates/core/project/src/project/save.rs:117-122`（`save_to_archive` 直接 `std::fs::write(path, archive_bytes)`）
  - `crates/core/project/src/project/save.rs:22-114` + `folder.rs:110-119`（文件夹形态逐文件原位覆盖，无临时目录 + 原子替换）
  - 调用方：`src/runner/menu/file/save.rs:321-357`（用户 Ctrl+S 覆盖原 `.lmpj`）、`src/runner/cloud_save.rs:87`、`src/runner/menu/window/collaboration.rs:54`
- **证据**：`save_to_archive` 先把整个归档构建到内存，再对目标路径执行一次 `fs::write`——`fs::write` 会先截断文件；
  写入过程中进程被看门狗 `abort/SIGKILL`（内存监控在加载 MIDI 期间会强杀！见 `watchdog.rs:229`）、断电、磁盘满，
  都会留下 0 字节或半截 `.lmpj`，**直接摧毁用户唯一副本**。文件夹形态同理（`write_track` 逐轨覆盖，中途失败 = 音轨新旧混杂）。
- **影响**：数据丢失，且保存路径正是用户原工程（Ctrl+S 覆盖保存），无备份回退。
- **最小修复**：
  1. `save_to_archive` 改为 `path.with_extension("lmpj.tmp")` 写入 → `fs::File::sync_all()` → `fs::rename(tmp, path)`（同卷原子替换；Windows 用 `ReplaceFileW` 或先 `rename` 旧文件为 `.bak`）。
  2. 文件夹形态：先写 `path.tmp-{pid}` 目录，成功后 `rename` 整个目录交换（Windows 上先 rename 旧→`.bak`，再 rename 新→目标，失败可回滚）。
  3. 失败时保留 `.bak` 并在 UI 提示；不得静默。
- **工作量**：0.5–1 人日 + 2 个回归测试（模拟写入中途失败）。

### C2. LMPJ 归档解析器对损坏/恶意文件会 panic（越界 slice），CRC 只写不验

- **文件**：`crates/core/project/src/project/archive.rs`
  - `:228-230` `let ft_data = &archive_bytes[ft_start..ft_end];`——`file_table_offset/compressed_size` 来自文件头，未做上界/溢出校验
  - `:240-242` `let data = &archive_bytes[start..end];`——条目 `data_offset/compressed_size` 同样未校验
  - `:205` `FileTable::decode` 中 `&bytes[pos..]`——`pos` 由前序条目长度累加，可越界
  - `:281,289` CRC32 在写入时计算并存储；**读取路径从未调用 `compute_crc32`**，`file_table_original_size` 也从未校验
- **证据链**：`load_project` 对任何用户选择的 `.lmpj` 直接 `std::fs::read` + `load_from_archive`；
  一个被截断/手改的归档（比如只保留头部 55 字节 + 伪造的 `file_table_offset = u64::MAX`）会触发数组越界 panic。
  debug 下 panic，release 下 64 位加法溢出也可能 panic（`usize` 溢出在 release 不检查，但 slice 索引仍 panic）。
  应用虽有 panic hook 写崩溃日志，但用户体验是"打开工程 = 程序崩溃"，且违反仓库 `NEVER panic` 规则。
- **影响**：稳定性/安全边界（文件解析属不可信输入路径）。同类问题：`FileEntry::decode` 的 `bytes.len() < pos + path_len + ...` 加法未用 `checked_add`。
- **最小修复**：
  1. 引入 `checked_add` + 上界校验的统一 helper（如 `slice_at(bytes, offset, len) -> Result<&[u8]>`），全部替换 3 处裸索引。
  2. `FileTable::decode` 循环内对 `pos` 做 `pos.checked_add(consumed).filter(|p| *p <= bytes.len())`。
  3. 读取时校验 CRC（对 `stored_data` 计算比对）与 `*_original_size`，不一致返回 `CoreError::FileFormat`。
  4. 头部 `version` 校验（当前只写不读；未来格式演进需要）。
- **工作量**：0.5 人日 + 4 个畸形文件单测（fuzz 建议接入 `cargo-fuzz` 或至少 proptest）。

### H2. CollaborationService 连接状态竞争：二次 connect 被吞、disconnect 后客户端"复活"

- **文件**：`src/services/collaboration_service.rs:100-122`（connect 把 client 放进 Mutex 后，后台任务立即 `guard.take()`）、
  `:152-159`（连接完成后无条件放回）、`:326-340`（disconnect 只拿 Mutex 中现存 client）
- **证据**：
  1. 后台任务在第 110 行把 client **移出** Mutex，连接期间 `is_connected()/send_*` 全部看到 `None`；
     若用户在上一连接未完成时再次点击连接，`connect()` 开头 `disconnect_async()` 在 Mutex 里找不到 client，
     随即 `*self.lock_client()? = Some(client)` 存新 client，但上一任务仍持有旧 client 并在完成后覆盖回 Mutex →
     **两个连接任务竞争同一个槽位，先完成者被后完成者覆盖，被覆盖的连接对象被 drop（连接泄漏/状态错乱）**。
  2. `disconnect()` 期间若后台任务已 `take()`，则 disconnect 拿不到 client、只发信号；任务收到信号退出 `select!` 前
     已在 152-159 行把 client 放回 → **用户以为已断开，`is_connected()` 仍可能为 true**。
  3. `disconnect_tx` 槽位被新 connect 覆盖时旧 `oneshot::Sender` 被 drop，旧任务依赖 `Err(RecvError)` 结束——行为未定义文档化。
- **最小修复**：把"连接中"状态显式建模（`enum ClientSlot { Idle, Connecting(token), Connected(client) }`），
  连接任务持有 token，完成时仅当 token 仍为当前 token 才提交；disconnect 使 token 失效并广播。
  任何时刻 client 不离开服务结构，或引入 `generation` 计数。
- **工作量**：1–1.5 人日 + 单测（用 `tokio::test` 模拟 connect/disconnect/connect 交错）。

## 🟠 High（8）

### H1. GPU 合成管线仅支持立体声；Mono 导出产出错误音频

- **问题描述**：render/mix WGSL 与缓冲区布局全部按 2 声道硬编码；`readback()` 对 mono 配置按 `data.len()/4` 截获**交错立体声**前 `block` 个样本，当作单声道写出；limiter 也按 `out.len()/2` 解释。导出后端映射 `AudioChannelMode::Mono → ChannelMode::Mono` 后，只在写出时告警不降混。
- **影响文件**：
  - `crates/audio/gpu-synth/src/gpu/shaders/render.wgsl:3-4`、`mix.wgsl:110,182-183`
  - `crates/audio/gpu-synth/src/synth/engine/render.rs:46-56,91`
  - `crates/audio/gpu-synth/src/synth/engine/limiter.rs:19`
  - `crates/tools/export/src/audio/gpu_backend/synth_config.rs:22-25`
  - `crates/tools/export/src/audio/gpu_backend/render.rs:239-243`
- **证据**：`output[f*2]/[f*2+1]` 固定；`ChannelMode::Mono` 无任何 shader/引擎分支；导出侧仅 `tracing::warn!`。
- **严重程度**：High（用户可选配置产出错误音频：声道交替/调制失真，而非降混）
- **最小修复**：二选一并加护栏——（a）mix.wgsl 按 `mix_params.channels` 输出单声道 + limiter 分支；（b）GPU 后端强制 Stereo 并在 `write_gpu_result_to_sink` 前做标准降混，`validate()` 拒绝 Mono 直传。

### H2. limiter 在 `block_size < 256` 时切片下溢 panic（配置合法却崩）

- **问题描述**：`limit_block` 以 `LOOKAHEAD=256`（帧）为延迟线，末尾固定执行 `raw[raw.len() - LOOKAHEAD*2..]`；当 `block_size*2 < 512` 即 `block_size < 256` 时索引为负 → panic。`SynthConfig::validate` 只要求 `>=16`；设置页 LGS 缓冲区提供 64/128；`GpuSynth` 是公共 API，任何调用方都可触发。
- **影响文件**：
  - `crates/audio/gpu-synth/src/synth/engine/limiter.rs:18,49-51,68,153`
  - `crates/audio/gpu-synth/src/config.rs:200-205`
  - `crates/editor/ui-settings/src/pages/audio/lgs.rs:59-60`（2^6..2^13）
- **证据（可达性校正）**：`ApiKind::Lgs` 全仓**无构造点**（仅 `lib.rs:357` match 分支），LGS 后端当前未接线，故暂为潜在雷；导出 GPU 路径固定 `block_size: 512` 安全。
- **严重程度**：High（一步之遥的生产 panic；配置面已开放）
- **最小修复**：`validate()` 增加 `block_size >= 256`（或 `>= 2*LOOKAHEAD/2`）并给出可操作错误；或在 `limit_block` 中 `if raw.len() < LOOKAHEAD*2` 时以零填充延迟头。

### H3. 离线渲染复位不完整 → 同一引擎连续渲染串音

- **问题描述**：`render_midi_parsed` 的复位清单缺 `pending_mix_events`、`limiter_gain`、`limiter_tail`、`channels`（音量/表情/声像 lerp 状态）。上一次渲染遗留的 CC7/11/10/8 延迟事件会在新渲染首块生效；limiter 的增益与 1ms 延迟尾巴会把上一作品的声音带入下一篇开头。streaming 路径清了 `pending_mix_events`，但同样不清 limiter/通道状态。
- **影响文件**：
  - `crates/audio/gpu-synth/src/synth/engine/offline.rs:33-46`
  - `crates/audio/gpu-synth/src/synth/engine/streaming.rs:73-89`
- **严重程度**：High（离线导出连续性正确性；同一实例被导出工具复用时必然命中）
- **最小修复**：抽 `reset_for_offline_render()` 统一包含 `pending_mix_events.clear()`、`pending_events.clear()`、`limiter_gain=1.0`、`limiter_tail.clear()`、`channels` 重建（或直接复用 `reset_channel_state()`），两个入口共同调用。

### H4. `MidiFile::parse` 的 tempo 段未全局排序，多轨 tempo 映射错误

- **问题描述**：pass 1 按"轨道优先"顺序 push `tempos`，随后直接构建前缀和 `tempo_segs`（隐含要求 tick 升序）。type-1/2 文件中 tempo 分布在多轨（合法 MIDI）时，`tempo_segs` 非单调，`partition_point` 定位错误 → tick→sample 映射错误（速度/时长错）。流式路径 `MidiStream` 在 `parse.rs:197` 有 `sort_by_key`，双路径语义不一致。
- **影响文件**：
  - `crates/audio/gpu-synth/src/midi/parser.rs:76-123`（缺排序；公开字段 `MidiFile.tempos` 也未排序）
  - 对照：`crates/audio/gpu-synth/src/midi/stream/parse.rs:197`
- **严重程度**：High（离线渲染与流式渲染/参考输出对不齐；常见"tempo 只在 track0"文件不受影响）
- **最小修复**：pass 1 后 `tempos.sort_by_key(|&(t, _)| t);`（稳定排序 + 既有循环对同 tick 重复段的零长度处理即可保持"后者生效"语义），并同步排序公开的 `tempos`。

### H5. 流式 MIDI 每事件克隆 `tempo_segs`（O(事件 × tempo 数) 分配）

- **问题描述**：`MidiStream::next_event` 每次投递事件都 `self.tempo_segs.clone()`（以及 `rewind` 一次），把 tempo 表整体拷贝到局部再调用 `ticks_to_sample`。百万级事件 + 数百 tempo 段时是纯 memcpy 风暴。
- **影响文件**：`crates/audio/gpu-synth/src/midi/stream/midi.rs:127-131`（`rewind` 的 `:98` 可接受）
- **严重修复**：`ticks_to_sample` 改为接收切片，或先把 `&self.tempo_segs` 的借用拆出（先算 `sample` 再改 `streams/heap`），消除逐事件克隆。

### H6. 每次编辑快照全量重建当前轨播放堆（黑 MIDI 编辑卡顿）

- **问题描述**：`set_document` 无条件调用 `rebuild_queue_from_current_track(None)`，后者遍历当前轨**全部**音符并 push 2N 个 `ScheduledEvent` 进 `BinaryHeap`（`reserve(2N)`）。黑 MIDI 当前轨数百万音符时，每次编辑（每个快照）都 O(N) 建堆，UI 编辑明显卡顿——与模块注释宣称的"消除大块拷贝"目标相反。
- **影响文件**：
  - `crates/audio/midi-io/src/playback/engine/control/core.rs:130-169,249-299`
- **最小修复**：当前轨与其它轨统一走"文档 + 游标"流式路径（其它轨已是），编辑时只钳制游标；至少在 `set_document` 中检测"同文档指针 + 同 current_track"时跳过全量重建。

### H7. 循环回绕每次 O(seek 位置) 重建 pending_offs

- **问题描述**：`handle_loop_wrap` 对每个非当前轨执行 `notes.iter().enumerate().take(state.note_cursor)`，把 loop_start 之前的**全部**音符扫一遍筛出 end_tick 未结束者。循环片段位于大文件尾部时，每次回绕 O(N)（数百万次迭代），可造成周期性卡顿/丢音。
- **影响文件**：`crates/audio/midi-io/src/playback/engine/control/state.rs:278-301`
- **最小修复**：以 `loop_start - max_note_length` 为下界用 `partition_point` 起步扫描；或维护"活跃音符"集合随游标增量更新，回绕只做集合内筛选。

### H8. 剪贴板/压缩载荷的预分配 DoS

- **问题描述**：`decode_clipboard` 直接以 19 字节头里的 `count`（u32，可达 42.9 亿）做 `Vec::with_capacity` → `ClipRecord` 约 16B，恶意载荷可诱导 ~68GB 预分配（Rust OOM abort）。Domino 路径同类：`ZlibDecoder` + `Vec::with_capacity(expected.max(64))`，expected 来自 u32 且解压无上限。
- **影响文件**：
  - `crates/audio/midi-model/src/clipboard.rs:289-295`（另 `:230-258` 分块路径安全）
  - `crates/audio/midi-model/src/clipboard/domino.rs:99-111`
- **最小修复**：预分配前与载荷长度夹紧（如 `min(count, bytes.len()/min_record_len)`）；解压侧设置输出上限并用 `take()` 限流，超限报错。

## 🔍 详细发现

### 🔴 High

#### H1. 音频 `FfmpegSink` stderr 管道不排空，长导出可死锁
- **问题描述**：非 WAV 音频导出（MP3/FLAC/OGG/WavPack）把 ffmpeg 的 stderr 设为 `Stdio::piped()`，但只在 `wait()` **之后**才读 stderr；命令参数没有 `-nostats/-loglevel`，ffmpeg 会持续向 stderr 写进度统计。管道缓冲区（Windows 约 4–64KB）写满后子进程阻塞在 stderr 写入，父进程阻塞在 `wait()` → 经典管道死锁。按 ffmpeg 0.5s/次统计估算，长导出（约 8 分钟以上）即可能触发；编码失败输出大量 stderr 时同样可能。
- **证据**：`crates/tools/export/src/audio/stream.rs:221-223`（stderr piped）、`stream.rs:241-269`（`process.wait()` 后才读 stderr）、`stream.rs:199-219`（args 无 `-nostats`）；对照视频路径 `crates/tools/export/src/video/ffmpeg.rs:71-99` 专门开线程实时排空 stderr —— 同一仓库两种口径，音频路径为缺陷方。
- **影响文件**：`crates/tools/export/src/audio/stream.rs`
- **严重程度**：High（用户可感知的导出永久挂起）
- **最小修复**：启动时 `stderr(Stdio::piped())` + `std::thread::spawn` 持续读取并保存尾部 N 行（复用视频侧实现）；或最简在 args 加 `-nostats -loglevel error`；或在非诊断场景直接 `Stdio::null()`。
- **预期收益**：消除长导出死锁；错误诊断改为有界保留，防内存增长。

#### H2. 协作断连静默 + 自动重连只有配置没有实现
- **问题描述**：WebSocket 后台循环在 `Close / 读错误 / 流结束` 时 break 并设置 `Disconnected/Error`，**从不 `emit_event(CollaborationEvent::Disconnected)`**（该事件变体存在但全仓无人发出）。UI 收不到断连通知；同时 `RECONNECT_INTERVAL_MS`、`ClientConfig.auto_reconnect`、`max_reconnect_attempts` 三个"自动重连"承诺项无任何消费点（grep 仅定义与测试）。结果：网络抖动后协作静默失效，必须人工重连。
- **证据**：`crates/network/collaboration/src/client/connection.rs:161-177`（Close/Err/None 分支只 set 状态并 break，无事件）、`connection.rs:213-217`（shutdown 同样无事件）；`client/event.rs:12`（`Disconnected` 变体）；`lib.rs:28`（`RECONNECT_INTERVAL_MS`）、`types/client.rs:19,36`（`auto_reconnect`/`max_reconnect_attempts`）在 `src/` 全仓无消费；`src/services/collaboration_service.rs:91-92` 明确把它们置为 `true/5`。
- **严重程度**：High（跨端协作静默掉线、无法自愈）
- **最小修复**：在 break 前 `emit_event(Disconnected)`（带原因）；实现重连循环（或至少删除误导性配置字段并在 UI 层轮询 `is_connected()` + 明确重连按钮语义）。
- **预期收益**：断线可见、可恢复；消除"配置承诺 ≠ 行为"的信任债。

#### H3. 云存储无重试；FTP/SFTP 无超时，死连接会永久挂起
- **问题描述**：`CloudManager` 所有操作经 `rt.block_on` 同步执行，失败仅把状态标 `Failed`，**没有任何重试/退避**（全仓 `retry|backoff|重试` 无命中）。FTP（suppaftp）与 SFTP（russh `Config::default()`）均未设置连接/读写超时；服务器假死或链路黑洞时，后台执行线程与 `block_on` 永久阻塞，连接状态停留 `Connecting/Failed`，既不超时也不自愈。WebDAV 有 10s/60s 超时，形成协议间行为不一致。
- **证据**：`crates/network/cloud/src/manager.rs:100-124`（无重试/超时）、`manager.rs:169-245`（block_on 直通）、`manager.rs:231-245`（仅记录 Failed）；`ftp.rs:66-88`（`FtpStream::connect` 无超时）、`sftp.rs:71-77`（`SshConfig::default()` 无 `inactivity_timeout/keepalive`）；`webdav.rs:32-33,62-72`（唯一有超时的协议）。
- **严重程度**：High（网络异常时云操作永久挂起、无自愈）
- **最小修复**：统一超时（suppaftp `set_read_timeout/set_write_timeout`、russh `Config { inactivity_timeout, keepalive_interval, .. }`）；在 `handle_io_result` 失败分支实现有限次指数退避重试（仅幂等读操作默认重试；写操作重试需幂等保护）。
- **预期收益**：网络/服务器异常可恢复；状态机不会卡死。

## ✅ 可疑但核实安全（防误报清单）

1. **`render_loops.rs:38` 的 `unsafe { memmap2::Mmap::map(&file)? }`**：mmap 期间源 MIDI 文件被外部改写会 UB，但导出是短生命周期、路径由用户选择；无 SAFETY 注释属文档债，不构成当前缺陷。
2. **`processor.rs:122` `bend.as_int() as u16`**：负值 as u16 仅用于诊断日志 `a` 字段展示，不参与音频计算（真正的归一化在 `pitch_bend_normalized`，有回归测试）。
3. **`event_stream.rs` 同 tick RPN 数据先于选择的"病态保序"**：已用测试锁死为 2026-10-03 决策，属有意行为，不是 bug。
4. **midly `u4::from(u8)` 不会 panic**：核实 midly 0.5.3 `primitive.rs` 为 `from_int_lossy`（mask），故 M6 是"静默截断"而非崩溃；`event_kind.rs:12` 另有 `& 0x0f` 显式防御。
5. **`about_egg.rs` / `echo_cave.rs` 的进程级 `AtomicBool` 全局状态**：测试用静态互斥串行化 + `into_inner` 容错；生产语义（重启恢复）与需求卡一致，非共享状态缺陷。
6. **`collaboration` 的 `Ordering::Relaxed`（ClientStateCell）**：状态为离散枚举，注释已论证无跨变量临界区，且 CAS 测试覆盖；`control.rs` 的 Relaxed 则因与 Condvar 组合列入 M8。
7. **`cloud/crypto.rs` 密文测试"篡改末字符"仍可靠**：base64 解码后 GCM 认证标签必校验失败，测试有效。
8. **`extras` 构建脚本 `include_bytes!` 相对路径 + `OUT_DIR` 复制**：文件名排序保证确定性；`escape_str` 对常见字符有效（换行场景见 L4）。
9. **`ui-settings/panel.rs` 中大量 `parse_setting` 静默忽略非法输入**：注释明确为"保持旧行为"，是产品决策；仅 Tempo 自定义入口缺 finite 校验（M11）。
10. **`dialog/windows.rs` transmute 原始 WndProc**：注释与测试覆盖坐标解析，`transmute` 生命周期在子类化约定内成立；生命周期管理问题另列 M12。
