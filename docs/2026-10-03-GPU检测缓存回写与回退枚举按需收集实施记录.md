## 三、实现要点

### 3.1 三态诊断策略（调研 §4-P0-1 选项 A）

```rust
// crates/editor/gfx/src/device_check/check.rs
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum FallbackDiagnostics { Never, OnFailure, Always }

pub(crate) fn fallback_adapters_with<F>(when: FallbackDiagnostics, passed: bool, enumerate: F)
    -> Vec<GpuAdapterSummary>
where F: FnOnce() -> Vec<GpuAdapterSummary>
{
    match when {
        FallbackDiagnostics::Never => { /* debug 日志 */ Vec::new() }
        FallbackDiagnostics::OnFailure if passed => { /* debug 日志 */ Vec::new() }
        FallbackDiagnostics::OnFailure | FallbackDiagnostics::Always => enumerate(),
    }
}
```

- `check_inner(when)` 的 3 个收集点（原 `:106` / `:139` / `:171`）统一走它；通过路径先把
  `let passed = failure.is_none();` 提出来，保证「通过 ⇒ 不枚举」在**任何**策略下都成立；
- `enumerate` 以闭包注入 → 决策与 IO 解耦，**「通过路径零枚举」成为可确定性断言的行为**（验收 1 的插桩证据，不需要 GPU）；
- 启动门控映射（`device_gate.rs`）：

```rust
fn fallback_diagnostics(policy: device_check_policy::StartupCheckPolicy) -> FallbackDiagnostics {
    if policy.show_warning { FallbackDiagnostics::OnFailure } else { FallbackDiagnostics::Never }
}
```

即：**失败且要弹警告窗**才收集（`failure_detail` 要用它拼「可能仍可运行」），
**通过路径 / 静默失败路径**一律不收集——正是调研 §4-P0-1 的结论。

### 3.2 实施偏差：删除旧签名，改为必填参数（五步纪律之「删除」）

调研稿建议「保留旧签名 = 永远收集，避免误伤其它调用方」。实施时全仓核对：

```
grep 结果（改动前）：run_check_with_timeout 的调用方仅
  src/runner/lifecycle/device_gate.rs、src/runner/menu/window.rs、device_check/tests.rs
  check_gpu_support() 的调用方：0 个（仅再导出）
```

「其它调用方」并不存在，保留的理由消失，于是：

```rust
// 之前（调研稿建议）                     // 现在
pub fn check_gpu_support() -> …            pub fn check_gpu_support(when: FallbackDiagnostics) -> …
pub fn check_gpu_support_with(when) -> …   （合并）
pub fn run_check_with_timeout(timeout) -> …      pub fn run_check_with_timeout(timeout, when) -> …
pub fn run_check_with_timeout_with(t, when) -> … （合并）
```

理由：留着「默认 Always」的旧签名，后来者一个无心调用就把本卡省下的 ~0.5s 又花回去，
正是本卡要消灭的那类隐形开销；**必填参数让每个调用点显式声明自己的场景**，
与 UI-008「用 API 收紧做编译期防回归」的既有手法一致。4 个名字收敛成 2 个，API 面更小。

### 3.3 事件载荷带指纹 + 主线程回写（调研 §4-P0-2 选项 A）


## 七、风险与遗留

1. **语义变更（需知悉）**：手动检测**失败**会覆盖此前 `passed=true` 的缓存 ⇒ 此后每次启动都会全量检测，
   直到某次检测通过。这正是卡面要的「刷新缓存」，同时修掉了调研 §2.2 场景 2（手动发现的失败被
   旧缓存掩盖、下次启动直接放行）——但它是用户可感知的行为变化，发布说明里应写一句。
2. **`NoAdapter` / `Timeout` 失败**：`report.fingerprint` 为 `None`，回写会把指纹清空 ⇒ 下次启动必然全量检测（自愈），
   与启动门控既有行为一致，非本卡引入。
3. **静默路径日志**：不再包含回退后端列表；如需排查「要求后端缺失但有 DX12」，让用户开「启动时显示 GPU 兼容性警告」
   或走设置页手动检测即可（两条路径都保留回退诊断）。
4. **未处理（调研 §7）**：`enumerate_fallback` 仍会先枚举要求后端再过滤（可再省几十毫秒）、
   超时后探测线程 detach 的既有遗留——均不在本卡范围。
5. **未提交**：本次改动停留在工作区，未 `git add` / 未创建分支；提交信息建议
   `perf(gpu,device-check): 手动检测回写缓存并按需收集回退后端诊断`（GPG 签名按仓库规范）。
