# XSynth 实时引擎治理与性能修复记录（2026-09-19）

## 背景

96kHz + 重型音色库（TWGMD Remake VI）+ 超密黑乐谱（Bad Apple 3.14M，331 万音符）
实时播放出现：声部爆炸、冻结长音、间歇性停滞、音频落后进度条、爆音。
经过一整天逐层 RCA，最终定位到 **9 个独立根因**，全部修复并验收通过。

## 前期思路（IMT11D 方案敲定记录，09-19 00:16–00:24）

> 以下为方案提出者（IMT11D）当时的沟通要点整理，作为本记录的前期思路背景。

- **实时阶段必须严格控制 voices，不能用 per-key / per-channel 上限来管**：
  "我不认为实时播放的时候做 max voice per key 或者 max voice per channel 是个好主意"；
  "渲染的时候这很好用，但是实时播放一定要设定一个硬上限，这个硬上限是执行过程中必须始终存在的"。
- **顶破引擎最大功率会进入正反馈循环导致音频崩坏**：
  "你的 Voices 一旦顶破引擎的最大功率……接下来就会陷入一个正反馈循环导致你的音频彻底崩坏"。
- **方案：用户设总上限，实际执行收敛到 1−1/e（63.2%）**：
  "允许用户设定总的 Voices 上限，但是实际执行的时候把它控制在 1−1/e 这个比例（大概 63.2%）的范畴内"。
  依据来自**一阶系统的响应时间**；更激进的 1−1/e²≈86.5% 余量只有 13.5%，容易顶破，不建议采用。
- **峰值顶破时的第二机制：追时间而不是保听感**：
  "引入另外一个机制去追时间而不是保证听感，即使卡、没法听、爆音、炸，也要糊过去"，
  红线约在**上限的 1.5 倍**启动，作为保险措施。
- **易用性取舍**：per-channel 不灵活、per-key 不直观，实时层面改回**全局 Voice**；
  渣机 voices 资源少没办法接受；VirtualMIDISynth / Omnimidi 用户通常也不会用几千 Poly（除非要"全损音质"）。

### 与最终实现的对应关系

| IMT11D 前期思路 | 最终实现 |
|---|---|
| 全局硬上限始终存在 | `xsynth_global_voice_limit`（自动 = 10000），全局共享资源池 |
| 运行时目标 63.2% | `xsynth_voice_target_ratio` 默认 `1−1/e`；运行目标 = ratio × 硬上限 |
| 峰值突破时"追时间"保险 | 保命闸（可选，默认关）：持续负载 >1.0 或单块尖峰 >2.0 立即限流；另有紧急模式直接丢弃 + 队列冲洗 |
| 不用 per-key / per-channel | 每通道上限关闭；每键同音数保留为可选（默认不限） |
| 一阶系统依据 | 目标 = ratio × 硬上限；负载自适应限速收缩/恢复（每块 ≤1%） |

| 5 | **"推迟/丢弃新音符"语义错误**：撞上限后推迟并补发旧音 → 碎片化、音频落后进度条 | "一下一下往前蠕动"、"间歇性断档" | 改为**抢旧不丢新**：预算耗尽时先抢占最不重要的旧声部（T1/T2 短淡出）再让新音符发声 | `2ae59e7` |

| 7 | **洪峰注入窗口**：单块 drain 4096 事件 ×16 通道，1M NPS 洪峰在闸门触发前注入数十万音符 | 卡 3–4s 后恢复 | 单块注入封顶（256/通道/admit）+ 瞬时 `load>2.0` 立即开闸 | `ca0ba81` |
| 8 | **播放器"迟到补发"**：`tick <= 播放头` 无迟到判断，播放线程停顿/跳变后把区间内所有过时音符一次性补发 | 爆破点后持续衰减的噼啪声 | `LATE_NOTE_SKIP_SECS=0.15`：进度条领先 150ms 以上的音符直接跳过（不发 NoteOn、不登记 NoteOff） | （lumino 侧） |
| 9 | **洪峰尾料逐块消化**：紧急模式退出后残留 NoteOn 在正常模式被"抢一个放一个"；管道硬删无淡出 | 爆后持续噼啪 | 紧急模式进出边沿整队列冲洗（丢弃残留 NoteOn 并配对取消 NoteOff）；上限回收统一软抢占（1ms 淡出），硬删仅留给 L4 看门狗 | `b65aedc` |

## 最终语义（已验收）

- **连续播放优先**：每个新 NoteOn 都会发声；撞上限时抢占最旧/最轻/释放中的声部（1ms 淡出），
  即"顶到上限有硬切、但音乐不断"。
- **全局上限**：用户设 `xsynth_global_voice_limit`（None=自动 10000），
  运行目标 = `xsynth_voice_target_ratio × 上限`（默认 `1 − 1/e ≈ 0.632`）。
- **负载自适应**：持续轻度过载会自动缓慢降目标（多切旧声部），轻载后缓慢恢复；
  瞬时尖峰不触发。
- **保命闸**（可选，默认关）：负载持续 >1.0 或单块尖峰 >2.0 时临时限流 NoteOn，
  回落后自动解除；关闭时不存在任何 NoteOn 丢弃路径。

## 性能基线（96kHz，TWGMD Remake VI，Ryzen 9 9950X3D）

| 场景 | 结果 |
|---|---|
| release 实时管线，Auto 并行 | 0.45 µs/声部/块（4480 声部 → load 0.20） |
| release 实时管线，串行 | 4.7 µs/声部/块（约 10 倍慢，验证并行生效） |
| 离线标定台（Auto） | 0.48 µs/声部/块；27k 声部 → load 1.36 |
| app（debug + xsynth opt-level 3） | V=7700 → load 0.74；V=1925 → load 0.20 |
| 洪峰（1M NPS 瞬时） | 保命闸兜底，load_peak 从 1.97 降到 1.05，3–4s 停滞压缩到秒级内 |

## 已知限制

- 声部资源是**全局共享池**：单通道与多通道共用同一 `soft` 目标，通道数量不改变资源分配；
  超过引擎实时容量时表现为按规则切旧声部/限流，不做"全音符实时"。
- V 上限的实际容量 ≈ 按 0.5–1.0 µs/声部/块反推（本机 96kHz 约 1–2 万声部为 load 1.0 边界）。

## 验收记录

用户实测（cap 自动 + ratio 0.77 + 保命闸开）：
- 连续无断档，撞上限按预期切最旧声部（乱切旧声部可接受、不允许断档）；
- 瞬时 1M NPS + 3W Poly 洪峰在保命闸下挺过，恢复后**无噼啪残余**；
- "迟到即弃"生效：进度条领先超过 150ms 的音符不会被延后补发。
- 结论：**验收通过**（2026-09-19）。

## 逐提交说明（交付版）

> 每条给出：**问题 → 改动 → 证据/验证**。哈希为补签名后的最终值。

### Phase A：实时播放可用性（2ee23ec → 3378b3b）

- **`2ee23ec` fix(control): RPN/NRPN 与 MIDI 规范对齐并统一 128 精度**
  问题：RPN/NRPN 解析与 MIDI 规范的精度/语义存在偏差，自动化音色参数不可靠。
  改动：`core/src/channel/control.rs` 重写 RPN/NRPN 状态机（+27/-8）。
  证据：note-core/midi-io 回归通过（后续实时展开基于此）。

- **`642a1d6` feat(realtime,soundfonts): NPS 限流可配置（0=不限）与音色库重采样并行化**
  问题：NPS 限流常开导致黑乐谱大量丢音；音色库加载 117.5s 阻塞启动。
  改动：`max_nps=0` 关闭限流；SF2 重采样 rayon 并行（`soundfonts/src/sf2/sample.rs`）。
  证据：用户实机初始化 **117.53s → 14.1s**。

- **`bcd0976` fix(core): 缓冲渲染保持至少一个渲染块的富余**
  问题：提前量守卫按 `last_requested × 110%` 计算，尖峰下提前量不足 → 实时欠载卡顿。
  改动：守卫改为"至少保留一个完整渲染块"。
  证据：用户实机卡顿缓解。

- **`771beda` fix(core): 音频回调不再阻塞 + 加深缓冲富余**
  问题：音频回调阻塞在 `recv()`；2 块富余仍不足以吸收调度抖动。
  改动：改 `try_recv()` 非阻塞；富余加深；samples 计数修正。
  证据：用户实机流畅度提升。

- **`93cb1f6` feat(realtime,core): 渲染块与缓冲解耦**
  问题：块大小同时承担"事件量化"和"抗欠载目标"两个角色，互相牵制。
  改动：`render_window_ms` 固定 10ms（保时序）；新增 `cushion_ms` 独立缓冲目标。
  证据：用户实机验收"不卡顿"。

- **`98a84c8` feat(core): 每通道声部上限治理**（历史阶段）
  问题：无限声部增长导致负载爆炸；上游无每通道治理。
  改动：`ChannelInitOptions.max_voices` + 超限释放最老声部（保留最新音符）。
  证据：首次出现"有界声部"行为；后续被全局方案取代。

- **`f721206` perf(core): 声部上限治理改增量统计**
  问题：治理本身 O(V) 全量扫描，形成"治理卡死"。
  改动：增量统计键级声部数。
  证据：治理开销消失。

- **`3378b3b` fix(core): 声部治理改按缓冲长度硬移除**
  问题：循环采样 `ended()` 永远为 false，活跃计数虚高、声部无界增长。
  改动：以缓冲长度为准，超限硬移除最老组。
  证据：用户实机"**可以了，流畅了，顶到上限有硬切**"——首个被用户接受的版本。

### Phase B：去丢音与全局治理（ee4154e → ae72cd2）

- **`ee4154e` feat(core): 分级抢占（T0 已杀 → T1 释放中最轻 → T2 最轻）+ 短淡出死期限**
  问题：无差别硬切会切掉自然声部；循环采样滞留。
  改动：分级选择 + 1ms 淡出 + 2 块死期限强制移除。
  证据：低音段部分回归。

- **`e0cc413` fix(core): 抢占跳过已 Kill 声部**
  问题：重复"抢占"已 Kill 组导致活跃计数虚降、治理失效（声部反而暴涨）。
  改动：T1/T2 只从活跃组选择。
  证据：治理重新生效。

- **`b3c8a8a` feat(realtime,core): 彻底移除 NPS 丢音路径 + 治理器运行时诊断**
  问题：上游 NPS 限流是最大丢音源（黑乐谱 75%+ 被丢）。
  改动：sender 无 NPS 分支；NPS 追踪线程 disabled；`[GOV]` 诊断。
  证据：日志确认"关闭时不存在任何 NoteOn 丢弃路径"。

- **`4811c9f` feat(realtime,core): 跨通道全局声部上限**
  问题：`max_voices` 语义是**每通道**，15 通道文件实际预算 ×15。
  改动：渲染管线统一调度 `Steal` 命令，跨通道按最忙通道分摊。
  证据：Parallel Universe Shifter（15 通道）不再按通道放大。

- **`ae72cd2` feat(realtime,core): 自适应负载治理（1−1/e 软目标 + L1~L4 + 看门狗 + 可选软 NPS 闸）**
  问题：需要"用户设硬上限、运行目标留暂态余量、过载有多级保命"的完整框架。
  改动：`Governor`（+201 行）、`EmergencyGate`（+142 行）、配置三项、看门狗。
  证据：单元测试；**教训**：首版负载反馈收缩过猛（25%/块）导致塌缩自激，被 `a0e07c5` 修正。

### Phase C：自激、计数与预算模型（bbab5ce → 56d713d）

- **`bbab5ce` fix(realtime): 治理器收缩限幅 + 单块抢占配额**
  问题：一次尖峰把软目标从 6185 砸到 64，随后"每块都在抢"自激。
  改动：收缩 ≤8%/块且仅在 V 构成压力时；单块抢占配额 `clamp(V/20,16,256)`。
  证据：日志 `soft` 不再塌到地板。

- **`a6bd4d3` feat(realtime): 通道级 NoteOn 入场控制**
  问题：长块 → 事件积压 → 下一块全量注入（数万音符）→ 更长块（雪崩）。
  改动：按预算接纳 NoteOn，超额推迟。
  证据：V 被钉在预算内（但暴露后续配对缺陷）。

- **`a0e07c5` fix(core,realtime): 权威声部计数 + 静态软目标**
  问题：共享计数靠渲染后差值对账，硬抢占下失真（日志：每秒硬抢 2000+，V 不动）；
  负载反馈与抢占成本互相激励（自激）。
  改动：`VoiceBuffer` 全增删点同步 `AtomicU64`；目标固定 = ratio × 硬上限。
  证据：计数与真实缓冲区一致；V 不再虚高。

- **`3103e47` fix(realtime,core): 入场控制改推迟+配对取消；固定预算除数**
  问题：扣住 NoteOn 把后续 NoteOff 一并堵死 → 声部永不释放（冻结长音）。
  改动：NoteOff 直通并与 deferred 配对；预算除数固定。
  证据：暂停后 V 回落（后续 `4e612df` 进一步修正配对）。

- **`56d713d` fix(realtime): 入场预算改全局共享池**
  问题：按通道均分预算与"全局资源池"语义矛盾，单通道文件被误伤（只拿 1/16）。
  改动：全局 `AtomicI64` 预算池，通道按需原子取用。
  证据：用户确认"全局上限就应该全局共享"。

### Phase D：连续播放语义与负载自适应（4e612df → ca0ba81）

- **`4e612df` fix(realtime): NoteOff 按发声计数配对**
  问题：撞墙后"同键有 deferred 就吞 NoteOff"，把**在响音符**的 NoteOff 吃掉 →
  循环采样永不结束 → 时间冻结、V 钉死。
  改动：每键 `sounding` 计数，键上有在响音符时 NoteOff 必须直通。
  证据：暂停后 V=2，冻结长音消失。

- **`9d7603e` fix(realtime): 推迟音符加 TTL 丢弃**
  问题：无限推迟后补发旧音 → 音频落后进度条（"蠕动"）。
  改动：推迟 >30ms 直接丢弃。
  证据：滞后消失；后因语义仍不够"实时"而被 `2ae59e7` 取代。

- **`2ae59e7` feat(realtime): 声部上限改"抢旧不丢新"语义（核心）**
  问题："推迟/丢弃新音符"必然把音乐切成碎片。
  改动：预算耗尽时先抢占最不重要的旧声部（T1/T2 短淡出）再让新音符发声；
  删除 defer/TTL；新增 `voice_load` 实时基准。
  证据：用户实机"**终于好了！可以切，没有间歇性断档**"。

- **`b82956a` feat(realtime): 负载自适应目标（限速+迟滞+地坂）**
  问题：V ≤ 目标但 load 略超 1 时无作为（"抢速度而不是杀音符"）。
  改动：load>0.9 持续 200ms → 每块 ≤1% 收缩；load<0.6 持续 1s → 缓慢恢复；地坂 5%。
  证据：headless（CAP=20000）目标自适应收敛 ~8.5–16k，load 均值 0.72，无塌缩/振荡。

- **`ca0ba81` perf(realtime): 洪峰停滞压缩**
  问题：1M NPS 洪峰在闸门触发前注入数十万音符，卡 3–4s。
  改动：瞬时 `load>2.0` 立即开闸；单块注入封顶 256/通道（原 4096）。
  证据：load_peak **1.97 → 1.05**，无秒级停滞。

### Phase E：洪峰余波治理（507f800 → b65aedc）

- **`507f800` fix(realtime): 紧急模式直接丢弃新音符**
  问题：洪峰后积压排空期"抢一个放一个"，连续 1ms 淡出叠加 = 电锯音。
  改动：洪峰/开闸/持续重载进入紧急模式（迟滞），新 NoteOn 直接丢弃并配对取消 NoteOff；
  队列加速排空。
  证据：用户实机恢复正常段落连续（残余噼啪由下一条解决）。

- **`b65aedc` fix(realtime): 洪峰回收改软抢占 + 紧急模式边沿整队列冲洗**
  问题：紧急模式退出后残留 NoteOn 被逐块消化；管道硬删无淡出成片 pop。
  改动：上限回收统一软抢占（1ms 淡出，硬删只留给 L4 看门狗）；
  紧急模式进出边沿整队列冲洗（丢弃残留 NoteOn）。
  证据：用户实机"**问题解决**"——噼啪残余消失。
