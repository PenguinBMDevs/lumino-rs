# xsynth-realtime 后端性能扫描与修复记录

- 扫描对象：`../xsynth-Lumino`（fork）+ 接入层 `crates/audio/midi-io`
- rev 变化：`3e52bfc`（扫描基线）→ `0d21c17`（本轮修复，已推送 origin/master）

## 1. 接入层面（Lumino ↔ xsynth-realtime）

### 1.1 【P0】>16 逻辑核走进"自我否决"的线程策略

`crates/audio/midi-io/src/api/xsynth.rs`：

```rust
const MIDI_CHANNEL_RENDER_THREADS: usize = crate::constants::MIDI_CHANNEL_COUNT as usize; // 16

fn forced_thread_count(logical_cores: usize) -> LuminoThreadCount {
    if logical_cores > MIDI_CHANNEL_RENDER_THREADS {
        LuminoThreadCount::Manual(logical_cores)   // ← 池化 + 关批渲染
    } else {
        LuminoThreadCount::None                    // ← 无池 + 开批渲染
    }
}
```

这条分支同时触发两个后果：

1. `RealtimeSynth::open` 里 `build_channel_pool(Manual(n))` → `Some(Arc<ThreadPool>)`，且该 `Arc` 被 **16 个通道共享**（`prepare_channels` 内 `channel_pool.clone()`，同一 `Arc`）。每个通道 `pool.install(|| key_voices.par_iter_mut()…)` 抢同一个池；
2. `set_batch_render_available(matches!(config.multithreading, ThreadCount::None))` → `Manual` 时为 `false`，**fork 的旗舰优化 B1 批渲染被整体关闭**，且 spawner 不再构造 batch voice。

而代码注释自己给出了实测结论：

> 共享 rayon 池最坏单块 0.96~4.6s（队头阻塞：块耗时取决于最晚完成的通道）；无池最坏单块 0.14~0.57s
> 故 ≤16 核一律用 `None`。>16 核场景暂无实测数据……上线后应在高核机器上复测尾延迟

也就是说：**20/24/32 线程的机器（i9-13900K/14900K、7950X/9950X、几乎所有高端桌面）恰好全部落在"作者自己承认没测过、且已知更差"的路径上**，并且这条路径会顺带关掉批渲染。12 核（本机）走的是好的那条，问题被掩盖了。

- 影响：高核机器上黑 MIDI 实时性显著劣化、尾延迟不可控；CI/低核开发机无法复现。
- 修复（1 行，可先止血）：`forced_thread_count` 恒返回 `None`（或在 >16 核上先用 `None` 与 `Manual` 做 A/B，以数据决定，而不是以"额外核可用"的推理决定）。
- 验证：在 ≥17 逻辑核机器上跑 `realtime/examples/perf_nps.rs` / `voice_load.rs`，对 `ThreadCount::None` 与 `Manual(n)` 两档比 `average_renderer_load` 与**最坏单块时间**（均值会掩盖队头阻塞）。

### 1.2 【P0】缓冲区设置被静默钳到 100ms

```rust
// api/xsynth.rs:209-210
rt_config.render_window_ms = 10.0;
rt_config.cushion_ms = opt.buffer_ms.max(100.0);   // ← 地板 100ms
```

```rust
// crates/editor/ui-settings/src/pages/audio.rs:237
iced_widget::slider(5.0..=100.0, settings.synth.xsynth_buffer_ms, |ms| { … })
```

UI 暴露 5–100ms，后端把 `buffer_ms` 一律抬到 ≥100ms。后果：**5–99ms 整段滑块是安慰剂**，用户把"缓冲区"拉到最小仍在 100ms + 设备缓冲的延迟上。这不是微优化问题，是"设置不生效"级别的问题。

- 修复方向：显式对齐两侧口径——要么 UI 下限改 100 并改文案，要么后端尊重用户值（配合 §1.3 的调度改进，低缓冲才不会破音）。
- 顺带：`XSynthOptions::sample_rate`（`midi_manager.rs:233` 传入）在 `init_synth` 里**完全未被使用**（真值取自 cpal 设备，`api/xsynth.rs:240`）；日志里打印的 `xsynth_sample_rate` 与真实采样率不一致，容易误导排障。

### 1.3 【P1 · 已修】渲染线程 pacing 自旋

`core/src/buffered_renderer.rs` 的缓冲等待循环原为 `spin_sleep::sleep(delay / 10)`（0.9ms）。
`spin_sleep` 的语义是"粗睡 + **尾部自旋到 deadline**"，而它的 Windows 精度阈值
（`sleep_accuracy()`，1.2.1 实测路径）是 **700µs**——0.9ms 仅略大于阈值，于是每次调用都
退化成"内核睡 0.2ms + 自旋 0.7ms"。渲染线程在稳态下几乎全部时间都停在这个循环里，
遂变成常驻自旋。

播放线程（`playback/manager.rs:144-148`）的 `sleep(700µs)+spin(300µs)` **经实测不成立**作为
问题：见 §4.2，实际只烧 2.1–2.8% 单核、tick 周期 1.11ms，**不改**。

### 1.4 【P1】生产者无界、消费者有硬上限

- 生产端：播放线程每 1ms 把 `engine.update()` 出的一批事件经 `flush_midi_messages` 逐条推入，通道队列是 `crossbeam_channel::unbounded()`（`realtime_synth.rs:631`）。
- 消费端：每个通道每渲染块只 `admit()` 两次，每次上限 `DRAIN_CAP = 256`（`:702-704`，紧急模式 4096）。即**正常模式吞吐上限 = 512 事件/块/通道**。

按 16 通道 × 100 块/秒换算：**总量上限 ≈ 81.9 万事件/秒**。超过后：

1. 队列无界增长（事件积压、延迟漂移、内存无界）；
2. 负载超过阈值进入"紧急模式"，`flush_epoch` 递增 → 通道整队列冲洗（单次最多丢弃 16384 个残留 NoteOn，`:727`）→ **成片丢音**；对黑 MIDI 编辑器这是功能性缺陷。
3. 更糟的是负反馈：过载 → 单块变长 → 每秒块数下降 → 消费上限进一步下降 → 队列更长。

fork 注释里自己写了"洪峰（1M NPS）"，而 1M NPS 恰好是上述上限的 1.2 倍以上。

- 修复方向：给队列一个**显式容量与显式背压策略**（bounded + 生产端丢最旧/合并），并让 `DRAIN_CAP` 成为"每块软预算"而非"吞吐天花板"（例如按剩余块时长动态放宽，或把事件按块预分桶）；同时把"丢音"从紧急模式的副作用改成**可观测**的计数器，而不是静默。

### 1.5 【P1】音频回调线程与公开 API 共用一把 `Mutex`

```rust
// realtime_synth.rs:1174-1179（音频回调内）
let mut guard = crate::profiling::tracy_zone!("audio_lock", { buffered.lock().unwrap() });
guard.read(&mut output_vec);
drop(guard);
```

```rust
// realtime_synth.rs:469-474（公开 API）
pub fn get_stats(&self) -> RealtimeSynthStatsReader {
    let data = self.data.as_ref().unwrap();
    let buffered_stats = data.buffered_renderer.lock().unwrap().get_buffer_stats(); // ← 同一把锁
```

同一把 `Arc<Mutex<BufferedRenderer>>` 还被 `set_buffer()`（`:553`）使用。当前 `XSynth::stats()` 在 Lumino 里**没有任何调用点**（只有 `api.rs:15` 的 re-export），`set_buffer` 也没有调用点，所以现今是"未争用"状态——**这是运气，不是设计**：实时音频线程绝不应该与任何非实时线程共享互斥量。一旦 UI 想显示 buffer/load（这是迟早的事），或配置变更调用 `set_buffer`，UI 线程被抢占的那一刻就是音频 underrun。

- 修复方向：把回调需要的状态（`remainder` + 无锁 SPSC 环形缓冲）与统计信息分离；统计走独立无锁/弱一致通道（原子 + 快照），`set_render_size` 走原子（已经是原子）或"下一块生效"的命令通道。

### 1.6 【P2】每个 MIDI 事件一把 Mutex

```rust
// api/xsynth_output.rs:30-35
fn send_event(&self, event: SynthEvent) {
    self.sender.lock().unwrap_or_else(|e| e.into_inner()).send_event(event);
}
```

`Arc<Mutex<RealtimeEventSender>>` 的 `Mutex` 只服务于"设备热插拔时整体替换 sender"这一个低频事件，却被放进了**每事件**路径（`note_on`/`note_off`/`send_raw`…）。同类问题还有 `get_channel_levels()`：播放线程每 1ms 调一次，锁 `mixer` 并把 16 个原子读出来（`playback/manager.rs:122-125`），而 `ChannelMix` 内部本来就是原子——外层 Mutex 只为重建语义服务。

- 修复方向：`arc_swap::ArcSwap<RealtimeEventSender>` / `ArcSwap<Vec<ChannelMix>>`，读端零锁；或把"重建"改成对同一内部结构做原地热替换。

### 1.7 【P2】默认路径不是单位增益（−3dB）

```rust
// realtime_synth.rs:226-237
let left  = ((1.0 - pan) * 0.5f32).sqrt() * gain;
let right = ((1.0 + pan) * 0.5f32).sqrt() * gain;
```

`pan = 0`（默认）时 `left = right = 0.707`，即**默认对每个通道的每个样本乘 0.707**（测试 `apply_channel_mix_gain_and_pan` 明确断言了 center = √0.5）。等功率声像律本身没错，但对于"每个 MIDI 通道都是一路独立素材"的合成器，center 应当单位增益（0dB pan law），否则用户把音量拉到 100% 得到的仍是 −3dB，且与 GPU 后端存在固定电平差。

- 建议：与 `crates/audio/gpu-synth` 的默认电平口径对齐后再定（这属于"听起来更小"类投诉的根因候选）。

### 2.2 【P1】过载路径上的锁

`EmergencyGate::allow()`（`gate.rs:73-94`）在闸门启用时**每个 NoteOn 取一次 `Mutex`**。闸门恰好只在重度过载时启用——也就是最不该出现锁竞争的时刻，而调用者是发送事件的播放线程。`realtime_synth.rs:932` 里命令通道用 `send(...).unwrap()`（`:932`、`:938`），生产者被 kill 时会 panic，热路径上的 `unwrap` 属于稳定性风险（AGENTS.md 亦明令生产代码不得 `unwrap`）。

### 2.3 已确认"做得对"的部分（避免误伤）

- `tracy` 未启用时 `tracy_zone!` / `tracy_frame!` 展开为原 block，**零开销**（`realtime/src/profiling.rs:19-25`）；`#[cfg(feature="tracy")]` 的 `count_voices()` 同理。
- `LUMINO_BATCH` 默认开、`LUMINO_BATCH=0|false` 可秒级回退，A/B 机制健全（`core/src/voice/batch.rs:57-70`）。
- 每键上限抢占改走 1ms 淡出、`is_past_end` 符号修复等，都是有实测依据的收敛。
- `cushion_target_interleaved` 的量纲对齐（`buffered_renderer.rs:24-30`）修掉了"立体声下缓冲只剩一半"的真实 bug。
- 播放引擎的 `reused_messages`（`engine/control/core.rs:81`）确实避免了每帧新分配。

## 3. 一次被数据否掉的优化设想（保留记录）

初读代码时我认为"每通道每块 3 趟全缓冲扫描（`apply_channel_mix` → `max_abs` → `sum_simd`）"值得融合成 1 趟。写基准复刻后：

- 维持累加语义前提下（`prepapre_cache_vec` 的清零**不可省**，因为 `sum_simd` 是 `+=`），把 mix 融进 sum：1.000s 音频仅省 0.11–0.27ms（≈0.01–0.03% 单核秒）；
- 真正的大头在 `max_abs` 那一趟（A 3.23ms vs C 0.71ms），但它是 UI 电平表所需，不是可删的浪费。

**结论：不立项。** 保留该判断是为了避免后续有人重复投入。

## 4. 实测数据

基准环境：Windows / 12 逻辑核 / rustc 1.98.1 `-O -C target-cpu=native`；
实时参数一律取 Lumino 实际值：48kHz 立体声、**10ms 渲染块**、**100ms 缓冲目标**。

### 4.1 渲染线程 pacing 自旋 A/B（本次修复的核心证据）

测量台：`realtime/examples/pacing_cpu.rs`（新增，随本次改动入库）。
它用**零成本静音管道**驱动真实 `BufferedRenderer`，消费者按实时节奏读取，
读到的样本带恒定电平——**任何非该电平的样本都说明音频回调没拿到数据（真实欠载）**。
因此同一进程内同时给出「CPU 成本」与「是否爆音」两个指标。

| 版本 | 进程 CPU / 3s 墙钟 | 常驻核数 | 稳态欠载样本 | 启动期缺样 |
|---|---|---|---|---|
| 修复前（`spin_sleep::sleep(delay/10)`） | 0.141 / 0.172 s | **4.7% / 5.7%** | 0 | 960 |
| 修复后（`native_sleep` + 有界余量） | 0.000 s | **0.0%** | 0 | 960 |

- 修复后 CPU 低于测量分辨率（`GetProcessTimes` 100ns 粒度）；
- **欠载画像逐位一致**（启动期仅 1 个块的空缓冲，属设计固有，与改动无关）→ 听感零损失；
- 安全不变量已固化为单测 `cushion_wait_never_drains_below_one_block`
  （睡眠后缓冲至少还剩一个整块，结构上不可能欠载）。

### 4.2 播放线程时基（**否证了我自己的 P1 结论**）

复刻 `playback/manager.rs:144-148` 的 `sleep(700µs) + spin(300µs)`，2000 tick：

| 项 | 实测（两次） |
|---|---|
| `thread::sleep(700µs)` 实际耗时 | min 816µs / **avg 1086–1131µs** / max 1542µs |
| `thread::sleep(1ms)` 实际耗时 | min 1030µs / avg 1418–1460µs |
| tick 实际周期 | **1.11–1.12ms** |
| 进入自旋的 tick | **155–162 / 2000（≈8%）** |
| CPU | 0.047–0.063s / 2.24s = **2.1–2.8% 单核** |

结论：Windows 上 `Sleep` 已能给出 ~1ms 精度（不存在代码注释担心的 15.6ms 量化），
自旋只在 8% 的 tick 上被触发。**原报告"常驻烧 30% 单核"是错的，已撤销该结论并放弃改动**
——动了它就要冒改动音符下发时机（=听感）的风险，ROI 为负。

### 4.3 逐块簿记成本（合成负载，结论：不是瓶颈）

48kHz / 立体声 / 10ms 块 / 16 通道 / 每通道 320 声部（合计 5120，接近默认软目标 0.632×10000）；窗口 = 1.0s 音频。

| 项 | 复刻内容 | 耗时/窗口 | 占单核秒 |
|---|---|---|---|
| A | 16×[清零 + `apply_channel_mix` + `max_abs`] + `sum` + master `max_abs` | 3.23 ms | 0.32% |
| B | mix 融进 sum（保留清零与 `max_abs`） | 2.96 / 3.13 ms | 0.30% |
| C | 同上但去掉逐通道 `max_abs` | 0.71 ms | 0.07% |
| D1 | `remove_ended_voices` 式 `VecDeque` 重建（1600 次/窗口，46 万次 push） | 8.87–10.26 ms | 0.89–1.03% |
| D2 | 改 `retain` 原地压缩 | 6.63–11.19 ms | 0.66–1.12% |
| E | `render_batched` 扁平索引 Vec + 每 chunk `Vec`（6.4 万次 chunk 分配/窗口） | 3.38–5.28 ms | 0.34–0.53% |
| F | 每 NoteOn 一次 `exclusive_classes` Vec | 0.048–0.072 µs/事件 | 100 万事件/秒 ≈ 5–7% 单核（分摊到 16 通道后 ≈0.3–0.45%/通道） |
| — | **A+D+E 固定簿记合计** | **≈15.5–18.8 ms** | **≈1.55–1.88%** |

读数说明与自我修正：
- D1 vs D2 在两次运行中**符号相反**，差异落在噪声内 → 不能说"retain 更快"，只能说"重建分配不是可观成本"；
- F 的上界只在有 exclusive class（打击乐）时才成立，无 exclusive class 时 `collect()` 不分配 → 实际更低；
- 因此**分配类优化一律降级为 P3**，本报告的 P0/P1 全部与分配无关。基准源码：`%TEMP%\xsynth-scan\bookkeeping_bench.rs`（临时文件，未入库）。

## 5. 建议的验证路径（改前必测）

1. **>16 核线程策略 A/B**（对应 §1.1）：`ThreadCount::None` vs `Manual(n)`，指标取**最坏单块时间**与 `average_renderer_load` 的 P99，而不是均值；顺带盯 `audio_buffered_samples`（tracy plot 已存在）。

3. **洪峰丢音计数**（§1.4）：把 `flush_epoch` 冲洗与 `dropped[key]` 计数导出为可观测指标，跑一个 ≥80 万事件/秒的测试文件，确认"丢多少、在哪丢"。
4. **CPU 空转基线**（§1.3）：空闲播放 60s，测进程 CPU 时间；改后应显著下降。
5. 复测低核（≤16）机器确保不回退——这是本次改动的主要风险面。
