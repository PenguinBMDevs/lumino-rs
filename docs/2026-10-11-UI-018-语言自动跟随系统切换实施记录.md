## 3. 实施中新发现的坑（调研阶段未预见）

### 3.1 🔴 调研 §7 的「覆盖率危机」是**误报**——仓库有第二套 i18n + CI 门禁

调研阶段我用「扫描含中文字符串字面量」的口径，得出「翻译 277 条 vs 硬编码中文 1132 行 / 209 文件，
英文用户会看到大面积中英混排」，并把它写成「本卡真正的成本」。

实施时一动手就撞墙：`crates/core/core/src/i18n.rs` 是一个 **gettext 风格运行时目录**
（`tr!` / `trf!` 宏，**原文即 key**），配 11 个分域静态表（约 839 条登记 / 101 KB），
且 `catalog.rs:476` 有**覆盖率 CI 门禁** `test_every_call_site_key_is_translated`——
每一处 `tr!("…")` 都必须登记英文，缺一条就红。

也就是说：**那些中文是 key，不是缺口**。正确口径下：

| 口径 | 数值 |
|---|---|
| 编译期结构体表 | 288 条（146 + 142） |
| 运行时目录调用点 | 1198 处（`tr!`/`trf!` 1119 / 171 文件 + `i18n::tr(…)` 79 / 14 文件） |
| 残留（未走任何机制的中文字面量） | 505 行 / 152 文件，抽样证明主要是**日志、内部追踪标签、规范数据值（显示侧走 `tr_dyn`）、已翻译的函数式取词** |

**动作**：重写调研 §7，并在该节留下修正记录与「可复用教训」——**统计 i18n 覆盖率前先确认仓内是否已有门禁，
别自己造扫描器；「原文即 key」的设计会让「扫中文」这种口径把已翻译的调用点全部算成缺口。**
`[PUA生效 🔥]` 发现结论反向时第一时间回写文档而不是留着漂亮数字——调研报告错了不丢人，把错的结论留在仓里等人踩坑才丢人。

### 3.2 启动日志的时序坑：文件日志层在配置加载之后才接上

调研 §8 的 P0-4 写「在 `inner.rs:258` 前后打日志」，我一开始图省事放在了 `ConfigWrapper::new` 里
（更靠近解析点）。真机跑完去翻日志文件——**没有那一行**。

根因：`logging::init()` 只装 subscriber，文件层要等 `start_file_logging()` 拿到
`config.ui.log_retention_count`（**依赖刚加载出来的配置**）才激活；而 `ConfigWrapper::new` 正好在它之前。
放在配置层的 `info!` 只进 stderr，**用户回传的日志文件里永远看不到**——而这行恰恰是排障刚需。

**修正**：`ConfigWrapper` 新增 `language_source` 字段 + getter，日志移到 `inner.rs` 的文件日志启动之后。
`[PUA生效 🔥]` 凡是「加日志」，必须去**真实产物**（日志文件）里确认它落地了——在终端看到一行绿字不等于用户拿得到。

### 3.3 用户真实配置恰好是 legacy「`language: en-US`」——朴素实现会静默改掉它

本机 `config.json` 里是 `"language": "en-US"` 且**没有** `language_preference` 字段。
若按「最省事」的做法（把 `language` 的 serde default 换成系统检测），这个用户的英文界面
**下次启动就会被系统语言（zh-CN）改回中文**——用户选择静默丢失，且他从来没点过任何语言选项。

这正是调研 §6.2 迁移矩阵要防的坑，而它**不是假想**：验证机上的真实配置就是这种形态。
真机 A 组日志（§2）直接证明现在走的是「老配置保留」分支。

### 3.4 macOS 菜单重建的安全性必须在依赖源码上确认（本机无法编译该平台）

`install_menu()` 会「先装新菜单、旧菜单随后在赋值时释放」。本机是 Windows，
`#[cfg(target_os = "macos")]` 代码**根本不参与编译**，凭直觉改等于裸奔。

去读 `muda 0.17.2` 源码确认两点后才有把握：
`init_for_nsapp()` = `NSApplication::setMainMenu(Some(new))`（`mod.rs:211-214`，会替换主菜单）；
`impl Drop for Menu` 只清理 **GTK** 结构（`mod.rs:69-77`），**不会**调用 `setMainMenu(None)`
（那是从未被调用的 `remove_for_nsapp()`）。结论写进了 `install_menu` 的文档注释。

### 3.5 小坑：clippy `field_reassign_with_default`

测试辅助函数里 `let mut ui = UiConfig::default(); ui.language = …;` 被
`clippy::field_reassign_with_default` 拦下（本仓 `-D warnings`）。改为结构体更新语法
`UiConfig { language, language_preference, ..Default::default() }`。

## 6. 复盘（四步法）

1. **回顾目标**：中文系系统显示中文、其他语言显示英语，且不覆盖用户显式选择。
2. **评估结果**：机制 + 设置入口 + 两个既有 macOS 缺陷全部闭环；真机两次启动验证通过；**超额完成**的是把调研阶段最大的假风险（覆盖率）证伪并回写——这比多修一个 bug 更有价值，因为它避免了后续一整张「补 1000 条翻译」的错卡。
3. **分析原因**：弯路的根因是**统计口径先于机制理解**——没先读 `lumino-core/src/i18n.rs` 就自造扫描器，导致结论反向；同理，日志位置没顺着「文件日志何时可用」的时序去查。两次都是「先动手后验证」。
4. **沉淀规律**：
   - 统计类结论必须**先确认仓内既有门禁/机制**，再决定是否自造工具；口径错了，数字越精确越误导。
   - 加日志要去**真实产物**（日志文件/落盘产物）里确认落地，终端可见 ≠ 用户可见。
   - 跨平台 `#[cfg]` 代码在本机不编译 → 改动前先读**依赖源码**取证，并把依据写进注释。
   - 「默认值」类改动要先问：**这个字段在用户机器上已经是什么值？** 本机恰好是 legacy `en-US`，差点制造一个「用户语言被静默改掉」的线上问题。
