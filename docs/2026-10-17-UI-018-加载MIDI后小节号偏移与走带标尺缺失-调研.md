## 2. 证据链（可复现）

> 说明：本机没有 `D:\MIDI Collection\Bad Apple 8.49 Million.mid`（路径不存在），
> 因此用**代码探针 + 合成 MIDI**锁定机制；真实文件的最终确认只需打印一次
> `document.time_signatures`（见 §7.3）。

### E1. 现场探针：单拍号文件，初始视口并没有滚动

临时在 `ruler::draw` 首帧打印定位输入，并用合成的
`format 1 / 123 轨 / division 960 / 单拍号` 文件跑测试模式：

```text
PROBE ruler: scroll_x=0 zoom_x=0.1 ppq=960 start_tick=0 end_tick=3640
             keyboard_w=120 bounds_w=484 total_ticks=387600
             time_sigs=[(0, 4, 4)]
```

- `scroll_x = 0`、`start_tick = 0` → **视口在第 1 小节起点**；
- 单拍号时首个标签是 `1`（见 E3 的 single 分支）。

结论：**“跳到第 2 小节”不是滚动偏移问题**，不能去查 `scroll_x` 初始化。

### E2. 加载器探针：同 tick 的重复拍号被原样保留

构造一个 2 轨 MIDI，两轨各写一个 tick 0 的 4/4 拍号，交给
`load_parsed_midi_from_bytes`：

```text
probe time_signatures = [(0, 4, 4), (0, 4, 4)]
```

对应代码：

- `crates/audio/midi-model/src/document_build.rs:155-163`
  —— 每轨的 `time_signatures` 直接 `extend` 进全局列表；
- `crates/audio/midi-model/src/document_build.rs:198-200`
  —— `finalize_sorted_events` 只排序、不按 tick 去重；
- 同文件 `:21-23` 的注释明确写着：
  “**加载 = 全量保留：同 tick 的多个 tempo/拍号/调号事件全部保留，不做去重**”，
  这是 EXP-005 逐事件往返等价验收的既定口径。

因此多轨文件里只要有 ≥2 轨携带 tick 0 拍号，`EditorData.time_signatures`
就是 `[(0,4,4), (0,4,4), ...]`，不是单元素。

### E3. 迭代器探针：重复拍号让小节号从 2 起跳

针对 `MeasureIterator` 写临时断言：

```text
probe duplicate ts: first=Some((0.0, 2)), second=Some((3840.0, 3))
probe single ts:    first=Some((0.0, 1))
```

- 单拍号：`(0, 1)`（正确）；
- 同 tick 两份拍号：`(0, 2)`（错误，首个标签直接是 2）；
- 后一个小节边界仍是 `3840`（tick 没变），但标签变成 `3`。

这正是用户看到的“第 2 小节”：**内容在第 1 小节，标签却从 2 开始**。

### E4. 旧实现 vs 新实现（回归定位）

`81cdb8b7`（2026-10-01，PREF-004 P2）把 `advance_to` 从
“从 tick 0 逐小节 `step()`”改成“O(段数) 闭式定位”。
旧实现：

```rust
fn advance_to(&mut self, target_tick: f32) {
    while self.current_tick < target_tick {
        self.step();
    }
}
```

`target_tick = 0` 时循环一次都不进，`measure_number` 保持 1 →
**旧实现正确**。新实现的错误路径见 §3.2。

## 3. 根因分析

### 3.1 为什么会出现“同 tick 重复拍号”

- format 1 的多轨 MIDI 里，拍号通常只在 Conductor 轨，但并非所有导出器都遵守；
- 只要有两轨（或同一轨内两次）在 tick 0 写 4/4，加载器就保留两份；
- 123 轨的文件把这个概率放大，但**不是 123 轨特有**——任何带重复拍号的文件都会中招；
- 重复不一定在 tick 0：中途 tick 的重复拍号会让该点之后的小节号一次性跳变（见 §5）。

### 3.2 为什么编号会 +1（逐行）

`crates/editor/ui-editor/src/grid/ruler.rs`：

1. `segment_index_at`（`:292-302`）返回“**最后一个**起始 tick ≤ target 的段”。
   对 `[(0,4,4),(0,4,4)]`、`target=0`，返回 `index = 1`（第二份）。
2. `advance_to`（`:325-361`）从 `number = 1` 开始，对 `i in 0..seg` 累加
   `measures_in_segment(i).unwrap_or(1)`。`i = 0` 时：
   - `segment_start(0) = 0`（段 0 的特殊口径）；
   - `measures_in_segment(0)` 的 `end = time_signatures[1].tick = 0`；
   - `((0 - 0) / ticks).ceil() = 0`，再 `.max(1)` → **计 1 小节**（`:305-314`）。
   - 于是 `number = 1 + 1 = 2`。
3. `seg = 1` 的 `start = time_signatures[1].tick = 0`，`steps = ceil(0/ticks) = 0`，
   走 `_` 分支：`current_tick = 0`、`measure_number = number + 0 = 2`。
4. 首个 `next()` 返回 `(0.0, 2)`。

**每个同 tick 重复段都被 `.max(1)` 当成一个完整小节**，所以：

- 2 份同 tick 拍号 → 首个标签 `2`；
- 3 份 → 首个标签 `3`；
- 用户看到“第 2 小节”，反推文件里恰好有 **2 份** tick 0 拍号。

### 3.3 为什么普通文件正常

单份拍号时 `segment_index_at(0) = 0`，`0..0` 不累加，`number = 1`，`steps = 0`
→ 标签 `1`。E1/E3 已实测。所以“普通长度文件初始视口/标尺行为不变”的回归
不会被本次修复破坏（见 §6 的测试矩阵）。

### 3.4 纵向卷帘的独立成因（症状 1b）

`crates/editor/ui-editor/src/grid/vertical_labels.rs`：

```rust
let mut measure_tick = (start_tick / ticks_per_measure).ceil() * ticks_per_measure;
let mut measure_no = (measure_tick / ticks_per_measure) as u32 + 1; // tick 0 -> 1
...
let screen_y = grid_bottom - measure_tick * view.zoom_x + view.scroll_x;
if screen_y >= grid_top && screen_y <= grid_bottom {
    // position.y = screen_y + 2.0，align_y = Top
```

- `scroll_x = 0` 时 `measure_tick = 0`、`measure_no = 1`；
- `screen_y = grid_bottom`（正好在键盘与网格的分界线上）；
- 文本画在 `screen_y + 2.0`，即**键盘区域内**，网格内看不到；
- 网格内第一个完整可见的标签是 tick 3840 的 `2`。

所以即使用户文件里没有重复拍号，**纵向卷帘也会表现成“首个可见小节号是 2”**。
它与 3.2 是两条独立路径，修复时都要覆盖，才能满足“任意 MIDI / 任意视图”。

## 4. 走带界面为什么没有小节号

### 4.1 代码事实：走带视图没有标尺 Widget

- `crates/editor/ui/src/root/view/main_view/arrangement.rs:16` 的
  `view_arrangement` 只组了 `toolbar + arrangement_row + bottom_row`；
- `arrangement_row = row![track_list, arrangement_area, v_scrollbar]`，
  **没有 ruler 行**；
- `arrangement_area` 是空容器 + 透明 `ArrangementClickCanvas`，
  实际画面全部由 WGPU `ArrangementRenderer` 绘制。

### 4.2 WGPU 走带管线只画线，不画文字

- `crates/editor/gfx/src/arrangement_instances.rs:90-150`：覆盖层只构建
  背景 / lane / 网格线（`measure_line_ticks`）+ 框选 / ghost / 指示线；
- `crates/editor/gfx/src/shaders/arrangement.wgsl`：纯色块 SDF，无文字采样；
- `crates/editor/gfx/src/render_thread/render_loop/prepare.rs:16-35`：
  `is_arrangement_mode` 直接 `return`，**根本不会 prepare `RulerRenderer`**；
- `crates/editor/ui/src/host/render/separate_thread/runner/params.rs:87-93`：
  走带模式的 `keyboard_width = 0.0`、`ruler_height = 0.0`；
- `RulerRenderer` 本身（`crates/editor/gfx/src/ruler_renderer/`）也只是
  刻度线四边形，没有文字层——钢琴卷帘的小节号是 Canvas 画的，不是它。

因此卡片里猜的“超长文件下截断/格式化问题”**不成立**：走带界面没有任何
小节号文本生成逻辑，自然不存在“被截断”。这是**功能缺失**。

### 4.3 参考实现（“旧版本”）

`D:\LuminoDevelop\Source\yinhe\crates\yinhe-egui\src\widgets\time_ruler.rs`
中的 `interactive_ruler` / `paint_labels`：

- 走带（ARRANGE）与卷帘共用时间标尺；
- 走带顶部标尺（yinhe 当前 `theme::RULER_H = 24.0`；Lumino 旧 yinhe 移植为 28px），
  标签按 `bar` / `bar.beat` / `bar.beat.sub` 自适应密度；
- 支持点击/拖拽跳转、拖出边缘自动滚动；
- 小节号从 1 开始，与 wgpu 网格线严格对齐。

Lumino 的走带视图在 `790f8892`（2026-05-30）引入时就是 WGPU 线框方案，
没有把这条标尺一起移植过来。所以“与旧版本一致”应理解为：
**补回走带时间标尺（含小节号文本，建议 28px 对齐旧移植）**。

补充观察（未改，供后续评估）：

- `detection_dashboard::format_position` 固定按 4/4 计算 `bar.beat`，
  不读拍号表（源码注释已声明）；Bad Apple 是 4/4，暂时不影响，
  但非 4/4 工程会与标尺不一致。
- 视频导出 counter 的 `Bars` 也是独立口径；若要“全项目小节号唯一权威”，
  应把“tick + 拍号表 → 小节号/小节边界”收敛成共享纯函数，供标尺、
  仪表盘、导出 counter、协作光标共同使用（本次不扩范围，建议单独立卡）。

## 6. 修复方案

### P0：小节号迭代器对“同 tick 重复拍号”去重（**已落地，见 §11**）

**原则**：文档层保持全量保留（EXP-005 往返等价不能破），只在**显示/编号消费者**
去重。这样保存/导出仍然逐事件一致，只有 UI 的小节号变正确。

推荐实现（`crates/editor/ui-editor/src/grid/ruler.rs`）：

```rust
use std::borrow::Cow;

fn dedup_time_signatures<'a>(sigs: &'a [(u32, u8, u8)]) -> Cow<'a, [(u32, u8, u8)]> {
    if !sigs.windows(2).any(|w| w[0].0 == w[1].0) {
        return Cow::Borrowed(sigs);
    }
    let mut out: Vec<(u32, u8, u8)> = Vec::with_capacity(sigs.len());
    for &(tick, num, den) in sigs {
        if let Some(last) = out.last_mut()
            && last.0 == tick
        {
            // 同 tick 后者覆盖：与 time_signature_at 的“最后一个 ≤ tick 生效”一致
            *last = (tick, num, den);
        } else {
            out.push((tick, num, den));
        }
    }
    Cow::Owned(out)
}
```

- `MeasureIterator` 内部持有 `Cow<'a, [(u32, u8, u8)]>`，`new` 时调用一次；
- 正常文件走 `Borrowed`，**零分配**；
- 有重复时才 `Owned`，段数很小（通常 < 100），开销可忽略；
- `segment_index_at` / `measures_in_segment` / `advance_to` 的逻辑不用改，
  因为输入已经是“每个 tick 唯一”的段表；
- 同 tick 冲突时（如 `(0,4,4)` 后跟 `(0,3,4)`），保留后者，与
  `time_signature_at` 的现行语义一致。

**不要**在 `EditorData::set_time_signatures` 里 dedupe：该函数会回写
`doc.time_signatures`（`editor_data/accessors/write.rs:16-20`），会破坏
EXP-005 的全量保留。

### P1：纵向卷帘首标签画进网格（**已落地，见 §12**）

`vertical_labels.rs` 的首个边界（`screen_y == grid_bottom`）应把文本画在
边界**上方**，而不是 `+2.0`：

- 最小改法：`position.y = (screen_y - text_height - 2.0).max(grid_top)`；
- 或过滤 `screen_y > grid_bottom - text_height` 的边界标签，让第一个
  完整可见标签从第 2 小节开始——但这会掩盖“第 1 小节”信息，不推荐；
- 推荐前者：在键盘顶线上方画出 `1`，与横向标尺行为一致。

### P1：走带视图补时间标尺（建议 28px，对齐旧移植；**已落地，见 §12**）

布局（`view_arrangement`）：

```text
column![
    toolbar,
    row![ Space(160px), ArrangementRulerCanvas ],   // 24–28px 高（建议 28）
    arrangement_row,                                // track_list + wgpu area + v_scrollbar
    bottom_row,
]
```

关键点：

1. 左侧 160px 与 `TRACK_LIST_WIDTH` 对齐；标尺 Canvas 只覆盖右侧走带区，
   本地 `x = tick * zoom_x - scroll_x`，与 WGPU 网格同源；
2. 偏移同步：`collect_viewport_info` 的走带 `canvas_offset.y += 28`、
   `canvas_size.y -= 28`；`collect_render_data` 的同一组常量也要同步，
   否则 WGPU 网格会与标尺重叠或错位；
3. 标签复用**去重后的** `MeasureIterator`（建议把它从 `ruler.rs` 提升为
   `pub(crate)` 或抽到 `grid/measure.rs`），避免两套编号逻辑；
4. 密度：用与 yinhe `compute_measure_divisor` 等价的步长（1/2/4/8… 小节），
   保证标签间距 ≥ 38px；不要每小节硬画，超长文件缩小时会糊成一片；
5. 交互：`Program::update` 里把点击/拖拽的 `x` 映射为 tick，发
   `Message::ArrangementCursorSet(tick)`；拖出边缘复用现有自动滚动；
6. 如果“数量信息”还要求**总小节数**，在标尺右端或仪表盘追加
   `current / total`，total 用同一去重段表累加，避免再写一套 4/4 假设。

## 8. 风险与回归

- **不要**在加载器去重：会破坏 EXP-005 的逐事件往返等价；
- **不要**在 `EditorData::set_time_signatures` 去重：会回写文档，同上；
- 走带标尺新增 24–28px 会改变 `canvas_offset/canvas_size`，必须同步
  `collect_viewport_info`、`collect_render_data`、滚动条与点击 Canvas 的
  几何；建议加一个“标尺高度常量 + 偏移换算”纯函数单测；
- 标尺标签密度要限流，否则长文件缩小时每帧数百个 `fill_text` 会掉帧；
- 纵向标签修复只动绘制位置，不动滚动/缩放，回归面小；
- 修改后跑：`cargo test -p lumino-ui-editor grid::ruler`、
  `cargo test -p lumino-ui --lib`、`cargo check -p lumino-ui`、
  以及新增的加载器/标尺集成测试。

   ```rust
       &document.time_signatures[..document.time_signatures.len().min(8)]
   );
   ```

   若输出以 `[(0, 4, 4), (0, 4, 4), ...]` 开头，则 §3.2 即时闭环；
   若只有一份，则症状 1 更可能是纵向卷帘路径（§3.4），按 P1 修复。
2. **“数量信息”口径**：确认用户要的是“时间轴上的小节号标签”，
   还是“当前/总小节数”文本。前者按 P1 标尺实现；后者需在标尺/仪表盘
   额外加 `current / total`。
3. **是否要求走带标尺可点击跳转**：yinhe 旧版支持；若验收要求“与旧版本一致”，
   建议一并实现，避免二次返工。
