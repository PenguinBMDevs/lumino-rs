## 二、诊断证据（已发表到 #94）

- 素材 8.5M NoteOn / 123 轨 / 单端口 / div=960 / 约 3:51；GPU = **RTX 5080**。
- 切片 60–90s：GPU 文档路径 **210.5s**（输出 91.3s ≈0.43×）、GPU 流式 282.7s、
  **CPU xsynth 34.5s**（≈2.6×）→ GPU 比 CPU 慢 6 倍。
- per-block profile：`collect`（等 GPU+回读）**67–80ms/块**、`upload` 10–12ms；
  活跃声部 **30k–52k**；per-key=4 墙钟 192.7s（几乎不降）。
- 根因：`max_voices=0`（#31 决策）关闭了全局裁剪/池兜底；声部仅受
  每 `(channel,key)` 组数上限约束（理论 16×128×32≈65k）；每块全量上传+回读+
  渲染 3–5 万 voices。**释放尾巴不计入上限、不裁** → 总量由尾巴主导（per-key=4 不提速）。

## 三、本次明确的用户决策（开工必守）

1. **`max_voices_per_key` 口径锁定（2026-10-03 二次修订）：每 (Port, key) 上限 = 设置值**：
   - Port 内同一 key（跨 16 通道合并）共享上限 S；不同 key 独立；单 Port 理论上限 128×S，总量 = Σ(实际使用 Port)；
   - **绝不**按“程序最多支持 16 Port”乘出 S×16；也不是 16×128×S 的 (channel,key) 乘积口径；
   - S 用 30s 切片扫 1k/4k/8k/16k 曲线后拍板；字段沿用 `max_voices_per_key`，作用域改为 (port, key)；
   - **依赖**：GPU 当前无端口维 → 必须以 #87 的 Port 感知为基础（**先做 #87**）。
2. **历史实现粒度（回答“作用于 Port 还是单 Channel”）**：
   - CPU（xsynth）：`SetLayerCount` 落在**每通道** `key_voices[128]` → 粒度 **(global channel, key)**（多端口即 **(port, channel, key)**），不是整个 Port；
   - GPU：`key_voices[channel*128+key]`（channel 0..15，**无 Port 维**，端口折叠）→ 粒度 **(channel, key)**；所有 Port 共享同一 16 通道，CC/PC/PB 跨 Port 冲突（#87 范围）。
3. **Port 资源按“实际使用”激活**：
   - 先检测 MIDI 轨道实际使用了哪些 Port（**有轨道的 Port 才激活**；B/D 无轨道不激活），
     不允许盲目按 `max_port`/16 一次性分配；
   - 现状核实：**CPU 导出**按 `doc.max_port()` 分配 `(min(max_port,15)+1)*16` 通道
     （稀疏端口会多分配，如仅 port0/port7 → 分配 128 通道）；**GPU 侧无端口维**
     （折叠 16 通道，`key_voices[channel*128+key]`，Port 不参与）。
4. **#105 与 #94 一并修**：`trim_key_voices` 释放优先（对齐 CPU REND-009）、
   去掉 `hard_kill`（>20k 无淡出硬杀）。
