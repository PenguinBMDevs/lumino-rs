# REF-DATA-002 验证 · 两套加载栈对同一 SF2 各自解析

> 日期：2026-11-01 ｜ 分支：`ref-data-002-verify` ｜ 状态：**验证完成**
> 结论：同一 SF2 在 XSynth 栈与 LGS 栈**各解析一次**（进程内共 2 次），
> 两栈的缓存互不共享——#226 的前提成立。

---

## 1. 方法

- 在两条加载路径各加**解析/命中计数**（`AtomicU64`，诊断用，不参与控制）：
  - `crates/audio/midi-io/src/soundfont_cache.rs`（XSynth）；
  - `crates/audio/gpu-synth/src/soundfont/cache.rs`（LGS）。
- 新增集成测试 `crates/audio/midi-io/tests/soundfont_cross_stack.rs`：
  同一文件在两栈各加载两次，断言 `(解析, 命中) = (1, 1)` / `(1, 1)`，
  且**进程内总解析次数 = 2**。
- 大音源经 `REF_DATA_SF2=<path>` 覆盖（相对路径按仓库根解析）。

## 2. 结果

`rich.sf2`（30 KB，release 级别的库但测试是 debug 构建）：

```
xs_parse=11.4ms xs_hit=16µs   lgs_parse=5.25ms lgs_hit=56µs
```

`F2 Jasmine 2.1.sf2`（3.4 GB，debug 构建；测试内顺序加载、加载后释放前一栈）：

```
xs_parse=30.08s xs_hit=17µs   lgs_parse=29.63s lgs_hit=67µs
```

- 两次缓存命中都是微秒级：**缓存本身没有问题**；
- 但同一文件被两套栈各解析一次：Jasmine 上是 **~60 s 的重复解析工作**
  （release 下实测单栈 ~5.7 s，双栈 ~11 s）；
- 若两栈同时驻留，CPU 采样内存约 **2 × 7.45 GB ≈ 15 GB**（Jasmine）。
  测试为此顺序加载并在切换前释放 XSynth 句柄，避免把峰值翻倍。

## 3. 运行时是否真的并存？

- 代码路径：实时后端是 XSynth 时，LGS 的 `GpuSynth` 仍可被**导出**创建
  （`AudioRenderConfig.backend = Gpu`），此时两栈同进程并存；
- 本次验证只证明「两栈不共享解析结果」，**不声称**默认配置一定并发；
  是否值得做共享层，取决于「XSynth 实时 + GPU 导出」是否是常见组合。
- 若确认常见：共享层必须不反向依赖 `midi-io`（避免环），且两栈的解析产物
  类型不同（`SoundfontBase` vs `SoundFontCore`）——要么抽公共 crate 承载
  「文件身份 + 解析入口」，要么只共享文件字节（mmap）。

## 4. 建议

1. #226 保持 open，把本验证结果作为「先度量、后优化」的依据；
2. 若要做，先做**共享文件身份 + 解析计数**的轻量层，再评估类型统一的成本；
3. 跨进程共享明确不做（014 边界）。

## 5. 复现

```bash
# 小音源
cargo test -p lumino-midi-io --test soundfont_cross_stack -- --nocapture
# 大音源
REF_DATA_SF2="test-file/bench/F2 Jasmine 2.1.sf2" \
  cargo test -p lumino-midi-io --test soundfont_cross_stack -- --nocapture
```
