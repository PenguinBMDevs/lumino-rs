# 吸附式滚动条拖拽全程卡顿（PREF-004）—— 卡片调研与修复方案

> 2026-10-01 · 审查对象：黑乐谱（千万~亿级音符）拖拽滚动条全程 UI 卡顿卡片
> 结论一句话：**根因方向对了一半；但"主修=滚动帧免等待"修的不是真正的阻塞点，且卡片明确排除的范围恰好是主导成本。按原方案实施，验收标准达不成。**

## 2. 复现仿真审计（本卡最强的"证据"其实不成立）

复现脚本：`docs/research/midi-scroll-sim/repro.py`（原样），审计脚本：`docs/research/midi-scroll-sim/audit.py`。

### 2.1 原样复现：基线与卡片一致

```
1.5e8 panorama (card baseline)  T= 18.40ms  mean= 34.9  P95= 48.6  >33ms= 58%
```
卡片表格的 18.4ms / 42FPS / 34.9ms / 58% 可复现（6 亿一行因未交代 `visible`/`overdraw` 取值，无法逐位复现）。

### 2.2 致命问题一："修复后"那一行不是仿真结果，是把结论写死在分支里

```python
if not wait_coupling:            # 免等待：present 落后一帧
    lat.append(VSYNC_MS); continue        # ← 直接填 16.7
```
`wait_coupling=False` 分支没有计算任何东西，直接返回常数 `VSYNC_MS`。**"免等待修复：UI 延迟均值 16.7ms / >33ms 占比 0%"是假设，不是推导。** 用同一模型、同一 `T` 无法产生该结果。

### 2.3 致命问题二：基线分支本身就是"UI 完全不阻塞"的理想模型

`if t >= gpu_free: 起一帧`，事件由"t 之后第一个启动的帧"服务 —— 这已经是**解耦后的上界**。也就是说：**卡片表格的"修复前"列已经假定了"修复后"的前提**。同一 `T` 下，任何"免等待"改造的延迟期望都落在 `[T, 2T]`：

```
=== C. 反推达标所需的 GPU 单帧 T ===
    P95 <= 33ms  ==>  T <= ~16.9ms
    P95 <= 24ms  ==>  T <= ~12.3ms
```
本卡基线 `T = 18.4ms` **已经越过达标线**：即使 100% 消除耦合（理想上界），P95 也只有 ~34.7ms（去掉 vsync 量化后同样是 34.7ms，见下），**不满足 ≤33ms**。要达标必须把 `T` 压到 16.9ms 以下（有工程余量则应 ≤12ms）。

### 2.4 致命问题三：vsync 量化与真机不符，且参数自相矛盾

- `ceil(dones/VSYNC)*VSYNC` 假设 vsync 量化；但 `gfx/src/context.rs:11-46` 在**非 macOS 平台优先选 `Immediate`**（无 vsync），`desired_maximum_frame_latency = 2`。去掉量化后同一 `T` 下 P95 = **34.7ms**（58% → 33%），说明卡片表格里最多 16.7ms 的"卡顿"来自一个真机不成立的假设。
- "1.5 亿·**缩小全景**"却取 `visible = 3,000,000`（占总量 2%）。而全景下 y 轴 128 键全可见、x 轴全曲可见 ⇒ `visible ≈ total`。敏感性：

```
=== E. 敏感性 ===
vis=  3,000,000 od=30   T= 18.40ms   P95=  48.6   >33ms= 58%
vis= 30,000,000 od=30   T=126.40ms   P95= 250.0   >33ms=100%
vis=150,000,000 od=30   T=606.40ms   P95=1159.3   >33ms=100%
```
⇒ 表格参数与它自己 §② 的定性描述（"显示大量音符才卡"）互相打架；真实 `T` 可能比基线乐观得多或悲观得多，**该表不能用作方案选型依据**。
- `fill` 用 30 Gpx/s 的像素率外推亚像素 quad（1.5 亿个）量纲不匹配；`cull` 用 400GB/s 假设也未在真机标定。

### 2.5 结论

仿真可以保留为**机理示意**（说明"帧耗时 → 延迟"的传播方向），但必须删掉"修复后"那一行，或者把它改成"**若 T 能压到 X，则延迟可到 Y**"的条件式结论。

## 3. 卡片没有覆盖到的、同一路径上的真实成本

### 3.1 VS 阶段把同一份 16B 再读一遍
`note.wgsl:111-116` 的 `vs_main` 用 `all_instances[visible_index]` 重新读取实例；`cull.wgsl` 已经读过一份。全景时两趟读量相同（1.5e8 × 16B ≈ 2.4 GB ≈ 6ms @400GB/s）。**这正好说明"cull 挪进 vertex shader"的真实价值是省掉一趟读，而不是省 dispatch。**

### 3.2 预览通道每帧重建 bind group（会直接抬高 `wait_for_frame` 的等待时长）
`note_update.rs:216-219` **每帧**都发 `PreviewInstances`；非空时 `onion_stream.rs:163-168 → note_renderer/prepare.rs:23-32 → update_cull_info → :190-237` **无条件重建 cull + render 两套 bind group**（每 chunk 各一个）并重写全部 cull uniform。铅笔工具 + Idle 状态下（拖滚动条时正是 Idle）hover 预览非空 ⇒ **每帧 2×N 个 bind group 创建**发生在渲染线程，而 UI 正阻塞在 `wait_for_frame` 上等它。卡片 §④"已排除"清单漏了这一条。

### 3.3 标尺重建是 O(播放位置小节数)
`grid/ruler.rs:57-58` 用 `MeasureIterator::new(..., start_tick)`，其 `advance_to`（`:271-275`）**从 tick 0 逐小节步进到 start_tick**。滚动时 `scroll.rs:91` 每帧失效标尺缓存 ⇒ 每帧重建的成本随播放位置线性增长。长曲/大 PPQ 工程需要改成 O(1) 定位（拍号分段上做前缀和/二分）。

### 3.4 "深度预通道"对亚像素 quad 没用
1.5 亿个 <1px 的 quad，瓶颈在 primitive setup / 小三角形光栅吞吐；early-Z 只能省 fragment 工作，省不掉图元装配。**减少图元数量（合并/LOD/点图元）才有效**，深度预通道基本无效。卡片把"填充率结构性优化"整体外推，等于把主导项外推。

### 3.5 已有的可复用资产被闲置
`gfx/src/global_bucket.rs` + `shaders/bucket_sort.wgsl` 已经产出 `sort_index[N]` + `key_offsets[257]`（**key 主序、桶内按 start_tick 升序**），且随 `onion_epoch` 维护。这意味着"可见 key 区间"在有序数组中**是一段连续区间**，卷帘 cull 完全可以只 dispatch 这一段——现有 cull 却仍扫全量。

## 4. 修复方案

### 判定：卡片三步的价值排序

| 步骤 | 判定 | 处置 |
|---|:---:|---|
| 1 滚动帧免等待 | **有效但收益上界有限**：只省掉 UI 与渲染线程每帧的强制会合（渲染线程单帧 CPU 工作 + 提交），**不解 GPU 队列背压**——帧率上限仍由 GPU 单帧 T 决定 | **保留**（P0-a），但必须配收尾帧 `Flush`（P0-b）才不会丢尾帧 |
| 2 滚动事件按帧合并 | **无收益**（iced 已批量 + 单次重绘） | **删除**，只增状态与复杂度 |
| 3 拖拽期间不失效标尺/键盘缓存 | **负收益**（clear 幂等 O(1)；不重建会画错位标尺） | **改为"参数真变了才失效"**，并顺手修 O(小节数) 迭代器 |
| — 卡片未提但必须做 | **交换链帧延迟收紧**：这才是限制"UI 领先 GPU 多少帧"、从而限制 GPU 队列深度的唯一有效杠杆 | **新增 P0-c**（`desired_maximum_frame_latency` 2 → 1，可 A/B） |

### P0：解开"UI 帧 = 一次全量音符渲染"的硬绑定（已在本次落地，见 §7）

> ⚠️ 本节 P0-a 的原始设计（按**在途帧数**跳过提交）在落地时被自己否掉，原因见 §7.2：
> `wait_for_frame` 的完成信号是**提交序**（≈2ms）而非 GPU 执行完成（≈18ms），
> 用它当闸门信号恒为 0、形同空转。真正限制"UI 领先 GPU 多少帧"的杠杆是交换链的
> `desired_maximum_frame_latency`。下面是修正后的方案。

**P0-a 视口帧免等待（卡片的步骤 1 + 内容脏标记）**

- `RenderParams` 增 `content_dirty: bool`（默认 `true` = 保守等待）。
- UI 侧仅在**新产生数据**时置位：音符增量事件（`note_update.rs`）、洋葱皮全量/增量/ViewState 重传（`stream_onion_skin_instances` 提前返回之后）、预览实例**变化**、走带 ghost/复制拖动、**首帧与视口物理尺寸变化**（离屏纹理重建）。
- `content_dirty == false` 的帧跳过 `wait_for_frame`，直接 `copy_offscreen_to_surface`（读 `latest_texture`，见 `thread/blit.rs:16`）。
- 编辑帧语义完全不变 ⇒ `wait_for_frame` 修复的原竞态不回退。

**P0-b 收尾帧 `Flush`（不做则单次缩放失效）**

- 非内容脏帧不再等待后，会出现"提交了但没有任何一帧 present 它"的尾帧。单次 Ctrl+滚轮缩放、拖拽最后一帧正是这种只产生一帧的视口变化，没有收尾会永远停在离屏纹理里（表现为"滚轮没反应"）。
- 实现：提交视口变化帧时登记 `pending_present_flush = Some(frame_id)`，并自请求一次重绘；下一帧若 `RenderViewKey` 指纹不变且无内容变化，则**不堆叠渲染**，只 `wait_for_frame(pending)` + copy 把它同步刷上屏，然后清除登记。循环必然收敛（`Flush` 不自唤醒）。

**P0-c 交换链帧延迟收紧（真正限制队列深度的杠杆）**

- `gfx/src/context.rs`：`desired_maximum_frame_latency` 由 `2` 收紧到 `1`，可用 `LUMINO_FRAME_LATENCY`（1~3）覆盖做真机 A/B。
- 理由：UI 每 present 一帧就携带一次全量音符渲染提交，CPU 每多领先一帧，GPU 队列里就多常驻一帧全量渲染，内容延迟被放大一整个 GPU 帧。

### P1：把 `T` 压到 16.9ms 以下（不做则 P0 也过不了验收）

1. **cull 范围裁剪（复用 `GlobalBucketIndex`）**：`prepare_pass_with_pipeline` 增加"可见 key 区间"入参，cull 只 dispatch 有序数组 `[key_offsets[k0], key_offsets[k1+1])`，并新增一个绑定 `sort_index` 的 cull 入口。常规编辑缩放收益 ≈ 可见键数/256；全景无收益（届时全键可见），需靠第 3 条。
2. **去掉 VS 的二次读**：cull 输出端改为写"渲染所需的紧凑实例"（例如把 tick/key/len 打包成 8-12B），VS 不再读 `all_instances`。或者做**自适应直绘**：上一帧 `visible/total > 阈值` 时切到"每实例 VS 自判可见、不可见输出退化三角形"的管线，省掉整趟 cull 读 + 可见索引写。全景场景正是该分支。
3. **图元量削减（全景场景的主导项，卡片外推的那一项）**：小缩放档位（`zoom_x × 最短音符 < 1px`）切到 **`PointList`/单顶点实例化**绘制，或按 (key, 时间桶) 做密度合并层。注意 `cull.wgsl:81-82` 有"不得 LOD 剔除、1px 以下音符仍需绘制"的硬约束——点图元方案**仍然绘制**这些音符，只是从 quad 变点，与约束不冲突，但需像素级 A/B 确认外观。
4. **（可选）真正的 GPU 完成度背压**：若实测 `desired_maximum_frame_latency = 1` 仍不足，再引入 `Queue::on_submitted_work_done` + 渲染循环非阻塞 `device.poll(Poll)` 的完成计数，实现按 GPU 完成度跳帧。届时不要用 `wait_for_frame` 的信号。

### P2：清理与顺手修

5. `note_renderer`：`update_cull_info` 拆分——**仅当源 buffer 句柄/容量变化时**才重建 bind group，实例数变化只重写 cull uniform（`prepare.rs:190-237`）。直接消掉 §3.2 的每帧 bind group churn。**（本次已通过"预览未变化不下发"消掉热路径上的大部分，结构性拆分仍建议做。）**
6. 标尺/键盘缓存：仅在 `scroll_x/zoom_x/scroll_y/zoom_y` 实际变化时 `clear()`；同时把 `MeasureIterator::advance_to` 改成 O(1)/O(log) 定位（§3.3）。
7. `thread.rs` 注释"如果通道满则丢弃旧帧"与实现不符（`std::sync::mpsc::channel` 是无界的，永不返回 `Err`），改为如实描述 drain-to-latest。**（本次已修。）**

### 明确不做

- 步骤 2（事件合并）—— iced 已做。
- 步骤 3 原表述（拖拽期间不失效缓存）—— 负收益。
- 深度预通道 —— 对亚像素 quad 无效（§3.4）。

## 5. 验收口径重写（现在这版不可测 / 不可达）

| 原验收项 | 问题 | 建议改写 |
|---|---|---|
| "UI 延迟 P95 ≤ 33ms" | 未定义"延迟"的起止点，也不是可控量 | 拆成三条可测指标：① `wgpu_render_thread_frame` P95 ≤ 16.9ms；② UI 帧间隔 P95 ≤ 33ms；③ 输入→可见帧 ≤ 2 个 present 周期 |
| "画面 ≥30FPS" | 与 P95 ≤33ms 互斥（30FPS 本身=33ms/帧） | 画面 ≥30FPS **且** UI 线程阻塞点（`get_current_texture`/`present`）单次 ≤ 8ms |
| "复现仿真结果趋势与真机一致" | 现仿真"修复后"一行是常数 | 改为条件式：给出 `T → 延迟分布` 映射表，禁止出现硬编码结论行 |
| 硬件环境 | 未注明 | 必须写明 GPU/驱动/分辨率/缩放/present_mode（`Immediate` 还是 `Fifo`） |

**真机打点方案（puffin scope 已就位，无需新增基础设施）**

- 帧内：`wgpu_render_thread_frame`、`render_pass`、`note_cull_pass`（`prepare.rs:313-317` 已有 label）、`get_current_texture`、`present`、`wait_for_frame`（本次已补 scope）。
- 指标：拖拽 2s 窗口内 ①`RenderStats.last_frame_time_ms` P50/P95；②`get_current_texture`+`present` 阻塞时长 P95；③UI 帧间隔 P95；④`wait_for_frame` 命中率（内容帧 vs 视口帧的占比，用于确认免等待路径真的被走到）。
- A/B：`LUMINO_FRAME_LATENCY=1|2` 直接对比（默认 1）；`docs/research/midi-scroll-sim/audit.py` 给出 `T → 延迟分布` 的理论映射，可与真机打点对表。
- 压测样本需随卡附上真实黑乐谱 MIDI + 音符数 + 时长，否则"1.5 亿"无法复现。

## 6. 给卡片作者的三句话

1. **③ 的因归错了**：`wait_for_frame` 等的是 `queue.submit`，不等 GPU；真正的阻塞点是 `get_current_texture`/`present` + 单张离屏纹理 + 同一 command queue。修 `wait_for_frame` 只省一次 CPU 会合。
2. **步骤 2 是无效工作，步骤 3 是负收益**：前者 iced 已经做了，后者 `Cache::clear()` 幂等 O(1) 且不重建就画错。
3. **"不在本卡范围"的那两项，恰好是本卡目标的必要条件**：`T=18.4ms` 时即使完全解耦，P95 仍 ≈34.7ms。要达标必须压 `T`，而压 `T` 就得动 cull 读取量和图元数量。

### 7.2 与原方案的一处**有意偏离**（必须让评审看见）

原 P0-a 设计「按**在途帧数**跳过提交」。落地时被自己否掉：

- `wait_for_frame` 的完成信号由渲染线程在 `queue.submit` **之后**置位（`render_loop/runner/run.rs`），而渲染路径全程**没有**阻塞式 `device.poll(Wait)` ⇒ 该信号出现的时间是 **CPU 编码/提交耗时（≈1~2ms）**，不是 GPU 执行耗时（≈18ms）。
- 因此 `frames_in_flight()` 在任何 UI 帧上都≈0，闸门条件恒不成立 —— **等于空转，还多引一套跨线程原子状态**。这与卡片把 `wait_for_frame` 当 GPU 同步点是同一个认知错误，不能自己再踩一遍。
- 替代方案：**交换链 `desired_maximum_frame_latency` 收紧到 1**。它直接限制"CPU 能领先 GPU 几帧"，而 UI 每 present 一帧恰好携带一次全量音符渲染提交，因此它等价地限制了 GPU 队列里的全量渲染深度——这才是"在途帧闸门"想达到的效果，且零新增状态、可用环境变量 A/B。
- 若实测 1 帧仍不足，升级路径写进 §4 P1-4：用 `Queue::on_submitted_work_done` + 渲染循环非阻塞 `device.poll(Poll)` 取得真正的 GPU 完成计数，再按完成度跳帧。

### 7.3 回归影响面

| 项 | 结论 |
|---|---|
| 「音符放置后不立即显示」竞态 | **不回退**：编辑帧 `content_dirty = true`，走原 `wait_for_frame` 同步路径 |
| 首帧 / 窗口 resize / 面板改尺寸导致离屏纹理重建 | 走等待路径（`last_sent_viewport` 变化 ⇒ 置脏），不会拷到空纹理 |
| 单次 Ctrl+滚轮缩放 / 拖拽最后一帧 | 由 `Flush` 收尾帧保证呈现（`RenderViewKey` 指纹判定"视口确实变了"才登记；呈现后清除，循环收敛） |
| 剪辑面板 / 全屏瀑布流 | `allow_present_lag = false`，逐帧提交，`note_data_pub` 活体缓冲发布节奏不变 |
| 静止画面 | 视口未变时**不登记**收尾帧 ⇒ 不会自唤醒空转（自唤醒条件为 `Sent{wait:false}` 且 `pending_present_flush.is_some()`） |
| 预览音符 | 内容不变时不再逐帧重传 ⇒ 顺带消除热路径上每帧 2×N 个 bind group 创建（§3.2 的主要部分） |

### 8.2 数据推翻了我自己上一轮的 P1 优先级

| 我上一轮的排序 | 实测结论 | 修正 |
|---|---|---|
| P1-1 cull 范围裁剪 ★★★ | 全景下 cull 只占 **5~10%**（1.60ms vs draw 13.44ms）；放大档 cull 占比虽高，但整帧只有 1.65ms、**根本不卡** | **降级/删除**——优化一个用户感知不到的段落 |
| P1-2 去掉 VS 二次读 ★★★ | 全景下 draw 的瓶颈**不是带宽**：16M 实例 × 16B = 256MB / 13.44ms = **19 GB/s**，仅为 2060 峰值（336 GB/s）的 6% | **降级**——省 16B/实例解决不了 6% 的带宽占用 |
| P1-3 图元量削减 ★★★ | **确认是唯一大头**：draw 线性于可见数（≈0.8~1.4 ns/实例），且卡片用的 `Gpx/s` 像素率模型量纲错误（实测是**每实例固定成本**主导，与 quad 面积无关） | **升级为 P1 唯一靶子** |

**关键量纲结论**：把 quad 换成「1 顶点 1 点」后，draw 只快了 **1.22~1.28×**
（16M 全景 15.35ms → 12.00ms）。顶点数 -75%、三角形数 -100%，收益却只有 25%
⇒ **瓶颈既不是顶点数也不是三角形数，而是「每实例的固定处理成本」**
（≈0.75~0.85 ns/实例，两条路径同量级）。**唯一的出路是减少实例数本身**
（密度聚合/合并渲染），而不是换图元类型。

**外推到 1.5 亿（卡片目标场景）**：`1.5e8 × 0.75ns ≈ 112ms/帧`（点）/`≈ 130ms`（quad）
⇒ 距「T ≤ 16.9ms」差 **约 7 倍**。这从数据上确认了卡片「填充率优化另立卡」的
决定**恰好把主导项排除在范围外**——本卡无论怎么修 present 路径都到不了 33ms。

### 8.3 仍然落地了的那一项（有实测收益，非估算）

`crates/editor/gfx/src/note_renderer/point.rs` + `shaders/onion_note.wgsl` 的
`vs_point` / `fs_point`：**亚像素档位点图元直绘**。

- 触发：`zoom_x × 吸附精度 < 1px`（最细可画音符也不足 1 像素）且非纵向卷帘
  ——由 UI 侧 `build_render_params` 判定，写入 `RenderParams::subpixel_note_mode`。
- 动作：主音符层走 `PointList`（每实例 1 顶点 1 点）+ **跳过 cull pass**
  （可见性判定移入 `vs_point`，省掉全量读 + 可见索引写）。
- 实测收益：**1.22~1.28×**（16M 全景 15.35 → 12.00ms；含省掉的 cull 1.60ms）。
- 深度契约：`global_index = chunk_start + instance_index`（= 源索引），与 quad 路径
  同值 ⇒ 两条路径深度逐位一致，重叠音符稳定裁决语义不回退。
- 回退安全：无点管线的渲染器（预览层 / 导出无 depth 变体）自动回退 quad 路径。

### 8.4 诚实标注：需要视觉签核的一处行为变化

亚像素档位下，quad 路径的描边判定 `horiz_margin = 1/half_width × border_px` 在
`half_width → 0` 时趋于无穷 ⇒ **整块音符都被判成描边色（原色 ×0.4，明显偏暗）**。
点路径改为纯色，因此**全景画面会比现在更亮/更接近真实音轨色**。这是行为变化，
不是像素等价：需按 `point_tests` 的覆盖掩码 + 真机截图做视觉签核。
可用 `LUMINO_PERF_NOTES` 之外的开关快速回退——把 `subpixel_note_mode` 判据
去掉即可（触发点单一，位于 `separate_thread/runner/params.rs`）。
