# REF-LGS-004 · mix 事件重放：全表扫描 → 按通道分桶 + 二分定位

> 日期：2026-10-31 ｜ 分支：`ref-lgs` ｜ 状态：**已完成**
> 目标：高事件密度素材 mix 耗时 −30%、该场景倍实时 +15%；
> `sustained65536` 不退化（±3%）；音频逐位一致。
> 实测：**总墙钟 +34.9%**（0.742 s → 0.483 s），GPU 等待相 `collect` **−42.4%**；
> 逐位一致（cc_storm 原始 f32 逐样本 `max|d| = 0`，全部 golden 不变）。

---

## 1. 现状与诊断

`mix.wgsl` 的每个 `(frame, channel)` 线程都从 `i = 0` 重扫**整块**事件表：

```wgsl
while (i < event_count && mix_events[i].frame <= f_global) {
    let ev = mix_events[i];
    if (ev.channel == ch) { ...重放... }
    i += 1u;
}
```

事件表按**帧**全局排序，所以：

- 每个线程要扫「本块已发生的全部通道」的事件，绝大多数命中
  `ev.channel != ch` 后空转；
- 最坏复杂度 `O(block × channels × events)`。黑乐谱密集段单块 4,096 条事件时，
  block 512 / 16 通道 ≈ **3350 万次事件读取/块**（其中 15/16 是无效比较）。

`MAX_EVENTS_PER_BLOCK = 4096`（`drain.rs:22`）。本卡的度量夹具取 ≈2,048 事件/块
（`scripts/gen_lgs_cc_fixture.py`：16 声部持续音 + 每块 2k 条 CC7/CC11/CC10），
把「事件重放」从声部 gather 里隔离出来。

---

## 2. 方案：按通道分桶，通道内保持帧序

### 2.1 主机侧

`update_mix_params`（`synth/engine/bind.rs`）把块内事件从

```rust
in_block.sort_by_key(|e| e.0);              // 全局帧序
```

改为

```rust
in_block.sort_by_key(|e| (u64::from(e.1) << 32) | (e.0 & 0xFFFF_FFFF));
//                              channel                    frame
```

- **稳定排序**：同通道同帧的事件保持原始到达顺序（CC10 与 CC8 都写 pan，
  顺序有语义）；
- CPU 侧重放从「每通道 `filter` 全表」改为**一次线性扫描**（事件已按通道聚集），
  16 × 2048 → 1 × 2048 次比较。

### 2.2 内核侧

```wgsl
// 二分：本通道事件段的起点（事件按 channel 升序）
var lo = 0u; var hi = event_count;
while (lo < hi) { ... mix_events[mid].channel < ch ... }

// 只扫本通道、且帧号不超过本帧的事件
var i = lo;
while (i < event_count && mix_events[i].channel == ch
    && mix_events[i].frame <= f_global) { ...重放... }
```

每线程成本从 `O(全块事件)` 降到 `O(log E + 本通道事件)`；16 通道时事件读取
约降一个数量级，256 通道（多端口）更多。

### 2.3 为什么逐位一致

- 每个通道的重放序列**完全不变**：仍是「块首状态 + 该通道按帧升序的事件 +
  `frame <= f`」，`lerp_advance` 的调用次数、顺序、参数都一样；
- 排序只在通道维度重排，通道之间本来互不影响（内核原注释即以此为前提）；
- 二分只定位起点，不改变扫描内容。

实证：

| 用例 | 结果 |
|---|---|
| cc_storm（2k CC/块） | 原始 f32 逐样本 **`max|d| = 0`** |
| `sustained65536` 512/2048/4096 | golden 不变（`ea209e1f…` 等） |
| 未滤波 512/2048/4096 | golden 不变（`ba3ce403…` 等） |
| `multiport_16p_256ch` 512/4096 | `927514d6…` / `170478c8…` |
| `gate_2p_32ch` / `scatter100k` | `48bbe593…` / `9ae3b80f…` |

## 3. 度量（A/B 6 对交替，中位数）

`python scripts/lgs_ab.py --baseline test-file/bench/hash_render_pre004.exe
--after target/release/examples/hash_render.exe --only cc_storm_10s_200ept@512
--pairs 6 --gate-pct 2 --no-gating`

| 指标 | 基线 | 本卡 | Δ |
|---|---|---|---|
| 总墙钟（10 s 音频） | 0.742 s | **0.483 s** | **+34.9%** |
| `collect`（等上一块 GPU，含 mix pass） | 594 µs | **342 µs** | **−42.4%** |
| `dispatch`（提交） | 56 µs | 55 µs | −2.2% |
| `mix`（CPU：排序 + 上传 + 状态机） | 32 µs | 37 µs | +16.4%（+5 µs） |
| `apply` | 4 µs | 4 µs | 0 |

> **口径说明**：mix pass 在 GPU 上，现有打点无法单独计时；`collect` 是
> 「等上一块 GPU 完成」的墙钟，mix pass 的成本包含在内，是可用代理。
> `mix=` 是 CPU 侧 `update_mix_params`，不是 GPU pass。
> `mix` +5 µs 是排序键从 u64 帧号变成 (channel<<32|frame) 的代价，
> 相对总墙钟 −259 µs 可忽略。
