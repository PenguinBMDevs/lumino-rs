## 0. 结论先行

1. **400 行文件红线已经死了**：CI 守卫在 `f740d1d6`（2026-10-10）被整体删除；`AGENTS.md` 里没有 400/500/600 的数字；`clippy.toml` 的 `too-many-lines-threshold = 400` 量的是**函数**且该 lint 从未启用。规则既没有执行者，也没有正确语义。
2. **拆分没有降低复杂度**：3 个月文件数 1,094 → 2,250（+106%），总行数 191k → 412k（+116%），平均文件 175 → 183 行；`>600` 文件 13 → 31。拆得更多，单文件反而更大。

5. **本任务不再用“文件行数”单指标**：改为 `文件 600 + 函数 100 + struct 20 字段 + impl 25 方法 + 模块预算 4,000 行/20 文件`，并用**只减不增的棘轮**执行，避免重演“守卫挡死开发 → 整条规则删掉”的失败模式。

### 3.1 规则表（写入 `AGENTS.md`，T-05）

| 对象 | 硬上限 | 软目标 | 例外 |
|---|---:|---:|---|
| 生产 `.rs` 文件 | **600 行** | 500 | level A DSP 文件只报告，不强制拆 |

| 函数参数 | **6** | 4 | 参数袋 struct 必须命名 |
| 模块目录 | **4,000 行 / 20 文件** | 2,500 / 12 | 超出需登记 owner 与拆分计划 |

### 3.2 门禁：不做 CI 硬拦截（2026-11-26 决策）

原计划是新增 `scripts/check-file-size.py` + 白名单 + CI job `size-guard`。本轮决策**不做**：

- CI 暂不新增文件尺寸 job。函数行数由 `clippy.toml` 的 `too-many-lines-threshold = 100` 约束，
  在 `too_many_lines` 启用后由现有 clippy CI（`-D warnings`）自动执行；当前该 lint 仍未启用（见 3.3）。
- 文件行数（生产 600 / 测试 800）不设自动门禁，改由 `AGENTS.md`（T-05）+ code review 执行。
- 代价：存量 31 个 `>600` 文件没有自动拦截，反弹只能靠周报（T-42）与评审发现；
  这也是 T-10 必须按阶段拆分、而不是按行拆分的原因。

### 3.3 clippy 配置修正（T-01，本轮已做）

**事实核对**：

- `too-many-lines-threshold` 是 `clippy::too_many_lines` 的阈值，单位是**函数行数**，不是文件行数。
- `too_many_lines` 属于 pedantic 组，默认 allow；`[workspace.lints.clippy]` 从未启用它，CI 也没加 `-W clippy::pedantic`。所以 `clippy.toml` 里的 400 一直没有生效。
- CI 使用 `cargo clippy --workspace --all-targets -- -D warnings`，直接启用 `too_many_lines = "warn"` 会让 309 个 `>100` 行函数一次性变成 309 条错误。

**因此本轮只做“语义修正 + 目标值”，不直接启用 lint**：

```toml
# clippy.toml
too-many-lines-threshold = 100
```

```toml
# Cargo.toml [workspace.lints.clippy] 增加注释说明：
# too_many_lines 暂不启用（存量 309 个 >100 行函数，-D warnings 会一次爆）；
# Phase 0 用基线棘轮逐 crate 开启；文件行数（生产 600 / 测试 800）由 AGENTS.md + review 执行。
```

**为什么不是 600**：把 `too-many-lines-threshold` 改成 600，等于允许 600 行的**函数**，与“文件 500–600”目标相反。文件阈值只能由脚本执行。
