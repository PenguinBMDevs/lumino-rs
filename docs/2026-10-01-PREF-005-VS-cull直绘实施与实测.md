# PREF-005 · VS cull 直绘 + 洋葱皮去混合：实施与实测

> 2026-10-01 · 关联 #82(PREF-004)、#46(REND-001)
> 一句话：**已按卡实施、正确性逐位验证通过；但卡内 `zoom-in 不劣化` 的假设被真机实测推翻（直绘慢 5~8 倍），
> 故加了严格闸门后才落地；实测收益 8~12%（未达卡内「≥50%」），且卡内根因①被数据否证。**

---

## 1. 实施内容（对齐卡内 6 步）

> ⚠️ **相对卡内原文的唯一偏离**：第二步的「UI 路径取消 compute cull」，落地时必须加
> **可见占比闸门**（> 90% 才启用直绘）。原因是卡内设计说明「zoom-in 场景 VS 全量读带宽
> ≈ 原 compute cull 全量读，不劣化」**被真机实测证伪**——见 §3.3，实测该档直绘慢 5~8 倍。

| 卡内步骤 | 落点 | 状态 |
|---|---|---|
| ① 洋葱皮管线去 alpha 混合 | `note_renderer/pipeline.rs::create_render_pipeline(…, opaque)`，`is_onion` 传 `true`；预览层 `note.wgsl`（70% alpha 哨兵）保持混合 | ✅ |
| ② cull 挪 vertex shader | `shaders/onion_note.wgsl::vs_direct`（`@builtin(instance_index)` + 视口相交判定，谓词与 `cull.wgsl` 逐字一致，不可见退化为视口外零面积点）；**新增 `RenderParams::vs_cull_mode` 闸门**（UI 侧按「可见 tick 比例 × 可见 key 比例」估算可见占比，> 0.9 才启用，纯函数 + 3 个单测） | ✅（加闸门） |
| ③ 利用实例序 = 深度序 | `draw_direct` 按 chunk 升序 `draw(0..4, 0..chunk_len)`；`global_index = chunk_start + instance_index` 与 cull 路径写入可见缓冲的 `local_index` **同值** ⇒ 深度逐位一致 | ✅ |
| ④ 保留 chunk 分片、退役 visible/indirect/cull bind group | `draw_direct` 每 chunk 一个 bind group + 一次普通 draw；启用直绘时不再跑 `prepare_pass` 的 dispatch（改 `prepare_direct`，只写相机 uniform） | ✅ |
| ⑤ 导出路径保持 compute cull | `render_pass.rs` 以 `has_depth && params.vs_cull_mode` 分流：UI 且近全量可见 ⇒ 直绘；无 depth（导出）或可见占比不足 ⇒ 原路径。双路径共存 | ✅ |
| ⑥ depth write 保持开启、深度语义不动 | 管线 depth 状态未改；`region_depth` 公式与分层不变 | ✅ |
| 硬约束：不得恢复 LOD 剔除 | `vs_direct` 只做「长度 > 0 且与视口矩形相交」判定，与 `cull.wgsl` 同口径 | ✅ |

## 2. 正确性验证（本卡最重要的一环）

### 2.1 逐位像素等价（`direct_tests::test_direct_path_pixels_match_cull_path`）

同一场景（主轨三音同 key 互叠 + 两轨洋葱皮叠音 + 一轨静音）分别走
「compute cull + 可见索引」与「VS cull + 实例序直绘」，**两档缩放各比一次**：

```text
test_direct_path_pixels_match_cull_path ... ok
test_direct_path_self_culls_invisible_notes ... ok
```

- 对比的是**整张 256×144 RGBA8 缓冲逐字节相等**，不是抽样像素——这是
  「改绘制序零视觉变化」唯一可信的验证方式（`tie_break_depth` 是其前提，
  #46 不回归）。
- 附**反假绿守卫**：常规缩放档位必须真有覆盖像素，否则「两边都画空」也会通过。
- 第二条契约：`vs_direct` 自判可见与 `cull.wgsl` 同口径——视口外 / `length ≤ 0`
  / 静音轨一律零片元。

### 2.2 全套回归

```text

cargo test -p lumino-gfx --lib                  → 192 passed / 4 ignored
```

## 3. 真机 A/B 实测（`perf_tests::bench_vs_cull_ab`）

硬件：`NVIDIA GeForce RTX 2060 / Vulkan / 驱动 610.62 / 1920×1080`。
15 轮中位数（前 2 轮预热丢弃）+ **正逆序双向轮转取最小值**。

| 负载 | 音符 | 混合+cull（改动前） | 不透明+cull | 不透明+直绘 | 去混合单项 | **总降幅** |
|---|---|---|---|---|---|---|
| dense（同 key 堆叠） | 8M | 6.55 | 6.60 | 5.86 | -1% | **11%** |
| dense | 16M | 12.29 | 12.35 | 10.79 | -0% | **12%** |
| dense | 24M | 18.24 | 18.33 | 16.22 | -0% | **11%** |
| uniform（均匀铺满） | 8M | 7.24 | 7.42 | 6.56 | -2% | **9%** |
| uniform | 16M | 13.75 | 14.25 | 12.67 | -4% | **8%** |
| uniform | 24M | 20.78 | 20.94 | 18.74 | -1% | **10%** |

### 3.1 测量方法学：顺序偏置必须控制

第一版单轮顺序采样给出过「dense 8M 降幅 46~49%」的结论，但同一张表里
**8M blended = 10.75ms、16M blended = 12.31ms**——音符翻倍只多 1.5ms，在
O(N) 负载上不可能。加入正逆序轮转取最小值后该行回落到 6.55ms，假象消失。
**教训**：A/B 里第一个被测量的配置会被时钟态/冷缓存污染，单向顺序采样足以
把结论从 11% 夸大到 49%。该项已固化进基准（`measure_frame_paths` 注释说明）。

### 3.2 结论（与卡片归因的差异，必须记录）

1. **总降幅稳定在 8~12%，未达卡内「≥50%」**。
2. 收益 **≈ 省掉的 compute cull 本身**：16M 全景早先分段实测 `cull 1.60ms / 总
   15.35ms ≈ 10%`，与本次降幅一致。**early-Z 的额外收益在本次测量中不可见。**
3. **根因①「alpha 混合空转 + 抑制 early-Z」被否证**：去混合单项 ≈ 0%
   （-4% ~ -1%，噪声内，甚至略慢）。NVIDIA 上 alpha blending **不关闭 early-Z**
   （blending 属 ROP 阶段，与深度测试正交），blend ROP 的读改写开销在本负载下
   可忽略。
4. 为什么 early-Z 没带来更大收益：三条独立证据指向**瓶颈是每实例固定处理成本**，
   而不是片元/混合——
   - quad → point（顶点 −75%、三角形 −100%）只快 1.22~1.28×（PREF-004 P1 实测）；
   - 本次 `opaque+直绘`(10.79) ≈ 早先 `point`(12.00)（两条完全不同的图元路径
     落在同一水平）；
   - 去混合 ≈ 0%（片元侧改动无感）。

### 3.3 ⚠️ 致命回退：zoom-in 档直绘慢 5~8 倍（卡内假设被证伪）

补测 **zoom-in** 档（2 px/tick × 20 px/key，约 52 键可见）后才暴露：

| 负载 | 音符 | cull 路径 | 直绘（无闸门） | 结果 |
|---|---|---|---|---|
| dense | 8M | 0.87 | 5.82 | **慢 6.7 倍** |
| dense | 16M | 1.39 | 10.89 | **慢 7.8 倍** |
| uniform | 8M | 1.09 | 5.92 | **慢 5.4 倍** |
| uniform | 16M | 1.79 | 11.19 | **慢 6.2 倍** |

**根因**：卡内设计说明把两种成本当成了等价，实际差一个量级：

- **compute cull**：一趟 compute 扫全量（≈**0.10 ns/实例**），随后 `draw_indirect`
  只画**可见实例**（16M 里 1.5 万）⇒ 1.39ms；
- **VS cull 直绘**：顶点着色器要为**全部实例**各跑一遍（≈**0.65 ns/实例**，
  含退化图元的几何装配）⇒ 10.89ms。

**直绘占优条件**（用本次实测系数解）：`0.65N < 0.10N + 0.65V` ⟺ **`V > 0.85N`**，
即「可见音符占比 > 85%」。全曲视图踩线，任何放大档都远远不满足。

**处置**：加严格闸门（阈值 0.9）——可见占比不足时走原 compute cull 路径。
闸门判据抽成纯函数 `estimate_visible_fraction` 并配 3 个单测（全曲开闸 /
放大关闸 / 退化输入保守关闸）；因为两条路径已被证明**逐位像素等价**，
闸门切换零视觉风险。

**闸门覆盖面提示**：极端缩放下（长曲全曲视图）亚像素档位会先命中**点图元**
路径（PREF-004 P1，用户已确认默认开），此时直绘不参与——两者是不同视觉档位，
优先级已按「点图元优先（保证亚像素音符可见）」固定。

## 5. 建议

1. **保留本卡改动（含闸门）**：零视觉变化（逐位等价）、零回归（闸门挡住放大档回退）、
   近全量可见档稳定 8~12% 收益，且该档移除了每帧一趟全量 compute dispatch
   （在 1.5 亿规模下按 PREF-004 的分段斜率外推约省 15ms/帧）。
2. **修正卡内归因与设计说明**：
   - 根因①删除或改述为「FS 恒不透明却走混合路径，语义不一致（无可测性能代价）」；
   - 根因②③成立，但收益量级应为 ~10%；
   - **「zoom-in 场景 VS 全量读带宽 ≈ 原 compute cull 全量读，不劣化」必须删除**：
     两者是 0.65 ns/实例 vs 0.10 ns/实例，差一个量级，实测慢 5~8 倍。
3. **「≥50%」只能由实例数削减达成**：见 PREF-004 §8.5 / 密度聚合。本卡与密度聚合
