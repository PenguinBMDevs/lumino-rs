**「依赖捎带自愈的潜在缺口」**，不是「拖屏必错」。真正会露出来的场景是
「物理尺寸不变、只有 DPI 变」的那一档（以及仅发 `ScaleFactorChanged` 的平台/时机）。

## 1. G-1（P1-1）视口随 DPI 重建

### 1.1 现状与根因链

5 个窗口事件处理器，全都只认 `Resized`：

| 窗口 | 处理函数 | `Resized` 分支 | 落空分支 |
|---|---|---|---|
| 主窗口 | `src/runner/window_manager.rs:134` | `:150-152` → `:190-201` + `resized = true` | `:163` `_ => ()` |
| 对话框（17 类） | `crates/editor/dialog/src/window/event.rs:11` | `:13-21` | `:30` `_ => {}` |
| 进度窗 | `src/runner/progress_manager.rs:51` | → `handle_resize` | `_ =>` 转给 iced |
| 云进度窗 | `src/runner/cloud_progress.rs:64` | → `handle_resize` | `_ =>` 转给 iced |
| 设备警告窗 | `src/runner/device_warning.rs:103` | `ui.resize` + `gfx.resize` | `other =>` 转给 iced |

根因链（每一环都有代码依据）：

1. `Viewport` 只在 `Host::resize` 里重建，而它**读当时最新的** `window.scale_factor()`
   ⇒ 只要来一次 `Resized`，viewport 就自愈；
2. 但没有任何分支处理 `ScaleFactorChanged`（`iced_winit` 已把它转成
   `Event::Window(Rescaled)` 喂给控件，**控件知道 DPI 变了，视口不知道**）；
3. 若系统只发 `ScaleFactorChanged`：`viewport.scale_factor()` 与真实 DPI 分叉 ⇒
   `viewport.logical_size()` 用旧 DPI 换算 ⇒ `UserInterface::build(…, viewport.logical_size(), …)`
   （`host/render/ui.rs:44-52`）按错的逻辑尺寸布局；`renderer.present(…, &viewport)`
   （`ui.rs:91-96`）按旧 DPI 做表面缩放；
4. 更隐蔽：光标换算用的是**每事件现读**的 `window.scale_factor()`
   （`host/event/window/events.rs:41-45`）⇒ 出现「光标位置对、控件尺寸错」的半对状态。

顺带修两处**同类漏置脏**（本轮读代码发现，不修则 DPI 修好也看不到效果）：

| 位置 | 问题 |
|---|---|
| `host.rs:169-174` `Host::resize` | 只重建 viewport，**不置 `ui_dirty`**；`render_iced_ui`（`ui.rs:30-39`）在 `!ui_dirty && !is_first_render` 时直接 present 缓存帧 |
| `render/separate_thread/runner/params.rs:165-169` | `viewport_key = (physical_w, physical_h)` 只含物理尺寸，DPI 变化时判不出「视口变了」⇒ 渲染线程不重建离屏纹理、不走等待路径 |

### 1.2 方案

```text
crates/editor/ui/src/host/render/viewport.rs
    pub(crate) fn viewport_for(size: (u32, u32), scale: f32) -> Viewport
        // 唯一换算入口（纯函数，可单测）：内部 Viewport::with_physical_size(Size::new(w, h), scale)
        // 该函数直接算 logical = physical / scale（iced_graphics-0.14.0/src/viewport.rs）
        // ⇒ scale 为 0/NaN 会得到 inf/NaN 逻辑尺寸，入口必须先兜底

crates/editor/ui/src/host.rs
    pub fn resize(&mut self, w, h) { viewport_for(w, h, 现读 scale_factor()); ui_dirty = true; }
        // 不另设 `sync_viewport` 入口（落地修订，见下）

crates/editor/ui/src/host/render/separate_thread/runner/params.rs
    viewport_key = (physical_w, physical_h, scale_factor.to_bits())
```

5 处接线（落地形态：复用各窗口**已有**的 resize 路径，每处 4 行）：

```rust
WindowEvent::ScaleFactorChanged { .. } => {
    let size = window.inner_size();   // 物理尺寸以窗口为准，别用事件里的 suggested size
    self.handle_resize(size, ...);    // 原有路径：ui.resize(现读 scale) + gfx.resize + 置脏
}
```

> **落地修订（实现时改的）**：规划里设想过独立的 `Host::sync_viewport()`。实现时发现
> 5 个窗口本来就各有一条 `handle_resize`（ui + gfx + 请求重绘三件套），再立一个入口
> 反而出现「改了 ui 忘了 gfx」的第二条路，因此**没有新增入口**，统一走原有 resize
> 路径；`Host::resize` 唯一的变化是内部改调 `viewport_for` 并置 `ui_dirty = true`。

「以 `window.inner_size()` 为准」是关键：`ScaleFactorChanged` 自带的
`inner_size_writer` 是**建议值**，winit 允许应用拒绝，我们不接这条通道，只信窗口。

### 1.3 测试与不可测部分

| 类型 | 内容 |
|---|---|
| 可自动化 | `viewport_for` 纯函数：`(1920,1080)@1.5 → logical (1280,720)`、`@1.0` 恒等、`@1.25/@2.0` 小数取整、非法 scale（0/NaN）兜底为 1.0 |
| 可自动化 | `viewport_key` 含 scale：同物理尺寸、不同 DPI ⇒ 判为「变了」 |
| **不可自动化** | 5 个窗口的 `ScaleFactorChanged` 分支需要真窗口 + 真事件循环；只能人工验收（§6） |

不假装能测：把「5 个 handler 都接上了」写成用例需要起 winit 事件循环，收益不抵成本。

### 1.4 风险

- **R1（历史坑，必须守住）**：`host/event/window/events.rs:125-129` 记录过
  「无条件 `request_redraw` ⇒ `RedrawRequested` 自循环 ⇒ GPU 满载」的事故。
  对话框的刷新由 `DialogManager::update` 驱动，因此 `sync_viewport` **只置脏**；
  `request_redraw` 由各窗口既有路径负责（主窗口下一帧自己有；对话框 manager 会调）。
  实现时必须确认对话框在 DPI 变化后**确实重绘了一次**，而不是"修了但看不到"。
- **R2**：`ui_dirty = true` 会让下一帧走完整 `UserInterface::build`，对主窗口是常规操作，
  对内存监控这类每帧重建的窗口无影响。
- **R3**：`gfx.resize` 目前只吃物理尺寸，DPI 变化时物理尺寸不变 ⇒ 仍需调用（幂等），
  以免某些后端把 surface 配置和 scale 绑在一起。

## 2. G-2（P1-2）`UiState` 单位统一：存逻辑 + 一次性迁移

### 2.1 现状与影响算例

| 动作 | 代码 | 单位 |
|---|---|---|
| 写尺寸 | `window_manager.rs:190-201`（`handle_resize`） | **物理** `PhysicalSize<u32>` |
| 读尺寸 | `window_manager.rs:296-303`（`build_window_attributes`） | **逻辑** `LogicalSize<u32>` |
| 写位置 | `window_manager.rs:153-159`（`Moved`） | **物理** `PhysicalPosition<i32>` |
| 读位置 | `window_manager.rs:308-312` | **逻辑** `LogicalPosition<i32>` |

150% DPI 算例：窗口逻辑 1440×900 = 物理 2160×1350。关闭时存 `w=2160,h=1350`；
下次启动按逻辑 2160×1350 建窗 ⇒ 物理 3240×2025 ⇒ **每次重启 ×1.5**（两次就到 4860 宽）。
位置同理：x=100 物理 → 逻辑 100 → 物理 150，每次重启向右下漂移。

### 2.2 方案对比

| | A（推荐）存**逻辑** | B 存物理、读物理 |
|---|---|---|
| 改动 | 写入侧 `.to_logical(scale)`；读取侧不动 | 读取侧改 `PhysicalSize`；写入侧不动 |
| 换 DPI 显示器后 | 逻辑尺寸不变（符合直觉：窗口"看起来一样大"） | 逻辑尺寸跳变（100%→150% 时看起来小 2/3） |
| 旧配置兼容 | 需一次性迁移（旧值是物理） | **天然兼容**（旧值本来就是物理） |
| 未来风险 | 无 | 任何"逻辑读"代码再次踩坑；`dpi` 类型混用不变 |

选 A：B 只是把 bug 搬到读侧，且用户换显示器后体验更差。

### 2.3 迁移设计

```rust
// crates/core/core/src/storage/ui_state.rs
pub struct UiState {
    pub x: Option<i32>, pub y: Option<i32>,
    pub w: u32, pub h: u32,
    pub is_maximized: bool,
    #[serde(default)] pub version: u32,   // 0 = 旧文件（物理值）；2 = 逻辑值
}
```

- 读取入口（`UiStateWrapper::new` 之后、`WindowManager::new` 之前）：`version < 2` 时
  用 `event_loop.primary_monitor().map_or(1.0, |m| m.scale_factor())` 把 `w/h`（及 `x/y`）
  除以 scale 转成逻辑，`version = 2` 落盘一次；
- 迁移结果**夹到工作区**（复用对话框侧已有的 `usable_size` 思路）：旧物理值在 100% 屏上
  转换是恒等，不会动；异常大值（历史 bug 累积的 3240 宽）必须被夹住，否则用户升级后
  第一眼就是超出屏幕的巨窗；
- 已知边角：窗口上次落在**非主屏**且 DPI 与主屏不同，迁移用的是主屏 scale ⇒ 一次性的
  逻辑尺寸偏差（可接受，写进 §7 边界）。

### 2.4 测试（本阶段唯一能真正跑红的红线）

把换算抽成纯函数（新文件 `src/runner/window_manager/geometry.rs`，
`window_manager.rs` 已 344 行，加代码必超 400）：

```rust
pub(super) fn persisted_from(physical: PhysicalSize<u32>, origin: PhysicalPosition<i32>, scale: f64) -> (u32, u32, i32, i32)
pub(super) fn restored_size(state: &UiState, scale: f64) -> PhysicalSize<u32>
```

| 用例 | 断言 |
|---|---|
| 150% 存还原 | 物理 2160×1350 → 存 (1440,900) → 还原 2160×1350 |
| 幂等 | 同 DPI 连续两次"存→还原"，值逐位相同（防复合误差） |
| 跨 DPI | 150% 存 → 100% 还原 ⇒ 逻辑尺寸不变（1440×900） |
| 旧文件迁移 | 无 `version` 的 (2160,1350) @150% ⇒ (1440,900) 且 `version=2` |
| 100% 屏旧文件 | (2160,1350) @1.0 ⇒ 恒等（老用户无感） |
| 夹取 | 迁移结果 > 工作区 ⇒ 被夹到工作区上限 |
| 位置 | x/y 同步换算；`is_maximized` 时不写位置（现行为保留） |

## 3. G-3（P1-3）生命周期注释

- 事实（`crates/editor/dialog/src/manager/lifecycle.rs`）：注释 `:104-110` 说
  "每帧最多推进一个阶段"；正文 `:118-178` 实际是——**同一次调用内**先建窗（阶段 1）、
  随即看到 `gfx_ref().is_none()` 便在同一帧初始化 GFX（阶段 2）；UI（阶段 3）
  至少晚一帧（要靠上一帧把 gfx 建好）。
- 动作：改注释为真实时序 + 补一行"为什么阶段 3 不能同帧"（需要 `main_ui` 与 wgpu
  资源就绪，且 UI 创建含字体扫描，是当初 900ms 卡顿的主因）。
- 不改行为。零风险，先做。

## 7. 边界（本阶段明确不做）

1. **不做 per-monitor 位置/尺寸记忆**（Windows 自己会挪窗口；收益低、状态多）；
2. **不改对话框在 DPI 变化后重新测量尺寸的策略**——测量用的是逻辑尺寸，与 DPI 无关；
3. **不动阶段 A–F 的既有结论**（宽自动计算、高测量、边缘尺子）；
4. 迁移不覆盖「上次落在非主屏且 DPI 不同」的精确还原（见 §2.3 边角）。
