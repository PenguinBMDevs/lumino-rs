## 一、阶段二：ChunkedList 分块存储（P0，核心任务）

### 1.1 目标（2026-08-06 设计修正）

`MidiDocument.notes: Vec<Vec<NoteEvent>>`（每轨一个大 Vec）→ `Vec<ChunkedList<NoteEvent>>`（每轨分块存储）。

**⚠️ 设计断点：分块单位是「事件」，不是「音符」**（用户评审确认）：

- 引擎里所有「按 tick 有序」的数据都面临同一个插入 O(N) 退化问题：`notes`、`control_events`、`tempo_changes`、`time_signatures`、`automation_lanes[].events`。
- 所以抽象为**泛型有序事件容器 `ChunkedList<T>`**，一套二分/分裂/前缀和代码吃所有类型，而非写死 `ChunkedNotes`。避免重复实现 = 铺三套结构，违背不养闲，把机会成本记在验收表里。
- **容量以「事件数」计**：`EVENT_CHUNK_CAPACITY = 500_000`（CC 事件量级一致性），不是以音符数。

- **每块容量 50W 事件**（50 万 = 500_000，NoteEvent 16B 时 ~8MB/块）
- **动态分裂**：向满块（50W）插入事件 → 分裂为两个 25W 块（容量保持 50W），在正确位置插入
- **块查找加速**：块级二分（`chunk_first_ticks`）+ 块内二分（`partition_point`）
- **对外 API 签名不变**（Commit 1b 已铺好隔离墙，下游零波及）

### 1.2 新文件：`crates/midi-model/src/chunked_list.rs`（泛型，注意命名不带 notes）

```rust
/// 单块容量：50 万事件
pub const EVENT_CHUNK_CAPACITY: usize = 500_000;
/// 分裂点：满块分裂为两个 25W 块（容量保持 50W 不变）
pub const EVENT_CHUNK_SPLIT: usize = 250_000;

/// 有序事件容器（泛型）。
/// 适用于任何「按 tick 排序的非唯一性事件」：NoteEvent、PackedControlEvent、
/// AutomationEvent、TempoPoint 等。
pub struct ChunkedList<T> {
    chunks: Vec<Vec<T>>,            // 块间按 tick 有序，块内 also 有序
    chunk_first_ticks: Vec<u32>,    // 每块首事件 tick（块级二分）
    chunk_offsets: Vec<usize>,      // 前缀和（全局索引二分）
    total_len: usize,
}

/// 事件必须能取出 tick（实现该 trait；NoteEvent/PackedControlEvent 都满足）
pub trait EventTick {
    fn tick(&self) -> u32;
}
```

### 1.3 核心操作设计

| 操作 | 实现 | 复杂度 |
|------|------|--------|
| `from_sorted(Vec<T>)` | 排序后按 50W 切块 + 双索引 | O(N) |
| `insert(tick, T)` | ① 块级二分 → ② 块内二分 → ③ 满块分裂（25W/25W，插中间）→ ④ 插入正确位置 → ⑤ 局部更新首 tick + offsets | O(块内 25W + 块级 ~120) |
| `replace(tick, T)` | 「同 tick 覆盖」语义：二分定位 + 直接替换 | O(log 块数) |
| `get(global_idx)` | chunk_offsets.partition_point 定位块 → 块内索引 | O(log 块数) |
| `iter()` / `iter_refs()` | 跨块迭代器 | O(N) |
| `range(start_tick, end_tick)` | 块级二分（first_ticks）+ 块内二分 | O(log 块数 + 命中量) |
| `remove(global_idx)` / `remove_by_tick(tick)` | 块内删除 + 空块合并 | O(块内) |
| `len()` / `is_empty()` | O(1) | — |

**分裂语义**（用户明确需求）：
```
满块 [50W] 插入事件
  → 分裂为 [25W] + [25W]（各容量 50W）
  → 判断插入位置：若 ≤ 25W 插左块，否则插右块
  → 块内二分插入
```

### 1.4 落点：用到它的三类数据（按优先级）

```rust
pub struct MidiDocument {
    pub notes: Vec<ChunkedList<NoteEvent>>,          // 1. 音符（黑乐谱一轨 6000W，最重）
    pub control_events: ChunkedList<midly::loader::PackedControlEvent>, // 2. 全局 CC/PC/PB（百万级）
    // tempo_changes / time_signatures / key_signatures 暂保持 Vec（量小，无需分块）
}

// 3. 编辑器热路径：自动化 lane（CC 绘制），次优先级
EditorData::automation_lanes[idx].events: ChunkedList<AutomationEvent>
```

- **注意边缘 case**：`MidiDocument.notes` 是 `Vec<ChunkedList<NoteEvent>>`，`control_events` 是单个 `ChunkedList`（全局一列），两者不是一个维度，分块事件迭代时要带着区分。
- `track_notes(track_id)` 返回类型问题：现为 `&[NoteEvent]`（连续切片），分块后**无法返回连续切片**——改为返回 `&ChunkedList<NoteEvent>` 或新增迭代器 API。这是唯一破坏影响点，但 Commit 1b 已把下游收拢到访问器层，实际只改访问器内部。
- `from_notes_bytes` 构建路径：排序后 `ChunkedList::from_sorted`
- 现有方法（track_notes / get_events / all_events 等 10 个）内部改走分块 API

### 2.1 播放引擎 Arc 视图（核心）

**方案 A（推荐）**：`MidiDocument.notes` 轨道数据内部 Arc 化

```rust
pub struct ChunkedList<T> {
    chunks: Vec<Arc<Vec<T>>>,       // 分块后天然可共享（每块可为 Arc）
    chunk_first_ticks: Vec<u32>,
    chunk_offsets: Vec<usize>,
    total_len: usize,
}
```

- EditorData 持有 `Arc<MidiDocument>`（唯一强引用），编辑走 `Arc::get_mut`（单引用时 O(1) 原地写）
- 播放引擎/导出持 `Arc<MidiDocument>` 弱引用或独立 Arc 视图（只读）
- 编辑只 COW 被修改的块，其余块共享

**实施**：
1. `midi_state.document: Option<Arc<MidiDocument>>` 恢复赋值（从 EditorData 克隆 Arc，O(1)）
2. `PlaybackEngine::set_document` 恢复正常路径
3. 音频/视频导出"内存模式"恢复
4. 验证：播放其他音轨、导出 356MB 黑乐谱无降级
