# GPU 检测子进程隔离 · 实施记录

- 日期：2026-10-23
- 关联卡：GPU 检测挂起（设置页手动检测卡死 UI）
- 关联：UI-008 / #37（启动路径同类冻结）、REND-019（TDR 恢复，另卡）、#39（缓存回写）

## 1. 问题与根因

进程内检测线程一旦在驱动调用（Vulkan loader / ICD / 队列提交 / 围栏等待）里挂起，
`recv_timeout` 只能「放弃等待」——Rust 没有线程取消，线程会 detach 并继续持有驱动锁，
把主渲染的提交 / present 一起拖死，表现为整个 UI 卡死，与「没有超时」体感一致。

> 根因一句话：**把不可取消的 FFI 调用放在 UI 依赖的进程里，并用「等待超时」冒充「执行终止」。**

因此根治手段不是调大 / 调小超时，而是把检测搬到**可强杀的执行边界**：子进程。

## 2. 结构

| 模块 | 职责 |
|------|------|
| `src/device_probe.rs` | 模式判定、参数编码、平台分派（入口） |
| `src/device_probe/child.rs` | 子进程：解析参数 → 起看门狗 → 检测/枚举 → 原子写结果 |
| `src/device_probe/supervisor.rs` | 父进程：启动 / 超时强杀 / 收割 / 解析 |
| `src/device_probe/supervisor/job.rs` | Windows Job Object（父进程崩溃连带杀子进程） |
| `src/device_probe/wire.rs` | IPC 契约（协议版本 + DTO，**不复用** gfx 内部类型） |

两种模式（同一子进程二进制）：

- `full`：完整检测（建实例 / 建设备 / 离屏试画）→ 回传完整报告；
- `fingerprints`：只枚举适配器指纹（启动缓存校验）→ 回传指纹列表。
  该模式超时**不写文件**——空列表会被误读成「探测成功但零适配器」，
  父进程按 cache miss 处理即可。

入口判定必须早于日志 / puffin / 内存监控 / clap：

```rust
if device_probe::is_child_mode() { device_probe::run_child_mode(); }
logging::init();
```

晚一步会抢 8585 端口、起看门狗线程、往 stdout 灌日志，或被 clap 以未知参数拒绝（退出码 2）。

## 3. 超时与强杀（双保险）

- 子进程看门狗：`timeout` 到点写结构化 `Timeout` 结果并 `process::exit(0)`；
- 父进程硬杀：`timeout + 500ms` 时 `Child::kill()`（Windows = `TerminateProcess`）并 `wait()` 收割。

**为什么两层**：`ExitProcess` 可能被 loader 锁卡住，子进程自杀只是优雅路径；
`TerminateProcess` 是唯一硬保证。反过来，硬杀拿不到结构化结果，看门狗负责「有结果地退出」。
两者产物都是 `Timeout`，语义一致。

**写锁**：看门狗与主线程通过 `Mutex<()> + AtomicBool` 互斥，避免看门狗在
「主线程正在写 JSON」的瞬间退出进程、留下半截文件。

## 4. 失败语义（fail closed）

子进程无法启动 / 崩溃 / 输出不可解析 / 协议版本不匹配 → `GpuCheckFailure::Aborted`，
**绝不静默降级回进程内检测**：降级等于把已知会冻死 UI 的路径重新打开。

为此新增 `GpuCheckFailure::Aborted(String)` 与 `GpuCheckOutcome::ProbeFailed`，
UI 侧落到「检测失败」并展示 `检测执行异常: …`（与「渲染失败」「超时」可区分）。

## 5. 平台口径（范围决策）

| 平台 | 完整检测 | 廉价探测（启动缓存校验） |
|------|----------|--------------------------|
| Windows | **子进程**（可强杀 + Job Object） | **子进程**（同一探针的 fingerprints 模式） |
| macOS / Linux | **子进程**（supervisor 为跨平台 std 代码） | **子进程** |

早期版本曾在 macOS / Linux 保留进程内线程模型（卡片范围决策），本版已收敛为
**全平台单一路径**：只有一套生产代码要维护、测试与解释。`lumino-gfx` 里的线程
包装（`run_check_with_timeout` / `probe_adapter_fingerprints_with_timeout`）保留为
测试与诊断 API，生产路径不再调用。

## 6. 已知遗留

1. **进程启动开销**：debug 构建实测指纹探针 810ms（其中枚举约 100ms、进程启动约
   700ms），全量检测子进程 1874ms（检测 898ms）。release 预期 200-300ms，**尚未实测**。
   若启动开销不可接受，优化顺序：
   a. 把探针拆成独立小 exe（只链 wgpu，不链整个应用）；
   b. 缓存探针结果（同一会话内只探一次）；
   c. 最后手段才是回退线程探测（会重新引入 detach 泄漏，不推荐）。
2. **debug 构建的启动开销**会吃掉 3s 预算的一部分：极端情况下父进程硬杀可能先于
   看门狗写结果——产物仍是 `Timeout`，语义不变；release 无此问题。
3. 文件长度已回到 400 行红线内：`supervisor.rs` 512 → 288（单测拆到
   `supervisor/tests.rs`），`child.rs` 244、`wire.rs` 321、`check.rs` 259、
   `timeout.rs` 185。

## 7. 验证记录

- 真实子进程（debug）：`--device-check-probe-mode full` 正常路径 **1874ms**
  （检测 898ms），写出 v1 协议 JSON（Vulkan 适配器 + DX12/GL 回退诊断 + 指纹）。
- 指纹模式（debug）：**810ms**，写出
  `{"version":1,"fingerprints":["Vulkan|NVIDIA GeForce RTX 2060|NVIDIA|610.62|DiscreteGpu"]}`。
- 挂起注入：`LUMINO_DEBUG_CHECK_HANG=1` + 超时 1500ms → 1700ms 内写出
  `{"failure":"Timeout"}`，退出码 0，无残留进程。
- 指纹模式挂起：`LUMINO_DEBUG_PROBE_HANG=1` + 超时 1500ms → 看门狗退出且**不写文件**
  （父进程按 cache miss 处理）。
- 单元测试 17 条（协议往返 / 版本拒绝 / 原子写读 / 强杀收割 / 无结果 → Aborted /
  损坏 → Aborted / 路径唯一 / 父参数 ↔ 子解析契约 / 策略编解码 / 指纹三种失败路径）。
- 集成测试 5 条（真实二进制：完整报告、挂起看门狗、指纹列表、指纹挂起不写文件、
